# Приложение J. Unsafe Rust Checklist

`unsafe` в Rust — это мощный, но опасный инструмент. Его использование требует особой осторожности и тщательной проверки. Это приложение поможет вам убедиться, что вы не упустили важные моменты перед тем, как использовать `unsafe`.

---

## J.1. Проверка необходимости

| Вопрос | Ответ |
| --- | --- |
| **Можно ли обойтись без `unsafe`?** | Всегда задавайте этот вопрос первым. |
| **Есть ли безопасная альтернатива?** | Проверьте стандартную библиотеку и крейты. |
| **Понятно ли, почему `unsafe` нужен именно здесь?** | Не используйте `unsafe` "на всякий случай". |

**Действие:** Если можно обойтись без `unsafe` — не используйте его.

## J.4. Сырые указатели (Raw Pointers)

| Вопрос | Ответ |
| --- | --- |
| **Указывает ли указатель на валидную память?** | Да, память выделена и не освобождена. |
| **Выровнен ли указатель для типа?** | `align_of::<T>()` должно быть соблюдено. |
| **Инициализирована ли память?** | Не читайте неинициализированную память. |
| **Не выходит ли доступ за границы?** | Проверьте размер выделенной памяти. |
| **Не является ли указатель null?** | Проверьте `ptr.is_null()` перед разыменованием. |
| **Правильно ли обработано владение?** | Кто владеет памятью? Кто освобождает? |

**Пример безопасной работы:**

```rust
fn main() {
    let x = 42;
    let ptr = &x as *const i32;
    unsafe {
        println!("Значение по указателю: {}", *ptr);
    }
}

```

## J.5. Pointer Arithmetic

| Вопрос | Ответ |
| --- | --- |
| **Не выходит ли арифметика за пределы выделенной области?** | Всегда проверяйте границы. |
| **Корректно ли вычислен размер типа?** | `size_of::<T>()` используется правильно. |
| **Не происходит ли переполнение указателя?** | Адрес должен оставаться в пределах адресного пространства. |
| **Не создаётся ли указатель, который выходит за допустимый диапазон?** | Только в пределах выделенной памяти. |

**Пример:**

```rust
fn main() {
    let arr = [1, 2, 3, 4, 5];
    let ptr = arr.as_ptr();
    unsafe {
        // ✅ Корректное смещение в пределах массива
        let third = *ptr.add(2);
        println!("Третий элемент: {}", third);
    }
}

```

## J.6. Преобразования (Transmutations)

| Вопрос | Ответ |
| --- | --- |
| **Почему нужно `transmute`?** | Есть ли безопасная альтернатива? |
| **Одинаков ли размер типов?** | `size_of::<From>() == size_of::<To>()` |
| **Корректно ли выравнивание?** | Выравнивание должно быть совместимо. |
| **Не нарушена ли семантика владения?** | Считается ли память перемещённой? |
| **Не нарушены ли инварианты типов?** | Например, `bool` должен быть 0 или 1. |

```rust
use std::mem;

fn main() {
    // ⚠️ Безопасное преобразование при совпадении размеров
    let x: u8 = 42;
    let y: i8 = unsafe { mem::transmute(x) };
    println!("Transmuted value: {}", y);
}

```

## J.8. Unsafe функции и трейты

| Вопрос | Ответ |
| --- | --- |
| **Документированы ли требования безопасности?** | `# Safety` секция должна быть. |
| **Проверяются ли инварианты вызывающим?** | Или вы проверяете внутри? |
| **Есть ли уверенность, что вызывающий соблюдает контракт?** | Убедитесь, что вы не возлагаете неоправданных ожиданий. |
| **Может ли функция использоваться безопасно?** | Или она всегда должна быть `unsafe`? |

**Документация `unsafe` функции:**

```rust
/// Делает что-то.
///
/// # Safety
///
/// - `ptr` должен указывать на валидную память.
/// - `ptr` должен быть выровнен для `T`.
/// - Память должна быть инициализирована.
unsafe fn do_something<T>(ptr: *const T) -> T {
    *ptr
}

```

## J.9. `static mut`

| Вопрос | Ответ |
| --- | --- |
| **Безопасен ли доступ из разных потоков?** | `static mut` не синхронизируется. |
| **Есть ли гонка данных?** | Используйте `Mutex`, `Atomic` или `UnsafeCell`. |
| **Можно ли использовать `OnceLock` или `LazyLock`?** | В большинстве случаев да. |
| **Документированы ли инварианты?** | Кто и как использует переменную? |

```rust
use std::sync::atomic::{AtomicI32, Ordering};

fn main() {
    // ✅ Безопасная альтернатива static mut с использованием атомиков
    static COUNTER: AtomicI32 = AtomicI32::new(0);
    COUNTER.fetch_add(1, Ordering::Relaxed);
    println!("Counter: {}", COUNTER.load(Ordering::Relaxed));
}

```

## J.11. `MaybeUninit` и `UnsafeCell`

| Вопрос | Ответ |
| --- | --- |
| **Инициализирована ли память перед чтением?** | `assume_init()` только после записи. |
| **Не читается ли неинициализированная память?** | Используйте `MaybeUninit::uninit()` и `write()`. |
| **Корректно ли используется `UnsafeCell`?** | Только когда нужна внутренняя изменяемость. |

```rust
use std::mem::MaybeUninit;

fn main() {
    // ✅ Правильное использование MaybeUninit
    let mut uninit = MaybeUninit::<i32>::uninit();
    uninit.write(42);
    unsafe {
        println!("Инициализированное значение: {}", uninit.assume_init());
    }
}

```

### Главное из этого приложения

После этого приложения мы:

* **Понимаем**, когда нужен `unsafe`.
* **Знаем**, какие инварианты нужно проверять.
* **Умеем** документировать требования безопасности.
* **Знаем**, как тестировать `unsafe` код.
* **Понимаем**, как минимизировать риски.

**Самая важная идея:**

> `unsafe` — это не "отключение" проверок, а ответственность. Используйте его только когда необходимо, всегда документируйте инварианты, проверяйте все условия и тестируйте критичные пути. Помните: безопасная абстракция над `unsafe` — это цель, а не сам `unsafe` код.
