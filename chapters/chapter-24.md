# Глава 24. `Send` и `Sync`

В предыдущей главе мы создавали потоки и передавали данные между ними. Вы могли заметить, что не все типы можно передавать между потоками. Некоторые типы работают, другие — нет. Почему?

В Rust есть специальные **автоматические трейты (auto traits)**, которые определяют, можно ли безопасно использовать тип в многопоточном коде. Это трейты `Send` и `Sync`. Они являются фундаментом безопасности параллельного программирования в Rust.

В этой главе мы разберёмся, что означают `Send` и `Sync`, как они работают, и почему это одна из самых важных инноваций Rust.

Все примеры этой главы используют **Rust Edition 2024** и подготовлены для запуска непосредственно в [Rust Playground](https://play.rust-lang.org/).

---

## 24.1. Что такое автоматические трейты (auto traits)?

`Send` и `Sync` относятся к особому классу трейтов Rust — **автоматическим трейтам (auto traits)**.

Автоматический трейт отличается от обычного тем, что компилятор может вывести его наличие для сложных типов на основании составляющих их типов.

Например:

```rust
struct Data {
    number: i32,
    text: String,
}
```

`i32` и `String` являются `Send`, поэтому компилятор может вывести, что и `Data` является `Send`.

То же самое происходит с `Sync`.

В общем случае:

```text
struct / enum / tuple
        │
        ▼
свойства составляющих типов
        │
        ▼
Send / Sync всего типа
```

Это один из важнейших принципов системы типов Rust: программисту не требуется вручную объявлять потокобезопасность обычных составных типов.

В стандартной библиотеке `Send` и `Sync` объявлены как `unsafe auto trait`. Компилятор автоматически реализует их, когда это допустимо. Стандартная библиотека также может явно запрещать реализацию auto trait для отдельных типов. ([Rust Documentation][3])

Два главных auto traits, связанные с многопоточностью:

| Трейт      | Смысл                                                                                 |
| ---------- | ------------------------------------------------------------------------------------- |
| **`Send`** | значение типа `T` можно безопасно передать владением в другой поток                   |
| **`Sync`** | значение типа `T` можно безопасно совместно использовать через `&T` из разных потоков |

Очень важно не путать эти свойства.

`Send` отвечает прежде всего на вопрос:

> **Можно ли передать само значение?**

`Sync` отвечает на вопрос:

> **Можно ли безопасно одновременно предоставить другим потокам доступ к этому значению через shared reference?**

Формально между ними существует фундаментальное правило:

```text
T: Sync  ⇔  &T: Send
```

То есть тип `T` является `Sync` тогда и только тогда, когда ссылку `&T` можно безопасно передать в другой поток. ([Rust Documentation][3])

## 24.2. Что означает `T: Send`?

`Send` означает, что **значение типа `T` можно безопасно передать через границу потока**.

Например:

```rust
use std::thread;

fn main() {
    let value = 42;

    let handle = thread::spawn(move || {
        println!("{value}");
    });

    handle.join().unwrap();
}
```

Здесь `i32` является `Send`, поэтому владение `value` можно передать в новый поток.

Обратите внимание: `Send` относится именно к **передаче значения**, а не к совместному использованию одного и того же значения несколькими потоками.

Например:

```text
i32
 │
 └── move ──► другой поток
```

Это случай `Send`.

Для большинства обычных типов Rust `Send` выводится автоматически.

Например:

- `i32`, `bool`, `char`;
- `String`;
- `Vec<T>`, если `T: Send`;
- `Box<T>`, если `T: Send`;
- структуры, все поля которых являются `Send`.

Условие особенно важно для generic-типов:

```rust
struct Container<T> {
    value: T,
}
```

Если `T` не является `Send`, то и `Container<T>` не становится `Send` автоматически.

Именно поэтому нельзя запомнить простое правило «`Vec` всегда `Send`». Правильнее говорить:

```text
Vec<T>: Send  если T: Send
```

## 24.3. Что означает `T: Sync`?

`Sync` отвечает за **безопасное совместное использование значения**.

Формально:

```text
T: Sync
```

означает:

```text
&T: Send
```

То есть shared reference `&T` можно передать в другой поток.

Для демонстрации этого свойства удобно использовать `thread::scope`.

```rust
use std::thread;

fn main() {
    let value = 42;

    thread::scope(|scope| {
        scope.spawn(|| {
            println!("Поток 1: {value}");
        });

        scope.spawn(|| {
            println!("Поток 2: {value}");
        });
    });
}
```

Здесь два потока одновременно получают доступ к одному значению `value`.

Само значение `value` никуда не перемещается.

Каждый поток получает shared reference:

```text
             ┌── &value ──► поток 1
value ───────┤
             └── &value ──► поток 2
```

Это именно тот случай, для которого требуется `Sync`.

`thread::scope` здесь важен не случайно. Обычный `thread::spawn` требует, чтобы данные, захваченные потоком, могли жить достаточно долго (`'static`). Scoped threads позволяют безопасно использовать локальные данные родительского потока в дочерних потоках, пока область `scope` не завершилась.

Поэтому два понятия можно представить так:

```text
Send
 │
 └── передаём владение значением

Sync
 │
 └── несколько потоков получают &T
```

И фундаментальная связь:

```text
T: Sync
    ⇔
&T: Send
```

## 24.4. Почему `Rc<T>` не реализует `Send`?

`Rc<T>` использует обычный, **неатомарный** счётчик ссылок.

Если два потока одновременно будут изменять этот счётчик, операции могут конфликтовать.

Поэтому Rust запрещает передавать `Rc<T>` между потоками:

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let data = Rc::new(42);

    let handle = thread::spawn(move || {
        println!("{data}");
    });

    handle.join().unwrap();
}
```

Этот код не компилируется.

Компилятор сообщает, что:

```text
Rc<i32> cannot be sent between threads safely
```

Это не недостаток компилятора.

Наоборот, компилятор обнаруживает потенциально небезопасную модель использования типа ещё до запуска программы.

`Rc` предназначен для совместного владения **в пределах одного потока**.

Если требуется совместное владение между потоками, используется `Arc`.

`Send` в данном случае можно сформулировать очень просто:

```text
Rc<T>
  │
  └── нельзя move в другой поток
```

## 24.5. Почему `Arc<T>` не делает любой `T` потокобезопасным?

`Arc<T>` — атомарный аналог `Rc<T>`.

Он использует атомарные операции для управления счётчиком ссылок, поэтому несколько потоков могут безопасно владеть одним `Arc`.

Например:

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(42);

    let first = Arc::clone(&data);
    let second = Arc::clone(&data);

    let handle1 = thread::spawn(move || {
        println!("Поток 1: {first}");
    });

    let handle2 = thread::spawn(move || {
        println!("Поток 2: {second}");
    });

    handle1.join().unwrap();
    handle2.join().unwrap();
}
```

Здесь два потока владеют разными `Arc`, которые указывают на одно значение:

```text
                  ┌── Arc ──► 42
                  │
data ─────────────┤
                  │
                  └── Arc ──► 42
```

Но существует важное правило:

> **`Arc<T>` реализует `Send` и `Sync` только тогда, когда `T` реализует и `Send`, и `Sync` одновременно — для обеих реализаций требуются оба ограничения сразу.**

Формально в стандартной библиотеке это выглядит так:

```rust
unsafe impl<T: ?Sized + Sync + Send> Send for Arc<T> {}
unsafe impl<T: ?Sized + Sync + Send> Sync for Arc<T> {}
```

Обратите внимание: даже реализация `Send` для `Arc<T>` требует `T: Sync`, а не только `T: Send`. Причина в том, что отправка `Arc<T>` в другой поток фактически даёт этому потоку возможность получить `&T` (через разыменование `Arc`) — а значит, если бы `T` не был `Sync`, другой поток мог бы получить недопустимый доступ к `&T` из чужого потока в обход правил.

Рассмотрим конкретный пример:

```rust
Arc<RefCell<i32>>
```

`RefCell<i32>` **реализует** `Send` (так как `i32: Send`), но **не реализует** `Sync`. Из-за этого `Arc<RefCell<i32>>` не удовлетворяет условию `T: Send + Sync` ни для одной из двух реализаций — то есть `Arc<RefCell<i32>>` является **ни `Send`, ни `Sync`**, а не только «не `Sync`», как можно было бы подумать по аналогии с самим `RefCell<i32>`.

```text
Arc<RefCell<i32>>
 │
 └── RefCell<i32>: Send, но !Sync
       │
       └── условие Arc (T: Send + Sync) не выполнено ни для Send, ни для Sync
             │
             └── Arc<RefCell<i32>>: !Send и !Sync
```

Поэтому стандартная комбинация для общего изменяемого состояния выглядит так:

```rust
Arc<Mutex<T>>
```

Здесь ответственность разделена:

```text
Arc
 │
 └── безопасное совместное владение

Mutex
 │
 └── безопасный доступ к изменяемому T
```

`Mutex<T>` реализует и `Send`, и `Sync` при более мягком условии — достаточно `T: Send` (не требуется `T: Sync`, потому что `Mutex` сам гарантирует эксклюзивный доступ через блокировку), поэтому `Arc<Mutex<T>>` реализует `Send + Sync`, как только `T: Send` — мы разберём это подробнее в разделе 24.7.

## 24.6. Почему `RefCell<T>` не реализует `Sync`?

`RefCell<T>` позволяет проверять правила заимствования **во время выполнения**, а не во время компиляции.

Это полезно внутри одного потока, но механизм `RefCell` сам по себе не предназначен для одновременного доступа нескольких потоков.

Поэтому:

```text
RefCell<T>: !Sync
```

Но здесь есть важное уточнение:

> `RefCell<T>` **может быть `Send`**, если `T: Send`.

Это принципиально важно.

Например:

```rust
use std::cell::RefCell;
use std::thread;

fn main() {
    let data = RefCell::new(42);

    let handle = thread::spawn(move || {
        *data.borrow_mut() = 100;
        println!("{}", data.borrow());
    });

    handle.join().unwrap();
}
```

Этот код корректен.

Почему?

Потому что `RefCell` **перемещается целиком** в новый поток:

```text
поток main
    │
    │ move
    ▼
RefCell<i32>
    │
    ▼
новый поток
```

Здесь нет совместного использования одного `RefCell` двумя потоками.

А вот попытка одновременно предоставить другим потокам `&RefCell<T>` требует `RefCell<T>: Sync` и поэтому невозможна.

Именно поэтому предыдущая формулировка:

> «`RefCell<T>` нельзя передать между потоками»

была неверной.

Правильнее:

> `RefCell<T>` нельзя безопасно **совместно использовать через `&T` из нескольких потоков**, поэтому `RefCell<T>` не реализует `Sync`.

Документация стандартной библиотеки явно показывает эту комбинацию:

```text
RefCell<T>
    Send
    !Sync
```

при соответствующих условиях для `T`. ([Rust Documentation][4])

## 24.7. `Mutex<T>` и потокобезопасный доступ к данным

`Mutex<T>` предназначен для ситуации, когда несколько потоков должны иметь доступ к одному изменяемому значению.

Он гарантирует, что одновременно получить изменяемый доступ через mutex сможет только один поток.

Типичная комбинация выглядит так:

```text
Arc<Mutex<T>>
```

Например:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(0));

    let first = Arc::clone(&data);
    let second = Arc::clone(&data);

    let handle1 = thread::spawn(move || {
        let mut value = first.lock().unwrap();
        *value += 1;
    });

    let handle2 = thread::spawn(move || {
        let mut value = second.lock().unwrap();
        *value += 1;
    });

    handle1.join().unwrap();
    handle2.join().unwrap();

    println!("{}", *data.lock().unwrap());
}
```

Результат:

```text
2
```

Здесь:

```text
Arc
 │
 └── позволяет нескольким потокам владеть Mutex

Mutex
 │
 └── защищает доступ к T
```

Важное свойство `Mutex<T>`:

```text
Mutex<T>: Send  если T: Send
Mutex<T>: Sync  если T: Send
```

Для `Sync` не требуется `T: Sync`.

Это может показаться неожиданным, но логика заключается в том, что `Mutex` не предоставляет несколько одновременных ссылок на `T`: доступ защищён блокировкой и предоставляется одному владельцу guard за раз. ([Rust Documentation][2])

## 24.8. Таблица `Send` / `Sync` для распространённых типов

Полезно не запоминать таблицу как набор исключений, а понимать правила, по которым свойства выводятся.

| Тип                   |           `Send` |           `Sync` | Условие / причина                                    |
| --------------------- | ---------------: | ---------------: | ---------------------------------------------------- |
| `i32`, `bool`, `char` |               ✅ |               ✅ | обычные потокобезопасные значения                    |
| `String`              |               ✅ |               ✅ | компоненты типа потокобезопасны                      |
| `Vec<T>`              |        `T: Send` |        `T: Sync` | свойства зависят от `T`                              |
| `Box<T>`              |        `T: Send` |        `T: Sync` | свойства зависят от `T`                              |
| `Rc<T>`               |               ❌ |               ❌ | неатомарный reference counting                       |
| `Arc<T>`              | `T: Send + Sync` | `T: Send + Sync` | атомарное совместное владение                        |
| `RefCell<T>`          |        `T: Send` |               ❌ | runtime borrow checking, но не thread-safe           |
| `Mutex<T>`            |        `T: Send` |        `T: Send` | синхронизированный доступ                            |
| `RwLock<T>`           |        `T: Send` | `T: Send + Sync` | concurrent read / exclusive write                    |
| `*const T`            |               ❌ |               ❌ | raw pointers не являются `Send`/`Sync` автоматически |
| `*mut T`              |               ❌ |               ❌ | raw pointers не являются `Send`/`Sync` автоматически |
| `&T`                  |        `T: Sync` |        `T: Sync` | shared reference                                     |
| `&mut T`              |        `T: Send` |        `T: Sync` | exclusive reference                                  |

Для generic-типов особенно важно видеть именно **условие**, а не просто `✅`.

Например:

```text
Vec<i32>: Send + Sync
```

но:

```text
Vec<Rc<i32>>: не Send и не Sync
```

потому что свойства контейнера определяются свойствами содержащегося типа.

Это прямое следствие правил auto traits: для составных типов компилятор выводит свойства на основе их компонентов, если стандартная библиотека не задаёт специальное исключение. ([Rust Documentation][3])

## 24.9. Проверка `Send` и `Sync` на практике

`Send` и `Sync` можно проверять непосредственно через ограничения generic-функций.

```rust
fn is_send<T: Send>() {}
fn is_sync<T: Sync>() {}

fn main() {
    is_send::<i32>();
    is_sync::<i32>();

    is_send::<String>();
    is_sync::<String>();

    is_send::<std::cell::RefCell<i32>>();

    is_send::<std::sync::Arc<i32>>();
    is_sync::<std::sync::Arc<i32>>();

    is_send::<std::sync::Mutex<i32>>();
    is_sync::<std::sync::Mutex<i32>>();
}
```

Важный момент:

```rust
is_send::<std::cell::RefCell<i32>>();
```

**компилируется**.

А:

```rust
is_sync::<std::cell::RefCell<i32>>();
```

не компилируется.

Это позволяет увидеть реальное различие между двумя auto traits, а не запоминать упрощённое правило «`RefCell` нельзя использовать в потоках».

Для проверки отрицательных случаев можно раскомментировать соответствующие строки:

```rust
fn is_send<T: Send>() {}
fn is_sync<T: Sync>() {}

fn main() {
    // Rc не является Send:
    // is_send::<std::rc::Rc<i32>>();

    // RefCell не является Sync:
    // is_sync::<std::cell::RefCell<i32>>();

    // Arc<i32> является Send + Sync:
    is_send::<std::sync::Arc<i32>>();
    is_sync::<std::sync::Arc<i32>>();
}
```

Такой способ проверки особенно полезен при работе с незнакомыми generic-типами.

Вместо вопроса:

> «Кажется ли мне, что этот тип потокобезопасен?»

можно задать компилятору конкретный вопрос:

```rust
fn requires_send<T: Send>() {}
fn requires_sync<T: Sync>() {}
```

и позволить системе типов дать ответ.

## 24.10. `Send` и `Sync` как часть API

`Send` и `Sync` являются не только внутренним механизмом стандартной библиотеки. Они непосредственно влияют на дизайн API.

Рассмотрим функцию:

```rust
use std::thread;

fn spawn_on_thread<F, T>(f: F) -> thread::JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
{
    thread::spawn(f)
}

fn main() {
    let handle = spawn_on_thread(|| 42);

    println!("{}", handle.join().unwrap());
}
```

Здесь ограничения имеют конкретный смысл.

### `F: Send`

Замыкание `F` должно быть возможно передать в другой поток.

```text
main thread
    │
    │ F: Send
    ▼
worker thread
```

### `T: Send`

Результат, который создаёт поток, должен быть возможно безопасно передать обратно владельцу `JoinHandle`.

### `'static`

Это уже не `Send` и не `Sync`.

`'static` означает, что тип не должен содержать заимствований, которые могут стать недействительными до окончания жизни spawned thread.

Таким образом:

```rust
F: FnOnce() -> T + Send + 'static
```

означает:

> это замыкание можно передать в поток, и оно не содержит недопустимых короткоживущих заимствований.

А:

```rust
T: Send + 'static
```

означает:

> результат можно безопасно передать из потока, и он не зависит от короткоживущих заимствований.

Это хороший пример того, как система типов превращает требования многопоточной архитектуры в часть API.

### Эксперимент 1. Попытка передать `Rc` в поток

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let data = Rc::new(42);

        println!("{data}");

```

Код не компилируется.

Компилятор сообщает, что `Rc<i32>` не может быть передан между потоками.

Причина:

```text
Rc<T>: !Send
```

### Эксперимент 2. `RefCell` можно переместить в поток

Попробуйте следующий код:

```rust
use std::cell::RefCell;
use std::thread;

fn main() {
    let data = RefCell::new(42);

    let handle = thread::spawn(move || {
        *data.borrow_mut() = 100;
        println!("{}", data.borrow());
    });

    handle.join().unwrap();
}
```

Этот код **компилируется**.

Это важный эксперимент, потому что он разрушает распространённое упрощение:

> «`RefCell` нельзя использовать с потоками».

Правильнее:

```text
RefCell<T>
    ├── Send   если T: Send
    └── !Sync
```

`RefCell` можно переместить целиком в другой поток.

Нельзя безопасно одновременно использовать один `RefCell` из нескольких потоков через shared references.

---

### Эксперимент 3. Попытка поделиться `RefCell` между потоками

Теперь изменим программу:

```rust
use std::cell::RefCell;
use std::thread;

fn main() {
    let data = RefCell::new(42);

    thread::scope(|scope| {
        scope.spawn(|| {
            println!("{}", data.borrow());
        });

        scope.spawn(|| {
            println!("{}", data.borrow());
        });
    });
}
```

Теперь компилятор должен остановить программу.

Причина:

```text
RefCell<i32>: !Sync
```

Потокам необходимо получить доступ к одному `RefCell` через shared reference, а `RefCell` не предоставляет требуемой потокобезопасности.

---

### Эксперимент 4. `Arc` не заменяет `Mutex`

Попробуйте:

```rust
use std::cell::RefCell;
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(RefCell::new(0));

    let first = Arc::clone(&data);
    let second = Arc::clone(&data);

    thread::scope(|scope| {
        scope.spawn(|| {
            *first.borrow_mut() += 1;
        });

        scope.spawn(|| {
            *second.borrow_mut() += 1;
        });
    });
}
```

Этот код не компилируется.

Может показаться, что причина в том, что оба потока совместно обращаются к `RefCell` без синхронизации — и это действительно так, если бы `Arc<RefCell<i32>>` вообще можно было безопасно передавать в поток. Но на самом деле здесь останавливающая проблема ещё более фундаментальная: `RefCell<i32>` реализует `Send` (поскольку `i32: Send`), но не реализует `Sync` — а `Arc<T>` требует от `T` **обоих** свойств (`Send + Sync`) сразу, чтобы сам `Arc<T>` мог быть `Send`. Значит, `Arc<RefCell<i32>>` не реализует даже `Send`, и компилятор откажется передавать значения `first`/`second` внутрь замыканий `scope.spawn(...)` уже на этом основании — то есть до того, как вообще встанет вопрос об одновременном доступе.

```text
Arc<RefCell<i32>>
    │
    ├── RefCell<i32>: Send ✓, но Sync ✗
    │
    └── Arc<T> требует T: Send + Sync для своих Send и Sync
              │
              └── условие не выполнено → Arc<RefCell<i32>>: !Send и !Sync
```

Для такого сценария требуется, например:

```rust
Arc<Mutex<i32>>
```

`Mutex<i32>` реализует и `Send`, и `Sync` уже при одном лишь условии `i32: Send` (подробнее — в разделе 24.7), поэтому `Arc<Mutex<i32>>` полностью потокобезопасен: и сам `Arc` можно клонировать и передавать между потоками, и содержащийся `Mutex` синхронизирует одновременный доступ к значению.

Именно это является одним из самых важных практических различий между:

```text
Arc<T>
```

и:

```text
Arc<Mutex<T>>
```

## Главное из этой главы

После этой главы мы должны понимать не набор исключений, а **модель**, по которой Rust определяет потокобезопасность типов.

### `Send`

```text
T: Send
```

означает:

> значение `T` можно безопасно передать между потоками.

### `Sync`

```text
T: Sync
```

означает:

> shared reference `&T` можно безопасно передать между потоками.

Формально:

```text
T: Sync
    ⇔
&T: Send
```

### `Rc<T>`

```text
Rc<T>: !Send
Rc<T>: !Sync
```

`Rc` использует неатомарный reference counting и предназначен для использования внутри одного потока. ([Rust Documentation][5])

### `Arc<T>`

`Arc` обеспечивает потокобезопасное **совместное владение**, но не делает содержащийся тип автоматически потокобезопасным:

```text
Arc<T>: Send + Sync
```

только при соответствующих свойствах `T`. ([Rust Documentation][1])

### `RefCell<T>`

```text
RefCell<T>: Send     если T: Send
RefCell<T>: !Sync
```

`RefCell` можно переместить в другой поток, но нельзя использовать для безопасного совместного доступа нескольких потоков. ([Rust Documentation][4])

### `Mutex<T>`

```text
Mutex<T>: Send   если T: Send
Mutex<T>: Sync   если T: Send
```

`Mutex` обеспечивает синхронизированный доступ к содержащемуся значению. ([Rust Documentation][2])

### Самая важная идея

`Send` и `Sync` не являются двумя магическими «флагами потокобезопасности».

Они описывают **разные формы взаимодействия с типом**:

```text
             Rust type
                │
       ┌────────┴────────┐
       │                 │
      Send              Sync
       │                 │
       ▼                 ▼
  передать T        поделиться &T
  другому потоку    между потоками
```

А компилятор использует эти свойства как часть системы типов.

Поэтому в Rust многопоточность строится не вокруг правила:

> «Программист должен помнить, какие типы безопасны».

Она строится вокруг другого правила:

> **Тип сам должен выражать, какие способы его использования между потоками безопасны, а компилятор проверяет эти ограничения.**

Именно поэтому `Send` и `Sync` являются фундаментальной частью архитектуры concurrent Rust, а не просто дополнительными трейтовыми ограничениями.
