# Глава 43. Macros как инструмент создания framework

В предыдущих главах мы изучили техническую сторону макросов: как они работают, как их писать и какие библиотеки для этого используются. Теперь пришло время подняться на уровень выше и посмотреть на макросы как на **инструмент проектирования**.

Макросы — это не просто способ избежать дублирования кода. Это мощный инструмент для создания **фреймворков**, **DSL (предметно-ориентированных языков)** и **эргономичных API**. Однако с большой силой приходит и большая ответственность: макросы могут сделать код как удобным, так и нечитаемым.

В этой главе мы разберёмся, как использовать макросы для создания фреймворков, когда это оправдано, а когда лучше выбрать другие инструменты.

Все примеры этой главы используют **Rust Edition 2024**.

---

## 43.1. Что такое DSL?

**DSL (Domain-Specific Language)** — это язык, созданный для решения задач в конкретной предметной области. Макросы в Rust позволяют создавать DSL, которые выглядят как естественное расширение языка.

**Примеры DSL в Rust:**

```rust
// SQL DSL (sqlx): процедурный макрос, проверяет запрос при компиляции
let users = sqlx::query!("SELECT * FROM users WHERE age > ?", 18)
    .fetch_all(&pool)
    .await?;

// HTML DSL (maud): процедурный макрос
html! {
    h1 { "Welcome" }
    p { "Hello, " (name) }
}

// Routing API (axum): обычный builder-API, не макрос
Router::new()
    .route("/users", get(users_handler))
    .route("/users/{id}", get(user_handler))
```

Обратите внимание на различие. `sqlx::query!` и `maud::html!` — это настоящие макро-DSL: у них собственный синтаксис, который разбирает макрос. А `axum` маршрутизирует с помощью обычных вызовов методов: никакого макроса здесь нет, поэтому его маршруты — пример **эргономичного runtime-API**, а не DSL. Мы вернёмся к этому различию в разделе 43.10: именно такой API часто служит основой, поверх которой строится макро-DSL.

> **О синтаксисе параметров пути.** Запись `/users/{id}` соответствует `axum` 0.8. В более ранних версиях (0.7 и ранее) параметр записывался как `/users/:id`; начиная с 0.8 этот синтаксис не поддерживается как запись параметра, и маршруты нужно переписать на `{id}`.

## 43.2. Создание DSL через макросы

Макросы позволяют создавать синтаксис, который выглядит как встроенный язык. Однако важно понимать границу возможностей `macro_rules!`: это **синтаксический DSL**, а не новый язык программирования. Макрос получает токены, сопоставляет их с шаблонами и расширяет их в обычный Rust-код.

Рассмотрим небольшой HTML-подобный DSL. Главное правило при проектировании рекурсивного макроса:

> Каждое правило должно забирать **целую синтаксическую единицу** (тег вместе с телом, литерал, выражение в скобках) и передавать остаток рекурсивному вызову.

```rust
macro_rules! html {
    // Конец ввода
    () => {
        String::new()
    };

    // Тег с телом, затем остальное
    ($tag:ident { $($inner:tt)* } $($rest:tt)*) => {{
        let mut out = format!(
            "<{tag}>{inner}</{tag}>",
            tag = stringify!($tag),
            inner = html!($($inner)*),
        );
        out.push_str(&html!($($rest)*));
        out
    }};

    // Строковый литерал, затем остальное
    ($text:literal $($rest:tt)*) => {{
        let mut out = String::from($text);
        out.push_str(&html!($($rest)*));
        out
    }};

    // Выражение в скобках, затем остальное
    (($value:expr) $($rest:tt)*) => {{
        let mut out = ($value).to_string();
        out.push_str(&html!($($rest)*));
        out
    }};
}

fn main() {
    let name = "Alice";

    let result = html! {
        div {
            h1 { "Hello" }
            p { "Welcome, " (name) "!" }
        }
    };

    println!("{result}");
}
```

Результат:

```text
<div><h1>Hello</h1><p>Welcome, Alice!</p></div>
```

_string%28%29%3B%0A%20%20%20%20%20%20%20%20out.push_str%28%26html%21%28%24%28%24rest%29%2A%29%29%3B%0A%20%20%20%20%20%20%20%20out%0A%20%20%20%20%7D%7D%3B%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20name%20%3D%20%22Alice%22%3B%0A%0A%20%20%20%20let%20result%20%3D%20html%21%20%7B%0A%20%20%20%20%20%20%20%20div%20%7B%0A%20%20%20%20%20%20%20%20%20%20%20%20h1%20%7B%20%22Hello%22%20%7D%0A%20%20%20%20%20%20%20%20%20%20%20%20p%20%7B%20%22Welcome%2C%20%22%20%28name%29%20%22%21%22%20%7D%0A%20%20%20%20%20%20%20%20%7D%0A%20%20%20%20%7D%3B%0A%0A%20%20%20%20println%21%28%22%7Bresult%7D%22%29%3B%0A%7D%0A)

Здесь происходит несколько интересных вещей:

1. `html!` распознаёт конструкцию `tag { ... }` вместе со всем, что идёт после неё (`$rest`).
2. Содержимое блока рекурсивно передаётся обратно в `html!`.
3. Строковый литерал превращается в `String`.
4. Выражение `(name)` вычисляется обычным Rust-кодом; скобки нужны, чтобы отличить выражение от тега или литерала.
5. Результаты соседних элементов объединяются в одну строку: каждое правило добавляет к своему результату результат рекурсивного вызова для остатка.

Важно заметить, что макрос **не создаёт HTML и не работает с DOM**. Он только преобразует DSL в обычные вызовы `format!`.

Это фундаментальная идея DSL-макросов:

> Хороший DSL — это удобный синтаксический слой над обычным API.

### Типичная ошибка: правило, отрывающее один токен

Соблазнительно написать «универсальное» правило, которое обрабатывает вход по одному токену:

```rust
($head:tt $($tail:tt)*) => {
    format!("{}{}", html!($head), html!($($tail)*))
};
```

Для плоских списков оно работает. Но для вложенных тегов оно разрывает пару `тег { тело }`: из `h1 { "Hello" } p { ... }` оно отрывает токен `h1` и вызывает `html!(h1)`, а этот вызов снова попадает в то же правило. Рекурсия не заканчивается, и компилятор отвечает:

```text
error: recursion limit reached while expanding `$crate::__export::format_args!`
```

Полный код с этим правилом:

```rust
macro_rules! html {
    ($tag:ident { $($inner:tt)* }) => {{
        format!(
            "<{tag}>{inner}</{tag}>",
            tag = stringify!($tag),
            inner = html!($($inner)*),
        )
    }};

    ($text:literal) => {
        $text.to_string()
    };

    (($value:expr)) => {
        $value.to_string()
    };

    // «универсальное» правило: отрывает ровно один токен
    ($head:tt $($tail:tt)*) => {
        format!("{}{}", html!($head), html!($($tail)*))
    };

    () => {
        String::new()
    };
}

fn main() {
    let name = "Alice";

    let result = html! {
        div {
            h1 { "Hello" }
            p { "Welcome, " (name) "!" }
        }
    };

    println!("{result}");
}
```

Урок: правило должно соответствовать **единице грамматики**, а не единице токенов. Поэтому в рабочей версии выше теги, литералы и выражения в скобках разбираются отдельными правилами, и каждое из них само передаёт остаток дальше.

## 43.3. API Ergonomics — эргономика API

Макрос особенно полезен там, где он позволяет выразить **структуру данных или конфигурацию непосредственно в синтаксисе вызова**.

Например, представим простой конфигурационный API:

```rust
#[derive(Debug)]
struct Config {
    host: String,
    port: u16,
    logging: bool,
}

macro_rules! config {
    (
        host = $host:expr,
        port = $port:expr,
        logging = $logging:expr $(,)?
    ) => {
        Config {
            host: $host.to_string(),
            port: $port,
            logging: $logging,
        }
    };
}

fn main() {
    let config = config! {
        host = "localhost",
        port = 8080,
        logging = true,
    };

    println!("{config:?}");
}
```

Результат:

```text
Config { host: "localhost", port: 8080, logging: true }
```

Обратите внимание на `$(,)?` в конце правила: он разрешает завершающую запятую. Без него вызов с запятой после последнего поля не сопоставился бы ни с одним правилом.

Без DSL пришлось бы писать более многословный код:

```rust
let config = Config {
    host: "localhost".to_string(),
    port: 8080,
    logging: true,
};
```

В таком простом примере выигрыш невелик. Поэтому сам по себе факт, что макрос делает запись короче, **ещё не является достаточной причиной для его создания**.

Макрос становится действительно интересным, когда DSL начинает описывать структуру, которую обычный Rust API выражает неудобно.

Например:

```rust
routes! {
    GET  "/users"       => list_users,
    POST "/users"       => create_user,
    GET  "/users/{id}"  => get_user,
}
```

Здесь макрос уже может выступать декларативным языком конфигурации framework. Полный рабочий пример такого макроса (для маршрутов без параметров) мы разберём в разделе 43.10.

## 43.4. Compile-time programming — программирование на этапе компиляции

Здесь важно сделать принципиальное уточнение.

`macro_rules!` **не является механизмом вычисления значений во время компиляции**. Его основная задача — преобразование исходного кода:

```text
исходный Rust-код
       ↓
   macro_rules!
       ↓
сгенерированный Rust-код
       ↓
обычная компиляция
```

Например:

```rust
macro_rules! values {
    ($($value:expr),* $(,)?) => {
        vec![$($value),*]
    };
}

fn main() {
    let values = values!(1, 2, 3, 4, 5);

    println!("{values:?}");
}
```

Результат:

```text
[1, 2, 3, 4, 5]
```

Макрос фактически превращает:

```rust
values!(1, 2, 3, 4, 5)
```

в:

```rust
vec![1, 2, 3, 4, 5]
```

А уже `vec!` и остальной Rust-код обрабатываются компилятором.

Поэтому правильнее говорить:

> Макросы позволяют **генерировать Rust-код во время компиляции**, а не просто «выполнять вычисления во время компиляции».

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=macro_rules%21%20values%20%7B%0A%20%20%20%20%28%24%28%24value%3Aexpr%29%2C%2A%20%24%28%2C%29%3F%29%20%3D%3E%20%7B%0A%20%20%20%20%20%20%20%20vec%21%5B%24%28%24value%29%2C%2A%5D%0A%20%20%20%20%7D%3B%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20values%20%3D%20values%21%281%2C%202%2C%203%2C%204%2C%205%29%3B%0A%0A%20%20%20%20println%21%28%22%7Bvalues%3A%3F%7D%22%29%3B%0A%7D%0A)

Для настоящих compile-time вычислений в Rust существуют другие механизмы, в частности `const`, `const fn` и `build.rs`.

Например:

```rust
const fn square(value: u32) -> u32 {
    value * value
}

const RESULT: u32 = square(12);

fn main() {
    println!("{RESULT}");
}
```

Результат:

```text
144
```

Здесь `square(12)` — именно вычисление, которое может быть выполнено компилятором.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=const%20fn%20square%28value%3A%20u32%29%20-%3E%20u32%20%7B%0A%20%20%20%20value%20%2A%20value%0A%7D%0A%0Aconst%20RESULT%3A%20u32%20%3D%20square%2812%29%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20println%21%28%22%7BRESULT%7D%22%29%3B%0A%7D%0A)

Таким образом, не следует смешивать:

- **macros** — преобразуют исходный код;
- **`const` / `const fn`** — вычисляют значения, допустимые в compile-time контексте;
- **`build.rs`** — выполняет отдельную программу во время сборки;
- **procedural macros** — запускают Rust-код для анализа и генерации токенов.

## 43.5. Макросы vs Generics

Макросы и generics решают **разные задачи**, поэтому сравнивать их только по принципу «что мощнее» неправильно.

| Характеристика  | Макросы                              | Generics                               |
| --------------- | ------------------------------------ | -------------------------------------- |
| Уровень работы  | Синтаксис / код                      | Типы и значения                        |
| Проверка типов  | После расширения макроса             | Непосредственно системой типов         |
| Выполнение      | Расширение происходит при компиляции | Код компилируется с конкретными типами |
| Основная задача | Генерация и преобразование кода      | Типобезопасная абстракция              |
| Гибкость        | Очень высокая                        | Ограничена системой типов              |
| Диагностика     | Может быть сложнее                   | Обычно лучше                           |
| Типичные задачи | DSL, derive, кодогенерация           | Полиморфизм, traits, контейнеры        |

Например, если нам нужно сложить два значения, macro здесь обычно не нужен:

```rust
fn add<T>(a: T, b: T) -> T
where
    T: std::ops::Add<Output = T>,
{
    a + b
}
```

Макрос:

```rust
macro_rules! add {
    ($a:expr, $b:expr) => {
        $a + $b
    };
}
```

значительно менее выразителен с точки зрения API. Он не описывает контракт типов — он просто подставляет выражения.

### Практическое правило

Если задачу можно естественно решить с помощью:

1. функции;
2. `trait`;
3. generics;
4. обычной структуры данных;

не следует начинать с макроса.

Макрос становится кандидатом, когда задача требует **манипуляции самим исходным кодом** или создания специального синтаксиса.

## 43.6. Макросы vs Build Scripts

`build.rs` и procedural macros оба могут выполнять Rust-код до основной компиляции, но находятся на разных уровнях.

| Характеристика               | Макросы                      | `build.rs`                        |
| ---------------------------- | ---------------------------- | --------------------------------- |
| Основной объект              | Rust-код программы           | Проект и внешние ресурсы          |
| Вход                         | `TokenStream` / атрибуты     | Файлы, environment, конфигурация  |
| Типичная задача              | Анализ и генерация Rust-кода | Подготовка данных и файлов        |
| Работа с файловой системой   | Обычно не является целью     | Естественная задача               |
| Зависимость от исходного AST | Да, для procedural macros    | Нет                               |
| Типичный результат           | Расширение исходного кода    | Сгенерированные файлы / настройки |

Например, `build.rs` может сгенерировать Rust-код из внешнего файла:

```rust
fn main() {
    println!("cargo::rerun-if-changed=data/schema.txt");

    // Здесь обычно находится код генерации,
    // например чтение schema.txt и создание generated.rs.
}
```

> Запись `cargo::rerun-if-changed=...` (с двумя двоеточиями) поддерживается начиная с Rust 1.77. Старая запись `cargo:rerun-if-changed=...` с одним двоеточием по-прежнему работает, поэтому в проектах с более старым компилятором используйте её.

Затем основной crate может подключить результат:

```rust
include!(concat!(env!("OUT_DIR"), "/generated.rs"));
```

`build.rs` особенно уместен, когда источником данных является **что-то внешнее по отношению к Rust-коду**:

- protobuf;
- OpenAPI;
- SQL schema;
- файлы конфигурации;
- данные, доступные во время сборки;
- информация о целевой платформе.

Если же нужно посмотреть на:

```rust
struct User {
    id: u64,
    name: String,
}
```

и автоматически создать:

```rust
impl User {
    fn id(&self) -> &u64 { ... }
    fn name(&self) -> &String { ... }
}
```

то procedural derive macro подходит гораздо лучше.

## 43.7. Когда макрос оправдан

Использование макроса оправдано, если он решает задачу, которую обычные средства Rust выражают существенно хуже.

### Хорошие кандидаты

1. **Генерация повторяющегося кода**

   Например, реализация одного trait для большого количества структур.

2. **Создание декларативного DSL**

   Например:

   ```rust
   routes! {
       GET "/users" => list_users,
       POST "/users" => create_user,
   }
   ```

3. **Анализ структуры Rust-кода**

   Например:

   ```rust
   #[derive(Builder)]
   struct ServerConfig {
       host: String,
       port: u16,
   }
   ```

4. **Compile-time validation**

   Например, проверка специального DSL или SQL-подобного синтаксиса.

5. **Генерация большого количества однотипного кода**

   Особенно когда ручная реализация легко приводит к ошибкам.

6. **Интеграция с framework**

   Framework может использовать макрос как декларативный front-end над обычным runtime API.

### Важный критерий

Спросите себя:

> **Станет ли пользователь моего framework писать код существенно проще благодаря макросу?**

Если ответ «нет», макрос, скорее всего, не нужен.

---

## 43.8. Когда макрос делает API хуже

Макрос может сделать API хуже даже тогда, когда технически он работает.

Особенно опасны следующие ситуации.

### 1. Макрос скрывает обычный вызов функции

Плохо:

```rust
do_something!(value);
```

если внутри всего лишь:

```rust
do_something(value);
```

В таком случае макрос добавляет магию без пользы.

### 2. Макрос имеет слишком много неявных правил

Например:

```rust
framework! {
    magic_option = true,
    auto_register,
    optimize,
    ...
}
```

Если пользователь не может легко понять, какой код будет сгенерирован, API становится труднее изучать.

### 3. Ошибка возникает далеко от причины

Пользователь пишет:

```rust
#[derive(MyFramework)]
struct User {
    ...
}
```

а получает ошибку компилятора внутри сгенерированного `impl`.

Хороший procedural macro должен преобразовывать такую ситуацию в ошибку, указывающую на исходную структуру или конкретное поле.

### 4. Макрос невозможно нормально использовать без знания его реализации

Хороший framework должен позволять пользователю изучить **контракт** макроса, а не его внутреннюю реализацию.

### 5. Макрос становится мини-языком без необходимости

Если DSL уже настолько сложен, что требует собственной документации, грамматики и большого количества специальных правил, нужно задуматься, не лучше ли сделать обычный API или отдельный генератор.

### 6. Макрос вычисляет аргументы не так, как ожидает пользователь

Параметр `$x:expr` — это не вычисленное значение, а подставляемый **фрагмент синтаксиса**. Если макрос подставит его в расширение дважды, выражение выполнится дважды. Для функции такое невозможно: аргумент всегда вычисляется один раз. Подробный пример — в разделе 43.9.

## 43.9. Макросы vs функции

Если задача заключается в выполнении действия над значениями, функция обычно предпочтительнее.

Например:

```rust
fn max<T: Ord>(a: T, b: T) -> T {
    if a > b {
        a
    } else {
        b
    }
}
```

Макрос:

```rust
macro_rules! max_value {
    ($a:expr, $b:expr) => {
        if $a > $b { $a } else { $b }
    };
}
```

здесь не просто не даёт преимущества, он ещё и **ведёт себя хуже**. Метапеременные `$a` и `$b` подставляются в расширение по два раза, поэтому аргумент с побочным эффектом выполнится дважды. Исправляется это сохранением значений в локальные переменные, но тогда макрос превращается в то, что и так делает функция:

```rust
macro_rules! max_value {
    ($a:expr, $b:expr) => {
        if $a > $b { $a } else { $b }
    };
}

macro_rules! max_once {
    ($a:expr, $b:expr) => {{
        let a = $a;
        let b = $b;
        if a > b { a } else { b }
    }};
}

fn main() {
    let mut calls = 0;
    let mut next = || {
        calls += 1;
        10
    };
    let m = max_value!(next(), 5);
    println!("max_value: m = {m}, вызовов = {calls}");

    let mut calls = 0;
    let mut next = || {
        calls += 1;
        10
    };
    let m = max_once!(next(), 5);
    println!("max_once:  m = {m}, вызовов = {calls}");
}
```

Результат:

```text
max_value: m = 10, вызовов = 2
max_once:  m = 10, вызовов = 1
```

Однако макрос может работать с тем, чего функция не видит как синтаксис.

Например:

```rust
routes! {
    GET  "/users" => list_users,
    POST "/users" => create_user,
}
```

Функция не может получить эту запись в таком виде. Макрос может разобрать её и превратить в обычные вызовы API.

### Простое правило

> **Функция работает с данными. Макрос может работать с кодом, из которого эти данные и конструкции создаются.**

Это одно из наиболее полезных правил при проектировании Rust API.

## 43.10. Проектирование макросов для framework

Когда макрос становится частью framework, его нельзя проектировать как изолированный кусок метапрограммирования. Необходимо проектировать **границу между macro layer и runtime layer**.

Хорошая архитектура обычно выглядит так:

```text
                Пользователь framework
                         │
                         ▼
                ┌─────────────────┐
                │      Macro      │
                │      Layer      │
                └────────┬────────┘
                         │
                  генерирует код
                         │
                         ▼
                ┌─────────────────┐
                │    Runtime API  │
                │ functions/traits│
                └────────┬────────┘
                         │
                         ▼
                    application
```

Например:

```rust
#[derive(Handler)]
struct UserHandler;
```

может сгенерировать реализацию:

```rust
impl Handler for UserHandler {
    // ...
}
```

Но сама runtime-логика должна находиться в обычном Rust-коде framework, а не внутри macro implementation.

### Рабочий пример: два слоя

Построим мини-фреймворк маршрутизации. Runtime layer — обычные типы и методы; macro layer — только синтаксис, который превращается в вызовы runtime-API:

```rust
// ---- runtime layer: обычный Rust, без макросов ----
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Method {
    Get,
    Post,
}

type Handler = fn() -> String;

#[derive(Default)]
pub struct Router {
    routes: Vec<(Method, &'static str, Handler)>,
}

impl Router {
    pub fn new() -> Self {
        Self::default()
    }

    pub fn add(mut self, method: Method, path: &'static str, handler: Handler) -> Self {
        self.routes.push((method, path, handler));
        self
    }

    pub fn dispatch(&self, method: Method, path: &str) -> Option<String> {
        self.routes
            .iter()
            .find(|(m, p, _)| *m == method && *p == path)
            .map(|(_, _, handler)| handler())
    }
}

// ---- macro layer: только синтаксис, вся логика осталась в Router ----
macro_rules! method {
    (GET) => {
        $crate::Method::Get
    };
    (POST) => {
        $crate::Method::Post
    };
}

macro_rules! routes {
    ( $( $method:ident $path:literal => $handler:path ),* $(,)? ) => {
        $crate::Router::new()
            $( .add(method!($method), $path, $handler) )*
    };
}

fn list_users() -> String {
    String::from("список пользователей")
}

fn create_user() -> String {
    String::from("пользователь создан")
}

fn main() {
    let router = routes! {
        GET  "/users" => list_users,
        POST "/users" => create_user,
    };

    println!("{:?}", router.dispatch(Method::Get, "/users"));
    println!("{:?}", router.dispatch(Method::Post, "/users"));
    println!("{:?}", router.dispatch(Method::Get, "/nope"));
}
```

Результат:

```text
Some("список пользователей")
Some("пользователь создан")
None
```

Тот же код без макроса выглядит так:

```rust
let router = Router::new()
    .add(Method::Get, "/users", list_users)
    .add(Method::Post, "/users", create_user);
```

Это показывает, что DSL — лишь сокращение: если макрос мешает отладке, пользователь всегда может перейти на явный API.

**Проверка на этапе компиляции.** Макрос `method!` знает только `GET` и `POST`. Если написать `PATCH "/users" => list_users`, получится ошибка:

```text
error: no rules expected the token `PATCH`
```

Опечатка в имени HTTP-метода ловится до запуска программы, а сообщение указывает на вызов макроса. Это сильная сторона декларативных DSL: список допустимых форм задан самими правилами.

Обратите внимание на два приёма:

- Пути к собственным элементам записаны через `$crate`: `$crate::Router::new()`, `$crate::Method::Get`. Благодаря этому макрос работает и при вызове из другого crate.
- `method!($method)` вызывается **внутри** `routes!` для каждого маршрута. Маленький макрос, который выбирает вариант `enum`, лучше большого макроса, который делает всё сам.

### Принципы хорошего framework-макроса

1. **Макрос должен иметь чёткий контракт.**

2. **Сложную runtime-логику следует оставлять обычному Rust-коду.**

3. **Макрос должен генерировать минимально необходимый код.**

4. **Ошибки должны указывать на исходный пользовательский код.**

5. **Синтаксис макроса должен быть стабильнее его внутренней реализации.**

6. **Сгенерированный код должен использовать публичный runtime API framework.**

## 🔨 Эксперименты с компилятором

### Эксперимент 1: Макрос с плохой диагностикой

```rust
macro_rules! bad_macro {
    ($x:expr) => {
        $x +
    };
}

fn main() {
    let v = bad_macro!(1);
    println!("{v}");
}
```

[▶ Открыть пример с ошибкой в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=macro_rules%21%20bad_macro%20%7B%0A%20%20%20%20%28%24x%3Aexpr%29%20%3D%3E%20%7B%0A%20%20%20%20%20%20%20%20%24x%20%2B%0A%20%20%20%20%7D%3B%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20v%20%3D%20bad_macro%21%281%29%3B%0A%20%20%20%20println%21%28%22%7Bv%7D%22%29%3B%0A%7D%0A)

Компилятор сообщит:

```text
error: macro expansion ends with an incomplete expression: expected expression
 --> src/main.rs:3:13
  |
3 |         $x +
  |             ^ expected expression
```

Само определение `bad_macro!` ошибки не вызывает: `macro_rules!` не проверяет тело макроса до расширения. Ошибка появляется только в момент вызова, когда подставленный код оказывается некорректным. Поэтому каждое правило макроса нужно покрывать хотя бы одним вызовом.

Обратите внимание, что в сообщении нет ничего о самом макросе, кроме позиции в его определении. Именно так выглядит «плохая диагностика»: пользователь видит ошибку внутри чужого кода и не знает, какой из его аргументов к ней привёл.

### Эксперимент 2: Макрос, который сложно отлаживать

Классический рекурсивный счётчик токенов:

```rust
macro_rules! count {
    () => { 0usize };
    ($head:tt $($tail:tt)*) => { 1usize + count!($($tail)*) };
}
```

С пятью токенами он работает. Вызовите его теперь со 130 токенами: `count!(x x x ... x)`. Компилятор остановит расширение:

```text
error: recursion limit reached while expanding `count!`
```

Каждый рекурсивный вызов расходует лимит глубины, по умолчанию 128. Есть два пути.

**Путь 1: поднять лимит.** В корне crate добавьте `#![recursion_limit = "256"]`. С этим атрибутом тот же вызов возвращает `130`. Но лимит лишь отодвигает проблему, а каждый уровень рекурсии замедляет компиляцию.

**Путь 2: не использовать рекурсию.** Превратите каждый токен в элемент массива и посчитайте его длину:

```rust
macro_rules! replace_expr {
    ($_t:tt $sub:expr) => {
        $sub
    };
}

macro_rules! count {
    ($($x:tt)*) => {
        <[()]>::len(&[$(replace_expr!($x ())),*])
    };
}

fn main() {
    let n = count!(a b c d e);
    println!("{n}");
}
```

Результат: `5`. Со 130 токенами то же определение возвращает `130` без изменения лимита.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=macro_rules%21%20replace_expr%20%7B%0A%20%20%20%20%28%24_t%3Att%20%24sub%3Aexpr%29%20%3D%3E%20%7B%0A%20%20%20%20%20%20%20%20%24sub%0A%20%20%20%20%7D%3B%0A%7D%0A%0Amacro_rules%21%20count%20%7B%0A%20%20%20%20%28%24%28%24x%3Att%29%2A%29%20%3D%3E%20%7B%0A%20%20%20%20%20%20%20%20%3C%5B%28%29%5D%3E%3A%3Alen%28%26%5B%24%28replace_expr%21%28%24x%20%28%29%29%29%2C%2A%5D%29%0A%20%20%20%20%7D%3B%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20n%20%3D%20count%21%28a%20b%20c%20d%20e%29%3B%0A%20%20%20%20println%21%28%22%7Bn%7D%22%29%3B%0A%7D%0A)

Для отладки подобных ошибок используйте `cargo expand`: он показывает код после раскрытия макросов.

## Главное из этой главы

После этой главы мы понимаем:

- **DSL** — создание предметно-ориентированных языков через макросы; не любой удобный API — DSL: `axum` использует обычный builder-API, а не макрос.
- **Рекурсивные правила** должны забирать целую синтаксическую единицу, а не один токен, иначе рекурсия расходится и компилятор останавливает её по лимиту.
- **API эргономика** — макросы делают API удобнее, но сама по себе краткость записи — недостаточная причина писать макрос.
- **Compile-time programming** — макросы генерируют код на этапе компиляции, а вычисляют значения `const fn`.
- **Макросы vs Generics** — разные инструменты для разных задач.
- **Макросы vs Build Scripts** — что где использовать.
- **Макросы vs функции** — `$x:expr` подставляется как фрагмент синтаксиса и может вычисляться несколько раз.
- **Когда макрос оправдан** — устранение дублирования, DSL, эргономика.
- **Когда макрос делает API хуже** — излишняя сложность, плохая диагностика, неочевидное вычисление аргументов.
- **Два слоя** — макрос отвечает за синтаксис, а логика живёт в обычном runtime-API.

**Самая важная идея:**

> Макросы — это мощный инструмент для создания фреймворков и улучшения эргономики API. Но с большой силой приходит большая ответственность. Макросы должны быть хорошо спроектированы, документированы и тестированы. Используйте их, когда польза очевидна, и избегайте, когда можно обойтись более простыми средствами. Хороший макрос — это макрос, который делает код проще, а не сложнее.
