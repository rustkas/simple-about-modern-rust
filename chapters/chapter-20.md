## 20.1. Три области памяти

В программе на Rust данные могут находиться в трёх разных областях памяти:

| Область                                | Описание                                                           | Примеры                                               |
| -------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------- |
| **Stack (Стек)**                       | Быстрая, ограниченная память с автоматическим управлением          | Локальные переменные, параметры функций               |
| **Heap (Куча)**                        | Большая, динамическая память с ручным управлением (через владение) | `String`, `Vec<T>`, `Box<T>`                          |
| **Static memory (Статическая память)** | Память, существующая всё время работы программы                    | Строковые литералы, константы, статические переменные |

---

## 20.2. Stack: быстрая память с дисциплиной

Стек — это область памяти, которая работает по принципу **LIFO** (Last In, First Out). Как стопка тарелок: последняя положенная тарелка снимается первой.

```rust
fn main() {
    let x = 5;      // 1. Создаётся на стеке
    let y = 10;     // 2. Создаётся на стеке
    let z = x + y;  // 3. Создаётся на стеке
} // 4. Все переменные удаляются со стека (в обратном порядке)
```

**Характеристики стека:**

| Характеристика  | Описание                                                 |
| --------------- | -------------------------------------------------------- |
| **Скорость**    | Очень быстрый (простое перемещение указателя)            |
| **Размер**      | Фиксированный (обычно 1–8 МБ)                            |
| **Управление**  | Автоматическое (при входе/выходе из функции)             |
| **Размещение**  | Только значения с известным размером на этапе компиляции |
| **Время жизни** | Ограничено областью видимости                            |

**Что хранится на стеке:**

- Локальные переменные простых типов (`i32`, `bool`, `char`)
- Ссылки (`&T`, `&mut T`)
- Кортежи и массивы фиксированного размера
- Значения, которые реализуют `Copy`

---

## 20.3. Heap: гибкая, но медленная память

Куча — это большая область памяти, где данные могут жить произвольное время. Управление кучей в Rust осуществляется через **владение**.

```rust
fn main() {
    let s = String::from("hello");
    //             └─────────────┘
    //               Данные в куче

    let v = vec![1, 2, 3];
    //          └────────┘
    //            Данные в куче
}
```

**Характеристики кучи:**

| Характеристика  | Описание                                             |
| --------------- | ---------------------------------------------------- |
| **Скорость**    | Медленнее стека (запрос памяти, указатели)           |
| **Размер**      | Ограничен только доступной памятью ОС                |
| **Управление**  | Автоматическое через владение (вызов `drop`)         |
| **Размещение**  | Любые типы, включая динамические                     |
| **Время жизни** | До вызова `drop` (конец области видимости владельца) |

**Что хранится в куче:**

- `String` — данные строки
- `Vec<T>` — элементы вектора
- `Box<T>` — данные, помещённые в кучу
- Все динамические структуры данных

---

## 20.4. Static memory: вечная память

Статическая память существует всё время работы программы. Она не выделяется и не освобождается во время выполнения.

```rust
fn main() {
    let s: &'static str = "Hello, world!";
    //                   └──────────────┘
    //                     Статическая память

    const MAX_SIZE: usize = 1024;
    //                  └────────────┘
    //                    Статическая память
}
```

**Что хранится в статической памяти:**

- Строковые литералы (`"hello"`)
- Константы (`const`)
- Статические переменные (`static`)
- Данные с временем жизни `'static`

## 20.5. Размер типа: `size_of`

В Rust размер каждого типа известен на этапе компиляции (кроме DST). Узнать размер можно с помощью `std::mem::size_of`:

```rust
use std::mem;

fn main() {
    println!("i8: {} байт", mem::size_of::<i8>());
    println!("i32: {} байт", mem::size_of::<i32>());
    println!("i64: {} байт", mem::size_of::<i64>());
    println!("bool: {} байт", mem::size_of::<bool>());
    println!("char: {} байт", mem::size_of::<char>());
    println!("() : {} байт", mem::size_of::<()>());

    let x = 42;
    println!("x: {} байт", mem::size_of_val(&x));
}
```

**Размеры типов:**

- `i8`: 1 байт
- `i32`: 4 байта
- `i64`: 8 байт
- `bool`: 1 байт
- `char`: 4 байта (Unicode scalar)
- `()`: 0 байт

## 20.6. Выравнивание: `align_of`

Кроме размера, у каждого типа есть **выравнивание (alignment)**. Это адрес в памяти, по которому тип должен быть расположен.

```rust
use std::mem;

fn main() {
    println!("i8:  размер {} байт, выравнивание {} байт",
        mem::size_of::<i8>(), mem::align_of::<i8>());
    println!("i32: размер {} байт, выравнивание {} байт",
        mem::size_of::<i32>(), mem::align_of::<i32>());
    println!("i64: размер {} байт, выравнивание {} байт",
        mem::size_of::<i64>(), mem::align_of::<i64>());
}
```

**Выравнивание:**

- `i8`: 1 байт

Выравнивание нужно для эффективного доступа к памяти. Процессор читает данные быстрее, если они расположены по адресу, кратному их размеру.

## 20.7. Структуры и выравнивание

Компилятор может добавлять **прокладки (padding)** между полями структур для правильного выравнивания:

```rust
#![allow(dead_code)]

use std::mem;

struct A {
    a: i8,
    b: i64,
}

struct B {
    b: i64,
    a: i8,
}

fn main() {
    println!("A: {} байт", mem::size_of::<A>());
    println!("B: {} байт", mem::size_of::<B>());
}
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=%23%21%5Ballow%28dead_code%29%5D%0A%0Ause+std%3A%3Amem%3B%0A%0Astruct+A+%7B%0A++++a%3A+i8%2C%0A++++b%3A+i64%2C%0A%7D%0A%0Astruct+B+%7B%0A++++b%3A+i64%2C%0A++++a%3A+i8%2C%0A%7D%0A%0Afn+main%28%29+%7B%0A++++println%21%28%22A%3A+%7B%7D+%D0%B1%D0%B0%D0%B9%D1%82%22%2C+mem%3A%3Asize_of%3A%3A%3CA%3E%28%29%29%3B%0A++++println%21%28%22B%3A+%7B%7D+%D0%B1%D0%B0%D0%B9%D1%82%22%2C+mem%3A%3Asize_of%3A%3A%3CB%3E%28%29%29%3B%0A%7D)

**Результат:**

```
A: 16 байт  (1 + 7 байт прокладки + 8)
B: 16 байт  (8 + 1 + 7 байт прокладки)
```

Обратите внимание: оба варианта дают одинаковый, уже минимальный размер — 16 байт (8 байт под `i64` плюс 1 байт под `i8` плюс 7 байт прокладки для выравнивания структуры целиком по границе 8). Это не совпадение.

**Важная особенность Rust:** структуры без явного `#[repr(...)]` используют так называемое **представление по умолчанию** (`repr(Rust)`), которое **не гарантирует**, что поля будут расположены в памяти в том же порядке, в каком вы их объявили в коде. Компилятор явно оставляет за собой право **самостоятельно переставлять поля**, чтобы минимизировать паддинг — независимо от того, в каком порядке они написаны в исходнике. Именно поэтому `A` и `B` выше дают одинаковый результат: как бы вы ни расположили `a: i8` и `b: i64` в объявлении, компилятор фактически уложит их в памяти оптимальным образом сам.

**Это отличает Rust от C, C++ и Go**, где порядок полей в объявлении действительно определяет физический layout, и программисту приходится вручную сортировать поля по убыванию размера, чтобы получить минимальный размер структуры. В Rust эта оптимизация происходит автоматически и бесплатно для любой обычной структуры.

Ручной контроль над порядком полей всё же нужен — но не для оптимизации, а в случаях, когда важен **предсказуемый, стабильный layout**: например, при взаимодействии с C через FFI. Для этого существует атрибут `#[repr(C)]`, который **отключает** автоматическую перестановку полей и укладывает их строго в порядке объявления (с паддингом между ними по тем же правилам выравнивания):

```rust
use std::mem;

#[repr(C)]
struct BadOrder {
    a: bool,
    b: i64,
    c: bool,
}

#[repr(C)]
struct GoodOrder {
    b: i64,
    a: bool,
    c: bool,
}

fn main() {
    println!("BadOrder (repr(C)):  {} байт", mem::size_of::<BadOrder>());
    println!("GoodOrder (repr(C)): {} байт", mem::size_of::<GoodOrder>());
}
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Amem%3B%0A%0A%23%5Brepr%28C%29%5D%0Astruct%20BadOrder%20%7B%0A%20%20%20%20a%3A%20bool%2C%0A%20%20%20%20b%3A%20i64%2C%0A%20%20%20%20c%3A%20bool%2C%0A%7D%0A%0A%23%5Brepr%28C%29%5D%0Astruct%20GoodOrder%20%7B%0A%20%20%20%20b%3A%20i64%2C%0A%20%20%20%20a%3A%20bool%2C%0A%20%20%20%20c%3A%20bool%2C%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20println%21%28%22BadOrder%20%28repr%28C%29%29%3A%20%20%7B%7D%20%D0%B1%D0%B0%D0%B9%D1%82%22%2C%20mem%3A%3Asize_of%3A%3A%3CBadOrder%3E%28%29%29%3B%0A%20%20%20%20println%21%28%22GoodOrder%20%28repr%28C%29%29%3A%20%7B%7D%20%D0%B1%D0%B0%D0%B9%D1%82%22%2C%20mem%3A%3Asize_of%3A%3A%3CGoodOrder%3E%28%29%29%3B%0A%7D)

**Результат:**

```
BadOrder (repr(C)):  24 байта
GoodOrder (repr(C)): 16 байт
```

Вот здесь порядок полей уже реально важен — именно потому что `#[repr(C)]` запрещает компилятору переставлять их. `BadOrder` кладёт `i64` между двумя `bool`, и каждый `bool` требует собственного паддинга до границы 8 байт (1 + 7 прокладки + 8 + 1 + 7 прокладки = 24), а `GoodOrder` ставит `i64` первым, и оба `bool` компактно укладываются друг за другом после него (8 + 1 + 1 + 6 прокладки в конце = 16).

**Порядок полей в структуре** влияет на её размер **только** при явном `#[repr(C)]` или `#[repr(packed)]` — для обычных структур без атрибутов `repr` компилятор уже переставляет поля автоматически. Для обычных структур без атрибутов `#[repr(...)]` заботиться о порядке полей не нужно — Rust уже делает это за вас.

## 20.8. `Sized`: типы с известным размером

Большинство типов в Rust имеют размер, известный на этапе компиляции. Они реализуют трейт `Sized`.

```rust
use std::mem;

fn main() {
    // Sized типы
    let x: i32 = 42;        // размер известен: 4 байта
    let y: [u8; 4] = [0; 4]; // размер известен: 4 байта

    // !Sized типы (DST)
    // let s: str = "hello"; // ❌ Ошибка! str не имеет известного размера
    let s: &str = "hello";   // ✅ Ссылка на str имеет известный размер
}
```

**DST (Dynamically Sized Types):**

- `str` — строковый срез
- `[T]` — срез
- `dyn Trait` — трейт-объект

**Правило:** Все параметры обобщённых типов по умолчанию являются `Sized`. Если нужно разрешить DST, используйте `?Sized`.

```rust
fn generic<T: ?Sized>(t: &T) {
    // T может быть Sized или не Sized
}
```

## 20.9. `Box<T>`: данные в куче

`Box<T>` — умный указатель, который помещает данные в кучу.

```rust
fn main() {
    let x = 42;           // на стеке
    let y = Box::new(42); // в куче

    println!("x: {} (стек)", x);
    println!("y: {} (куча)", y);
}
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=fn%20main%28%29%20%7B%0A%20%20%20%20let%20x%20%3D%2042%3B%0A%20%20%20%20let%20y%20%3D%20Box%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20println%21%28%22x%3A%20%7B%7D%20%28%D1%81%D1%82%D0%B5%D0%BA%29%22%2C%20x%29%3B%0A%20%20%20%20println%21%28%22y%3A%20%7B%7D%20%28%D0%BA%D1%83%D1%87%D0%B0%29%22%2C%20y%29%3B%0A%7D)

**Когда использовать `Box<T>`:**

1. Когда тип не имеет известного размера на этапе компиляции (DST).
2. Когда нужны рекурсивные структуры данных (связные списки).
3. Когда нужно передать владение, но размер данных велик.

**Важно:** сам `Box<T>` имеет фиксированный размер (обычно 8 байт на 64-битных системах) — это указатель.

**Пример: рекурсивная структура**

```rust
use std::mem;

enum List {
    Cons(i32, Box<List>),
    Nil,
}

impl List {
    fn new() -> Self {
        List::Nil
    }

    fn prepend(self, value: i32) -> Self {
        List::Cons(value, Box::new(self))
    }
}

fn main() {
    let list = List::new()
        .prepend(1)
        .prepend(2)
        .prepend(3);

    // Используем список, чтобы избежать предупреждения
    println!("List: {} байт", mem::size_of::<List>());

    // Выводим содержимое списка
    print_list(&list);
}

    match list {
        List::Cons(value, next) => {
            print!("{} ", value);
            print_list(next);
        }
        List::Nil => {
            println!();
        }
    }
}
```

## 20.10. Почему Rust не использует garbage collector

Rust управляет памятью без сборщика мусора (GC). Это одно из ключевых отличий от языков вроде Java, Go или C#.

| Характеристика         | Rust (ownership)                       | GC (сборщик мусора)                |
| ---------------------- | -------------------------------------- | ---------------------------------- |
| **Время освобождения** | Определённое (конец области видимости) | Неопределённое (при следующем GC)  |
| **Накладные расходы**  | Минимальные (только `drop` вызовы)     | Накладные расходы на сборку мусора |
| **Паузы**              | Нет (предсказуемая производительность) | Паузы при сборке мусора            |
| **Управление**         | На уровне языка (владение)             | Внешняя библиотека (runtime)       |
| **Безопасность**       | Проверяется компилятором               | Runtime проверка                   |

**Rust гарантирует:**

- Освобождение памяти происходит в известный момент.
- Нет пауз, связанных со сборкой мусора.
- Память никогда не утекает (если нет циклических ссылок с `Rc`).

---

## 20.11. Что Rust гарантирует на уровне памяти

**Rust гарантирует:**

1. **No memory leaks** — память освобождается, когда владелец выходит из области видимости.
2. **No double-free** — каждое значение освобождается ровно один раз.
3. **No use-after-free** — нельзя использовать память после освобождения.
4. **No null pointer dereference** — нет `null` (вместо этого `Option`).
5. **No data races** — нельзя одновременно изменять и читать одни и те же данные из разных потоков.

**Что Rust не гарантирует:**

1. **Порядок полей в памяти** — конкретный layout может меняться.
2. **Размер типов** — может отличаться на разных платформах.
3. **Производительность** — Rust даёт инструменты, но как их использовать — зависит от программиста.
4. **Отсутствие паники** — программа может завершиться с `panic!`.

## Главное из этой главы

После этой главы мы понимаем:

- **Три области памяти:** стек, куча, статическая память.
- **Стек** — быстрый, но ограниченный. Используется для простых типов и ссылок.
- **Куча** — медленная, но большая. Используется для динамических данных (`String`, `Vec`, `Box`).
- **Статическая память** — существует всё время работы программы.
- **`size_of`** — размер типа в байтах.
- **`align_of`** — выравнивание типа.
- **Порядок полей в структуре** влияет на её размер.
- **`Sized`** — трейт для типов с известным размером.
- **`Box<T>`** — данные в куче (фиксированный размер).
- **Rust не использует GC** — управление памятью через владение.

**Самая важная идея:**

> Понимание того, где и как хранятся данные, помогает писать эффективный код и понимать, почему Rust устроен именно так. Стек — для быстрых, короткоживущих данных. Куча — для больших, долгоживущих данных. Владение — это механизм, который делает управление памятью в куче безопасным и предсказуемым.

## Дополнение к главе

Выравнивание (alignment) — это одна из тех тем, которые часто упускают из виду, но она критически важна для понимания производительности и совместимости программ на Rust. Давайте разберёмся.

---

### Что такое выравнивание и зачем оно нужно?

**Выравнивание** — это требование к адресу в памяти, по которому может быть расположен объект определённого типа. Адрес должен быть кратен размеру типа (или его выравниванию).

**Пример:** Для типа `i32` (4 байта) адрес должен быть кратен 4 (например, 0x1000, 0x1004, 0x1008). Для `i64` (8 байт) адрес должен быть кратен 8.

**Почему это нужно?**

1. **Производительность:** Процессоры читают память блоками (cache lines). Если данные выровнены правильно, процессор может прочитать их за одну операцию. Если нет — потребуется несколько операций.

2. **Аппаратные требования:** Некоторые архитектуры (например, ARM) вообще не позволяют читать невыровненные данные — программа вызовет ошибку.

3. **Атомарность:** Определённые атомарные операции требуют выровненных данных.

---

### Важная особенность: Rust по умолчанию сам оптимизирует порядок полей

Прежде чем смотреть на примеры, нужно прояснить один принципиальный момент, без которого дальнейшая демонстрация не будет иметь смысла.

Обычная структура в Rust — без каких-либо атрибутов `#[repr(...)]` — использует так называемое **представление по умолчанию** (`repr(Rust)`). Это представление **намеренно не гарантирует**, что поля будут расположены в памяти в том порядке, в каком вы их написали в коде. Компилятор явно оставляет за собой право **самостоятельно переставлять поля**, чтобы минимизировать паддинг.

Это значит: если взять две структуры с одинаковым набором полей, но в разном порядке объявления, **без `#[repr(C)]` они, скорее всего, скомпилируются в один и тот же, уже минимальный размер** — компилятор всё равно уложит поля оптимально, независимо от того, как вы их написали.

Чтобы реально увидеть разницу от порядка полей — то есть чтобы продемонстрировать, зачем вообще нужен ручной подбор порядка, — нужно **отключить** эту автоматическую оптимизацию явным атрибутом `#[repr(C)]`. Именно так мы и поступим ниже.

---

### Покажем разницу на реальном примере

Вот пример, который демонстрирует, как порядок полей в структуре влияет на её размер из-за выравнивания — **при условии, что мы явно отключили автоматическую перестановку полей через `#[repr(C)]`**:

```rust
#![allow(dead_code)]
#![allow(unused_variables)]

use std::mem;

// Неоптимальный порядок: bool (1) + u32 (4) + bool (1) + u64 (8) + bool (1)
// #[repr(C)] обязателен: без него компилятор всё равно
// переставил бы поля сам и разницы с Optimized не было бы видно.
#[repr(C)]
#[derive(Debug)]
struct Unoptimized {
    a: bool,
    b: u32,
    c: bool,
    d: u64,
    e: bool,
}

// Оптимальный порядок: от большего к меньшему
#[repr(C)]
#[derive(Debug)]
struct Optimized {
    d: u64,
    b: u32,
    a: bool,
    c: bool,
    e: bool,
}

// Использование битовых флагов вместо трёх отдельных bool
#[repr(C)]
#[derive(Debug)]
struct PackedBools {
    d: u64,
    b: u32,
    flags: u8,
    _padding: [u8; 3],
}

// Полностью упакованная структура: без выравнивания вообще
#[repr(packed)]
#[derive(Debug)]
struct Packed {
    a: bool,
    b: u32,
    c: bool,
    d: u64,
    e: bool,
}

fn main() {
    let unopt = Unoptimized { a: true, b: 42, c: false, d: 100, e: true };
    let opt = Optimized { d: 100, b: 42, a: true, c: false, e: true };
    let packed_bools = PackedBools {
        d: 100,
        b: 42,
        flags: 0b00000101, // a=true, c=false, e=true
        _padding: [0, 0, 0],
    };
    let packed = Packed { a: true, b: 42, c: false, d: 100, e: true };

   println!("=== Размеры структур ===");
    println!("Unoptimized: {} байт", mem::size_of::<Unoptimized>());
    println!("Optimized:   {} байт", mem::size_of::<Optimized>());
    println!("PackedBools: {} байт", mem::size_of::<PackedBools>());
    println!("Packed:      {} байт", mem::size_of::<Packed>());
    println!();

    let count = 1_000_000;
    let unopt_size = mem::size_of::<Unoptimized>() * count;
    let opt_size = mem::size_of::<Optimized>() * count;
    let packed_bools_size = mem::size_of::<PackedBools>() * count;
    let packed_size = mem::size_of::<Packed>() * count;

    println!("=== Практическая разница для {} экземпляров ===", count);
    println!("Unoptimized: {} МБ", unopt_size / 1_000_000);
    println!("Optimized:   {} МБ", opt_size / 1_000_000);
    println!("PackedBools: {} МБ", packed_bools_size / 1_000_000);
    println!("Packed:      {} МБ", packed_size / 1_000_000);
    println!();

    println!("=== Экономия памяти относительно Unoptimized ===");
    println!(
        "Optimized:   {} МБ ({}%)",
        (unopt_size - opt_size) / 1_000_000,
        ((unopt_size - opt_size) * 100) / unopt_size
    );
    println!(
        "PackedBools: {} МБ ({}%)",
        (unopt_size - packed_bools_size) / 1_000_000,
        ((unopt_size - packed_bools_size) * 100) / unopt_size
    );
    println!(
        "Packed:      {} МБ ({}%)",
        (unopt_size - packed_size) / 1_000_000,
        ((unopt_size - packed_size) * 100) / unopt_size
    );
    println!();

    println!("=== Работа с битовыми флагами ===");
    let mut flags = packed_bools.flags;
    println!("Исходные флаги: {:#b}", flags);
    flags |= 0b00000010;
    println!("Установили c:   {:#b}", flags);
    flags &= !0b00000001;
    println!("Сбросили a:     {:#b}", flags);
    let has_e = (flags & 0b00000100) != 0;
    println!("e = {}", has_e);
}
```

### Что мы видим?

1. **Реальная разница (при `#[repr(C)]`):** 32 байта против 16 байт — экономия 50%.
2. **Почему так происходит:**
   - `Unoptimized`: поля идут в порядке `bool, u32, bool, u64, bool`. `u64` требует выравнивания по 8 байтам, а перед ним в этом порядке оказывается `bool` — поэтому компилятор вставляет 7 байт прокладки перед `u64`, и ещё 7 байт в конце структуры, чтобы её общий размер стал кратен 8. Итог: 1 + 3(до b) + 4 + 1 + 7(до d) + 8 + 1 + 7(хвост) = 32.
   - `Optimized`: сначала `u64` (не требует прокладки — структура и так начинается с адреса 0), затем `u32`, затем три `bool` подряд без зазоров между ними. Итог: 8 + 4 + 1 + 1 + 1 + 1 байт хвостовой прокладки до кратности 8 = 16.
3. **`Packed` (15 байт)** — это ровно сумма размеров полей (1+4+1+8+1=15) без единого байта прокладки: `#[repr(packed)]` снижает **выравнивание всей структуры до 1**, поэтому итоговый размер вообще не округляется до кратного 8 — в отличие от `Optimized` и `Unoptimized`.
4. **Разница в 16 МБ** на миллионе экземпляров между `Unoptimized` и `Optimized` — но эта разница возникла **только потому, что мы явно указали `#[repr(C)]`**. Без этого атрибута обе структуры (`Unoptimized` и `Optimized`) компилятор уложил бы одинаково компактно уже сам, и никакой разницы в размере не было бы вовсе.

### Золотое правило оптимизации структур — и когда оно на самом деле нужно

**Для обычных структур (без `#[repr(...)]`) заботиться о порядке полей не нужно** — компилятор Rust уже переставляет их автоматически, чтобы минимизировать паддинг, независимо от порядка объявления. Это фундаментальное отличие Rust от C, C++ и Go, где порядок полей в коде совпадает с физическим порядком в памяти, и программисту приходится сортировать их вручную.

Порядок полей начинает иметь значение только тогда, когда вы **сознательно отключаете** автоматическую перестановку — чаще всего атрибутом `#[repr(C)]`, необходимым для совместимости с C и FFI, где физический layout структуры должен быть предсказуемым и совпадать с ожиданиями внешнего кода. Именно в этом случае действует классическое правило:

```rust
#[repr(C)]
struct Optimized {
    big: u64,     // 8 байт
    medium: u32,  // 4 байта
    small: u16,   // 2 байта
    tiny: bool,   // 1 байт
}
// При repr(C): минимальный размер — поля идут от большего к меньшему
```

Без `#[repr(C)]` та же самая структура (в любом порядке полей) даст точно такой же минимальный размер и без ручной сортировки — компилятор сделает это сам.

---

### Как Rust размещает поля в памяти (с `#[repr(C)]`)

Возьмём более простой пример из трёх полей, чтобы наглядно увидеть логику паддинга:

```rust
#[repr(C)]
struct BadOrder {
    a: bool,
    b: i64,
    c: bool,
}

#[repr(C)]
struct GoodOrder {
    b: i64,
    a: bool,
    c: bool,
}
```

**`BadOrder` (repr(C), неоптимальный порядок):**

```
Адрес   Поле       Содержимое
0x00    a (bool)   1 байт
0x01    [padding]  7 байт прокладки (чтобы b начинался с адреса, кратного 8)
0x08    b (i64)    8 байт
0x10    c (bool)   1 байт
0x11    [padding]  7 байт хвостовой прокладки (чтобы весь размер был кратен 8)
0x18    Конец структуры
Всего: 24 байта
```

**`GoodOrder` (repr(C), оптимальный порядок):**

```
Адрес   Поле       Содержимое
0x00    b (i64)    8 байт
0x08    a (bool)   1 байт
0x09    c (bool)   1 байт
0x0A    [padding]  6 байт хвостовой прокладки
0x10    Конец структуры
Всего: 16 байт
```

Именно так работал бы Rust, **если бы он всегда сохранял порядок полей** — то есть именно так ведут себя C, C++ и Go по умолчанию, и именно поэтому в них программисту приходится думать о порядке полей самостоятельно. В обычном же Rust-коде (без `#[repr(C)]`) компилятор проделал бы эту сортировку за вас — независимо от того, в каком порядке вы написали `a`, `b`, `c`.

## Уникальность Rust в сравнении с другими языками

### C и C++

1. Порядок полей в памяти всегда совпадает с порядком объявления.
2. Нет встроенного способа проверить размер и выравнивание типа на этапе компиляции без сторонних инструментов.
3. Размер структуры может отличаться на разных платформах, и это нужно отслеживать вручную.

### Go

1. Порядок полей в памяти тоже фиксирован и совпадает с объявлением.
2. Нет возможности явно управлять выравниванием структуры (`#[repr(align(N))]`-аналога нет).
3. Существуют сторонние линтеры (например, `fieldalignment` из `golangci-lint`), которые предупреждают о неоптимальном порядке полей — то есть эта забота вручную переложена на разработчика и его инструменты.

### Rust

1. **По умолчанию — автоматическая оптимизация.** Компилятор сам переставляет поля структуры без `#[repr(...)]`, экономя память без каких-либо усилий со стороны программиста.
2. **`#[repr(C)]` — для совместимости с C.** Явно фиксирует порядок полей и layout, совместимый с C ABI:

```rust
#[repr(C)]
struct CCompatible {
    a: bool,
    b: i64,
    c: bool,
}
// Порядок полей соответствует C — гарантированно, но потенциально с лишним паддингом
```

3. **`#[repr(packed)]` — полная упаковка**, ценой более медленного и потенциально небезопасного доступа к невыровненным полям:

```rust
#[repr(packed)]
struct Packed {
    a: bool,
    b: i64,
    c: bool,
}
// Размер: ровно 10 байт (1+8+1, без единого байта прокладки)
// ⚠️ Взятие ссылки на поле такой структуры может быть небезопасным —
// компилятор предупредит об этом
```

4. **`#[repr(align(N))]` — увеличение выравнивания**, если структуре явно требуется более строгое выравнивание, чем даёт стандартный алгоритм:

```rust
#[repr(align(16))]
struct Aligned {
    a: bool,
    b: i64,
}
// Выравнивание увеличено до 16 байт
```

5. **Инструменты для исследования** прямо в стандартной библиотеке — `std::mem::size_of` и `std::mem::align_of` — доступны без каких-либо внешних зависимостей.

## Реальный пример: влияние на производительность

Разница в выравнивании — это не только про экономию памяти, но и про скорость доступа к полям:

```rust
use std::time::Instant;

#[repr(packed)]
struct Packed {
    a: bool,
    b: i64,
    c: bool,
}

#[repr(C)]
struct Aligned {
    a: bool,
    b: i64,
    c: bool,
}

fn main() {
    let count = 10_000_000;
    let packed_vec: Vec<Packed> = (0..count).map(|_| Packed { a: true, b: 42, c: false }).collect();
    let aligned_vec: Vec<Aligned> = (0..count).map(|_| Aligned { a: true, b: 42, c: false }).collect();

    let start = Instant::now();
    let mut sum: i64 = 0;
    for item in &packed_vec {
        sum += item.b;
    }
    println!("Packed:  {:?} (sum={})", start.elapsed(), sum);

    let start = Instant::now();
    let mut sum: i64 = 0;
    for item in &aligned_vec {
        sum += item.b;
    }
    println!("Aligned: {:?} (sum={})", start.elapsed(), sum);
}
```

## Главный вывод

> Выравнивание — это компромисс между памятью и производительностью. Для подавляющего большинства Rust-кода этот компромисс уже решён за вас: без `#[repr(...)]` компилятор сам подбирает оптимальный порядок полей, и вам не нужно об этом думать. Ручной контроль над layout — через `#[repr(C)]`, `#[repr(packed)]` и `#[repr(align(N))]` — становится нужен только тогда, когда важен предсказуемый, стабильный физический layout: чаще всего при взаимодействии с C через FFI. В отличие от многих языков, где выравнивание либо скрыто и непредсказуемо, либо целиком ложится на плечи программиста, Rust даёт both: разумную автоматику по умолчанию и полный явный контроль, когда он действительно нужен.

## Главное из этой главы

После этой главы мы понимаем:

- **Три области памяти:** стек, куча, статическая память.
- **Стек** — быстрый, но ограниченный. Используется для простых типов и ссылок.
- **Куча** — медленнее, но большая. Используется для динамических данных (`String`, `Vec`, `Box`).
- **Статическая память** — существует всё время работы программы.
- **`size_of`** — размер типа в байтах.
- **`align_of`** — выравнивание типа.
- **Порядок полей** влияет на размер структуры **только** при `#[repr(C)]` / `#[repr(packed)]`.
- **`Sized`** — трейт для типов с известным размером.
- **`Box<T>`** — данные в куче (фиксированный размер указателя).
- **Rust не использует GC** — управление памятью через владение.

**Самая важная идея:**

> Понимание того, где и как хранятся данные, помогает писать эффективный код и понимать, почему Rust устроен именно так. Стек — для быстрых, короткоживущих данных. Куча — для больших, долгоживущих данных. Владение — механизм, который делает управление памятью в куче безопасным и предсказуемым.
