## Практика

Практические задания этой главы направлены на то, чтобы не просто запомнить `Arc`, `Mutex`, `RwLock` и атомарные типы, а научиться выбирать подходящий механизм синхронизации и видеть проблемы многопоточного кода.

### Задание 1. Общий счётчик

Создайте программу, которая запускает **10 потоков**. Каждый поток должен увеличить общий счётчик на `1000`.

Используйте:

```rust
Arc<Mutex<usize>>
```

После завершения всех потоков программа должна вывести:

```text
Counter: 10000
```

**Требования:**

* счётчик должен быть общим для всех потоков;
* каждый поток должен получить собственный `Arc`;
* изменение счётчика должно выполняться внутри `Mutex`;
* основной поток должен дождаться завершения всех worker threads с помощью `join()`.

Начальная структура программы:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0usize));

    let mut handles = Vec::new();

    for _ in 0..10 {
        let counter = Arc::clone(&counter);

        let handle = thread::spawn(move || {
            for _ in 0..1000 {
                // TODO: изменить общий счётчик
            }
        });

        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Counter: {}", *counter.lock().unwrap());
}
```

**Ожидаемый результат:**

```text
Counter: 10000
```

Каждый worker должен выполнить 5 заданий. Для простоты роль задания может выполнять обычное число:

```rust

```

Каждый worker должен сообщать о выполнении задания:

```text
Worker 0 processed job 1
Worker 1 processed job 2
...
```

Используйте `Arc` для совместного доступа к общему состоянию.

Добавьте общий счётчик обработанных заданий:

```rust
Arc<Mutex<usize>>
```

После завершения всех worker threads программа должна вывести:

```text
Processed jobs: 20
```

**Цель задания:** понять, что `Arc` решает проблему совместного владения, а `Mutex` — проблему одновременного изменения общего состояния.

### Задание 3. Исправление race condition

Рассмотрим следующий код:

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(0usize);

    let mut handles = Vec::new();

    for _ in 0..10 {
        let counter = Arc::clone(&counter);

        let handle = thread::spawn(move || {
            // TODO
            // Попробуйте увеличить counter
        });

        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }
}
```

Попробуйте самостоятельно решить задачу.

Возникает вопрос: **почему одного `Arc` недостаточно?**

`Arc<T>` позволяет нескольким потокам владеть одним значением, но сам по себе не предоставляет изменяемый доступ к `T`.

Исправьте программу, используя:

```rust
Arc<Mutex<usize>>
```

Затем попробуйте заменить `Mutex` на атомарный тип:

```rust
Arc<AtomicUsize>
```

Сравните два решения.

**Вариант с `Mutex`:**

```rust
let mut value = counter.lock().unwrap();
*value += 1;
```

**Вариант с атомарным типом:**

```rust
counter.fetch_add(1, Ordering::SeqCst);
```

**Вопросы для самопроверки:**

1. Почему `Arc<usize>` не позволяет безопасно изменять `usize`?
2. Что добавляет `Mutex`?
3. Почему `AtomicUsize` не требует `Mutex`?
4. Какой вариант удобнее для сложной структуры данных?

### Задание 4. Эксперимент с deadlock

Создайте программу с двумя мьютексами:

```rust
let a = Arc::new(Mutex::new(0));
let b = Arc::new(Mutex::new(0));
```

Создайте два потока.

Первый поток должен захватывать блокировки в порядке:

```text
a → b
```

Второй:

```text
b → a
```

Например:

```rust
let handle1 = thread::spawn(move || {
    let _a = a1.lock().unwrap();

    thread::sleep(Duration::from_millis(10));

    let _b = b1.lock().unwrap();
});

let handle2 = thread::spawn(move || {
    let _b = b2.lock().unwrap();

    thread::sleep(Duration::from_millis(10));

    let _a = a2.lock().unwrap();
});
```

Запустите программу несколько раз и наблюдайте за результатом.

Программа может зависнуть, потому что возникает ситуация:

```text
Thread 1              Thread 2
--------              --------
lock(a)               lock(b)
   ↓                     ↓
wait(b)               wait(a)
   ↓                     ↓
       DEADLOCK
```

#### Исправление

Измените программу так, чтобы **оба потока всегда захватывали блокировки в одинаковом порядке**:

```text
a → b
```

Например:

```rust
let handle1 = thread::spawn(move || {
    let _a = a1.lock().unwrap();
    let _b = b1.lock().unwrap();

    // работа с a и b
});

let handle2 = thread::spawn(move || {
    let _a = a2.lock().unwrap();
    let _b = b2.lock().unwrap();

    // работа с a и b
});
```

Теперь циклического ожидания возникнуть не должно.

**Главный вывод эксперимента:**

> Rust гарантирует безопасность доступа к данным, но не гарантирует отсутствие логических проблем синхронизации. Deadlock — это не нарушение memory safety, а ошибка организации взаимодействия между потоками.

### Задание 5. Мини-проект: многопоточный счётчик

Объедините предыдущие задания в одну программу.

Создайте:

* **4 worker threads**;
* каждый worker выполняет **2500 операций**;
* общий счётчик `Arc<Mutex<usize>>`;
* каждый worker увеличивает счётчик после выполнения своей операции;
* основной поток ждёт завершения всех workers.

Ожидаемый результат:

```text
Worker 0 finished
Worker 1 finished
Worker 2 finished
Worker 3 finished

Counter: 10000
```

После этого сделайте вторую реализацию с:

```rust
Arc<AtomicUsize>
```

Таким образом, вы получите два полноценных решения одной задачи:

```text
              Общий счётчик
                    │
          ┌─────────┴─────────┐
          │                   │
    Arc<Mutex<usize>>    Arc<AtomicUsize>
          │                   │
       Mutex             atomic operation
          │                   │
          └─────────┬─────────┘
                    │
              4 worker threads
```

Это упражнение закрепляет основной принцип главы:

> `Arc` отвечает за совместное владение, `Mutex` — за взаимное исключение, а атомарные типы позволяют безопасно выполнять определённые операции над простыми значениями без `Mutex`.
