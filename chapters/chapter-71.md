# Глава 71. Designing Library APIs

Разработка библиотеки — это не просто написание кода. Это создание **интерфейса**, которым будут пользоваться другие разработчики.

Хороший API:

* легко изучить;
* трудно использовать неправильно;
* скрывает ненужные детали реализации;
* позволяет библиотеке развиваться;
* сообщает пользователю, какие гарантии предоставляет библиотека;
* предсказуемо обрабатывает ошибки.

Плохой API, напротив, заставляет пользователя знать внутреннее устройство библиотеки и делает даже небольшие изменения потенциально breaking.

Поэтому публичный API библиотеки следует рассматривать как **контракт** между библиотекой и её пользователями.

В этой главе мы разберёмся, как проектировать стабильные, удобные и эволюционирующие API для Rust-библиотек.

Все примеры этой главы используют **Rust Edition 2024**.

---

## 71.1. Публичное и приватное

Главный принцип API-дизайна:

> **Публикуйте минимум. Остальное оставляйте приватным.**

Каждый `pub` становится потенциальной частью публичного контракта библиотеки.

Например:

```rust
mod internal {
    pub(crate) struct InternalData {
        // Детали реализации доступны только внутри crate.
    }

    pub(crate) fn internal_helper() {
        // Внутренняя логика.
    }
}

pub struct PublicApi {
    // Поле приватное.
}

impl PublicApi {
    pub fn new() -> Self {
        Self {}
    }
}
```

Пользователь может создать `PublicApi` только через предусмотренный библиотекой API:

```rust
let api = PublicApi::new();
```

При этом библиотека сохраняет возможность изменить внутреннее представление:

```rust
pub struct PublicApi {
    // В следующей версии здесь может появиться
    // кэш, конфигурация, состояние и т. д.
}
```

### Почему публичные поля опасны

Рассмотрим:

```rust
pub struct User {
    pub id: u64,
    pub name: String,
}
```

Пользователь может написать:

```rust
let user = User {
    id: 42,
    name: String::from("Alice"),
};
```

Теперь библиотека обязана учитывать этот способ создания значения.

Если позже библиотеке понадобится добавить обязательное поле:

```rust
pub struct User {
    pub id: u64,
    pub name: String,
    pub permissions: Vec<String>,
}
```

старый код перестанет компилироваться.

Поэтому часто лучше использовать приватные поля и конструктор:

```rust
pub struct User {
    id: u64,
    name: String,
}

impl User {
    pub fn new(id: u64, name: impl Into<String>) -> Self {
        Self {
            id,
            name: name.into(),
        }
    }

    pub fn id(&self) -> u64 {
        self.id
    }

    pub fn name(&self) -> &str {
        &self.name
    }
}
```

Теперь библиотека контролирует создание `User` и может изменять внутреннее представление без изменения способа использования API.

### Правила

* Начинайте с приватных элементов.
* Делайте `pub` только то, что действительно является частью API.
* Скрывайте внутреннее состояние.
* Используйте методы-конструкторы вместо публичных полей, когда хотите сохранить свободу эволюции.
* Не публикуйте внутренние типы без необходимости.

## 71.2. API Stability — стабильность API

**Стабильный API** — это API, который позволяет существующему коду продолжать работать при обновлении библиотеки в пределах заявленной совместимости.

Стабильность касается не только имён и сигнатур.

Она включает:

* типы;
* trait implementations;
* generic bounds;
* публичные поля;
* поведение;
* ошибки;
* гарантии;
* возможность создавать значения;
* возможность pattern matching;
* особенности `Send`, `Sync`, `Unpin` и других trait bounds.

Например:

```rust
pub fn get_user(id: u64) -> Option<User> {
    // Реализация может изменяться.
    // Публичный контракт остаётся прежним.
    todo!()
}
```

Но даже изменение seemingly «внутреннего» поведения может быть breaking change, если пользователи полагались на документированную гарантию.

### `#[non_exhaustive]`

Если тип предполагает дальнейшее расширение, можно использовать:

```rust
#[non_exhaustive]
pub enum Status {
    Active,
    Inactive,
}
```

Внешний код должен быть готов к появлению новых вариантов:

```rust
match status {
    Status::Active => {}
    Status::Inactive => {}
    _ => {}
}
```

Для структуры:

```rust
#[non_exhaustive]
pub struct Config {
    pub host: String,
    pub port: u16,
}
```

внешний пользователь не может напрямую создать её через struct literal:

```rust
// В другом crate это запрещено:
//
// let config = Config {
//     host: "localhost".into(),
//     port: 8080,
// };
```

Поэтому библиотека должна предоставить способ создания значения:

```rust
impl Config {
    pub fn new(host: impl Into<String>, port: u16) -> Self {
        Self {
            host: host.into(),
            port,
        }
    }
}
```

Это позволяет библиотеке позднее добавить поле:

```rust
#[non_exhaustive]
pub struct Config {
    pub host: String,
    pub port: u16,
    pub timeout_ms: u64,
}
```

не ломая способ создания объекта через `Config::new`.

### Важная оговорка

Не следует считать, что **любое** добавление публичного элемента автоматически безопасно.

Например, добавление нового метода в trait может сломать существующие реализации этого trait.

Поэтому API нужно анализировать с точки зрения **downstream-кода** — кода пользователей вашей библиотеки.

## 71.3. SemVer — Semantic Versioning

**SemVer (Semantic Versioning)** — соглашение о версионировании программных пакетов.

Основная схема:

```text
MAJOR.MINOR.PATCH
  │     │     └── исправления и совместимые изменения
  │     └──────── совместимая новая функциональность
  └────────────── несовместимые изменения
```

Например:

```toml
[package]
name = "my_lib"
version = "1.2.3"
```

В общем случае:

| Изменение                               | Версия    |
| --------------------------------------- | --------- |
| Breaking change                         | MAJOR + 1 |
| Совместимое добавление функциональности | MINOR + 1 |
| Исправление ошибки                      | PATCH + 1 |

Например:

```rust
// v1.0.0

pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

В следующей версии можно добавить:

```rust
// v1.1.0

pub fn multiply(a: i32, b: i32) -> i32 {
    a * b
}
```

А изменение существующей сигнатуры:

```rust
// v2.0.0

pub fn add(a: f64, b: f64) -> f64 {
    a + b
}
```

является breaking change.

### SemVer — это не только изменение сигнатур

Например, было:

```rust
pub fn parse(input: &str) -> Result<Value, Error>
```

и документация обещает:

> Функция никогда не паникует.

Если в новой версии функция начинает вызывать `panic!`, это нарушение публичного контракта, даже если сигнатура осталась прежней.

Поэтому SemVer нужно применять к **поведению API**, а не только к его синтаксической форме.

## 71.4. MSRV — Minimum Supported Rust Version

**MSRV** — минимальная версия Rust, с которой библиотека поддерживает сборку.

Например:

```toml
[package]
name = "my_lib"
version = "1.0.0"
rust-version = "1.85"
edition = "2024"
```

Для этой главы важно помнить:

> **Rust Edition 2024 требует Rust 1.85 или новее.**

Поэтому MSRV `1.70` несовместим с crate, использующим:

```toml
edition = "2024"
```

### Зачем объявлять MSRV?

Пользователь библиотеки должен понимать:

> Какая минимальная версия компилятора мне нужна?

Это особенно важно для:

* крупных компаний;
* embedded-проектов;
* дистрибутивов Linux;
* проектов с жёстким контролем toolchain;
* CI/CD-систем.

### Проверка MSRV

Например:

```yaml
jobs:
  msrv:
    runs-on: ubuntu-latest

    strategy:
      matrix:
        rust: ["1.85", "stable"]

    steps:
      - uses: actions/checkout@v4

      - uses: dtolnay/rust-toolchain@master
        with:
          toolchain: ${{ matrix.rust }}

      - run: cargo test
```

Однако важно не просто записать `rust-version`, а действительно тестировать эту версию.

Если библиотека заявляет:

```toml
rust-version = "1.85"
```

пользователь вправе ожидать, что:

```text
Rust 1.85 + библиотека
```

будет работать.

## 71.5. Совместимость (Compatibility)

**Совместимость** — способность существующего пользовательского кода продолжать работать после обновления библиотеки.

### Часто совместимые изменения

Обычно безопаснее:

1. Добавить новую функцию.
2. Добавить новый тип.
3. Добавить новый inherent-метод, если он не создаёт конфликтов с существующим API.
4. Добавить метод в trait с реализацией по умолчанию.
5. Добавить вариант в `#[non_exhaustive]` enum.
6. Добавить поле в `#[non_exhaustive]` структуру.
7. Исправить внутреннюю реализацию без изменения контракта.

Но каждое изменение нужно рассматривать в контексте существующего кода.

### Важный пример: методы trait

Рассмотрим:

```rust
pub trait Storage {
    fn read(&self) -> String;
}
```

Пользователь может реализовать trait:

```rust
struct MyStorage;

impl Storage for MyStorage {
    fn read(&self) -> String {
        "data".into()
    }
}
```

Если библиотека добавит:

```rust
pub trait Storage {
    fn read(&self) -> String;

    fn write(&mut self, data: &str);
}
```

существующая реализация `MyStorage` перестанет компилироваться.

Поэтому для совместимого расширения лучше использовать реализацию по умолчанию:

```rust
pub trait Storage {
    fn read(&self) -> String;

    fn write(&mut self, _data: &str) {
        // По умолчанию запись не поддерживается.
    }
}
```

Теперь существующие реализации продолжают работать.

### Несовместимые изменения

Например:

```rust
// v1.0.0

pub enum Status {
    Active,
    Inactive,
}
```

Удаление варианта:

```rust
// v2.0.0

pub enum Status {
    Active,
}
```

может сломать существующий код.

Если enum предполагает расширение, лучше заранее объявить:

```rust
#[non_exhaustive]
pub enum Status {
    Active,
    Inactive,
}
```

Тогда пользователь изначально должен писать:

```rust
match status {
    Status::Active => {}
    Status::Inactive => {}
    _ => {}
}
```

и библиотека сможет добавлять варианты в будущих версиях.

## 71.6. Документация как часть API

Документация — не приложение к API.

**Документация является частью API-контракта.**

Например:

````rust
/// Складывает два числа.
///
/// # Arguments
///
/// * `a` — первое число.
/// * `b` — второе число.
///
/// # Returns
///
/// Сумма `a` и `b`.
///
/// # Examples
///
/// ```
/// assert_eq!(add(2, 3), 5);
/// ```
///
/// # Panics
///
/// Эта функция никогда не паникует.
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

Пример внутри документации — это **doctest**. Cargo может выполнить его как тест.

Это очень важно: документация становится не просто текстом, а проверяемым примером.

### Для функций с ошибками

Следует описывать возможные ошибки:

```rust
/// Читает конфигурацию из файла.
///
/// # Errors
///
/// Возвращает ошибку, если файл не существует
/// или не может быть прочитан.
pub fn read_config(path: &str) -> std::io::Result<String> {
    std::fs::read_to_string(path)
}
```

### Для `unsafe`

Если публичная функция использует `unsafe`, документация должна описывать условия безопасности:

```rust
/// Создаёт срез из указателя и длины.
///
/// # Safety
///
/// Вызывающий код должен гарантировать, что:
///
/// - `ptr` указывает на `len` корректных элементов `T`;
/// - память доступна для чтения;
/// - элементы находятся в одном выделенном объекте памяти.
pub unsafe fn from_raw_parts<'a, T>(
    ptr: *const T,
    len: usize,
) -> &'a [T] {
    // ...
    todo!()
}
```

Для `unsafe` API раздел `# Safety` — не формальность. Это часть контракта между библиотекой и вызывающим кодом.

### Что документировать

Для публичного API следует объяснять:

* что делает функция или тип;
* параметры;
* возвращаемое значение;
* ошибки;
* возможные panic;
* ограничения;
* гарантии;
* `unsafe`-условия;
* примеры;
* особенности использования.

## 71.7. Примеры — лучшая документация

Пользователь часто быстрее понимает API по небольшому рабочему примеру, чем по нескольким абзацам описания.

Например:

````rust
/// Конфигурация сервера.
///
/// # Examples
///
/// ```
/// let config = Config::new()
///     .host("localhost")
///     .port(8080);
///
/// assert_eq!(config.host(), "localhost");
/// assert_eq!(config.port(), 8080);
/// ```
pub struct Config {
    host: String,
    port: u16,
}

impl Config {
    pub fn new() -> Self {
        Self {
            host: "localhost".into(),
            port: 8080,
        }
    }

    pub fn host(mut self, host: impl Into<String>) -> Self {
        self.host = host.into();
        self
    }

    pub fn port(mut self, port: u16) -> Self {
        self.port = port;
        self
    }

    pub fn host_name(&self) -> &str {
        &self.host
    }

    pub fn port_number(&self) -> u16 {
        self.port
    }
}
````

На практике для библиотечного API стоит следить, чтобы пример был:

1. коротким;
2. реалистичным;
3. копируемым;
4. компилируемым;
5. автоматически проверяемым.

Не следует писать пример, который красиво выглядит, но не компилируется.

## 71.8. Deprecation — устаревание

Если публичный API больше не рекомендуется использовать, не следует сразу его удалять.

Сначала его можно объявить deprecated:

```rust
pub struct Config {
    timeout: u64,
}

impl Config {
    /// Устанавливает таймаут.
    #[deprecated(
        since = "2.0.0",
        note = "use `Config::with_timeout` instead"
    )]
    pub fn set_timeout(&mut self, value: u64) {
        self.timeout = value;
    }

    /// Создаёт конфигурацию с указанным таймаутом.
    pub fn with_timeout(mut self, value: u64) -> Self {
        self.timeout = value;
        self
    }
}
```

При использовании старого API пользователь получит предупреждение:

```text
warning: use of deprecated method `Config::set_timeout`:
use `Config::with_timeout` instead
```

Таким образом, переход можно выполнить постепенно:

```text
старый API
    │
    ▼
deprecated
    │
    ▼
пользователи получают warning
    │
    ▼
новый API
    │
    ▼
следующий major release
    │
    ▼
удаление старого API
```

### Хорошее сообщение deprecation

Сообщение должно отвечать на вопрос:

> Что мне теперь использовать?

Хорошо:

```rust
#[deprecated(
    since = "2.0.0",
    note = "use `Client::request` instead"
)]
```

Плохо:

```rust
#[deprecated(note = "old")]
```

## 71.9. API Evolution — эволюция API

Хороший библиотечный API проектируется не только для сегодняшнего дня.

Нужно заранее подумать:

> Что произойдёт, если через год потребуется добавить новую возможность?

### Стратегия 1. Добавляйте, не удаляйте

Если возможно, новый API добавляйте рядом со старым:

```rust
impl Client {
    pub fn request(&self, url: &str) -> Response {
        // Новый API.
        todo!()
    }

    #[deprecated(
        since = "2.0.0",
        note = "use `Client::request` instead"
    )]
    pub fn get(&self, url: &str) -> Response {
        self.request(url)
    }
}
```

Старый API продолжает работать, но пользователи постепенно переходят на новый.

### Стратегия 2. Используйте `#[non_exhaustive]`

Для типов, которые предполагается расширять:

```rust
#[non_exhaustive]
pub struct Config {
    pub host: String,
    pub port: u16,
}
```

Но при этом предоставьте конструктор:

```rust
impl Config {
    pub fn new(host: impl Into<String>, port: u16) -> Self {
        Self {
            host: host.into(),
            port,
        }
    }
}
```

### Стратегия 3. Builder вместо огромного конструктора

Если объект имеет много параметров, вместо:

```rust
Config::new(
    "localhost",
    8080,
    30,
    true,
    100,
    "json",
)
```

можно предоставить:

```rust
Config::builder()
    .host("localhost")
    .port(8080)
    .timeout(30)
    .compression(true)
    .build();
```

Такой API легче читать и расширять.

### Стратегия 4. Используйте re-export для стабильного пути

Предположим, реализация находится внутри:

```rust
mod client;
```

Но пользователь должен импортировать:

```rust
use my_lib::Client;
```

Можно написать:

```rust
mod client;

pub use client::Client;
```

Теперь внутренняя структура модулей может изменяться:

```text
v1:
my_lib::client::Client

v2:
my_lib::http::Client

v3:
my_lib::transport::Client
```

а публичный путь:

```rust
my_lib::Client
```

может оставаться неизменным.

Это важный приём: **публичный путь не обязан совпадать с внутренней структурой проекта.**

## 71.10. Feature flags — условные возможности

Cargo features позволяют сделать часть функциональности опциональной.

Например:

```toml
[features]
default = []
serde = ["dep:serde"]
async = ["dep:tokio"]
full = ["serde", "async"]

[dependencies]
serde = { version = "1", optional = true }
tokio = { version = "1", features = ["rt", "macros"], optional = true }
```

Теперь feature `serde` включает зависимость `serde`, а feature `async` — `tokio`.

В коде:

```rust
#[cfg(feature = "serde")]
use serde::{Deserialize, Serialize};

#[cfg(feature = "serde")]
#[derive(Serialize, Deserialize)]
pub struct User {
    pub id: u64,
    pub name: String,
}
```

Асинхронная функциональность:

```rust
#[cfg(feature = "async")]
pub async fn fetch_data() -> String {
    "data".into()
}
```

Пользователь может выбрать:

```bash
cargo add my_lib --features serde
```

или:

```bash
cargo add my_lib --features "serde async"
```

### Почему features являются частью API

Если функция существует только при определённой feature:

```rust
#[cfg(feature = "async")]
pub async fn fetch_data() {}
```

то feature становится частью контракта библиотеки.

Изменение feature может повлиять на:

* доступные типы;
* доступные функции;
* зависимости;
* время компиляции;
* размер бинарного файла;
* совместимость с другими crates.

Поэтому features тоже нужно проектировать и документировать.

## 71.11. Публичный API и «скрытые» зависимости

При проектировании библиотеки важно смотреть не только на `pub`.

Например:

```rust
pub fn parse() -> Result<MyValue, serde_json::Error> {
    // ...
    todo!()
}
```

Теперь `serde_json::Error` стал частью публичной сигнатуры.

Это означает, что библиотека фактически включает конкретный тип сторонней зависимости в свой API.

Иногда это нормально. Но иногда лучше скрыть деталь:

```rust
pub fn parse() -> Result<MyValue, ParseError> {
    // ...
    todo!()
}
```

где:

```rust
#[derive(Debug)]
pub struct ParseError {
    // Собственный публичный контракт.
}
```

Так библиотека получает больше свободы изменить внутренний parser.

### Практическое правило

Если тип сторонней зависимости появляется в публичной сигнатуре, спросите:

> **Я действительно хочу сделать этот внешний тип частью своего API-контракта?**

Если ответ отрицательный — рассмотрите возможность собственного типа-обёртки.

## 71.12. Чек-лист API дизайна

Перед публикацией библиотеки полезно пройти следующий чек-лист.

1. **Минимизируйте публичный API.**
2. **Скрывайте детали реализации.**
3. **Избегайте публичных полей, если хотите сохранить свободу эволюции.**
4. **Документируйте каждый публичный элемент.**
5. **Добавляйте компилируемые doctest-примеры.**
6. **Описывайте `Errors`, `Panics` и `Safety`, когда они применимы.**
7. **Определите и объявите MSRV.**
8. **Тестируйте заявленный MSRV.**
9. **Следуйте SemVer.**
10. **Используйте `#[non_exhaustive]` для расширяемых публичных типов.**
11. **Осторожно изменяйте публичные traits.**
12. **Используйте `#[deprecated]` перед удалением старого API.**
13. **Стабилизируйте публичные пути через `pub use`, если внутренняя структура может измениться.**
14. **Документируйте features.**
15. **Проверяйте публичные зависимости в сигнатурах.**
16. **Ведите changelog.**
17. **Тестируйте обратную совместимость.**
18. **Учитывайте не только компиляцию, но и поведенческий контракт.**

### Эксперимент 4: `#[non_exhaustive]`

Создайте:

```rust
#[non_exhaustive]
enum Status {
    Active,
    Inactive,
}
```

Попробуйте написать:

```rust
match status {
    Status::Active => {}
    Status::Inactive => {}
}
```

В одном crate это может компилироваться, но для пользователя из другого crate потребуется учитывать будущие варианты.

Это хорошо демонстрирует, что `#[non_exhaustive]` является механизмом **эволюции API**, а не просто атрибутом enum.

## Главное из этой главы

После этой главы мы понимаем:

* **`pub` / `private`** — публичная поверхность API должна быть минимальной.
* **API stability** — публичный контракт включает не только сигнатуры, но и поведение.
* **SemVer** — версия должна отражать совместимость изменений.
* **MSRV** — библиотека должна явно сообщать минимальную поддерживаемую версию Rust.
* **`#[non_exhaustive]`** — инструмент для проектирования расширяемых публичных типов.
* **Traits** — изменение публичного trait может сломать downstream-реализации.
* **Документация** — часть API-контракта.
* **Doctests** — способ превратить примеры документации в автоматически проверяемый код.
* **`#[deprecated]`** — механизм безопасного перехода от старого API к новому.
* **`pub use`** — способ отделить стабильную структуру публичного API от внутренней организации crate.
* **Feature flags** — часть API и должны проектироваться так же внимательно, как функции и типы.
* **Публичные зависимости** — типы внешних crates в сигнатурах также становятся частью вашего API.

**Самая важная идея:**

> API — это контракт между библиотекой и её пользователями.
>
> Этот контракт включает не только имена функций и их сигнатуры. В него входят типы, traits, ошибки, поведение, гарантии, публичные поля, feature flags и даже структура использования API.
>
> Поэтому хороший библиотечный API проектируют не только для того, чтобы им было удобно пользоваться сегодня. Его проектируют так, чтобы библиотека могла **эволюционировать завтра, не ломая вчерашний код**.
