# Глава 49. Integration Tests

В предыдущей главе мы научились писать модульные тесты (unit tests), которые проверяют отдельные компоненты в изоляции. Но настоящие программы — это системы, где компоненты взаимодействуют друг с другом. Как убедиться, что вся система работает правильно?

Для этого существуют **интеграционные тесты (integration tests)**. Они проверяют, как компоненты работают вместе, и тестируют публичный API так, как это делают пользователи вашего кода.

В этой главе мы научимся писать интеграционные тесты, организовывать их в проектах и использовать тестовые утилиты.

Все примеры этой главы используют **Rust Edition 2024**.

---

## 49.1. Что такое интеграционные тесты?

**Интеграционные тесты (integration tests)** проверяют работу нескольких частей программы через их публичный API.

Главное отличие от модульного тестирования состоит не столько в количестве компонентов, сколько в **границе теста**.

Модульный тест находится внутри исходного кода крейта и поэтому может обращаться к приватным элементам. Интеграционный тест находится за пределами `src/` и использует крейт так, как его использовал бы внешний потребитель.

Типичная структура библиотечного проекта:

```text
my_project/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   └── ...
└── tests/
    ├── integration_test.rs
    └── api_tests.rs
```

Каждый файл непосредственно внутри `tests/` становится **отдельным test crate**.

Например:

```text
tests/
├── users.rs
└── orders.rs
```

означает, что Cargo создаст два отдельных тестовых исполняемых файла:

```text
users
orders
```

Оба они будут импортировать `my_project` через его публичный API.

Поэтому интеграционный тест **не может** написать:

```rust
use my_project::private_function;
```

если `private_function` не является частью публичного API.

Это важное свойство интеграционных тестов: они позволяют проверить не внутреннюю реализацию, а **контракт библиотеки с её пользователем**.

## 49.2. Первый интеграционный тест

Создадим библиотечный крейт:

```text
my_project/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

### Библиотека

```rust
// src/lib.rs

pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

pub fn multiply(a: i32, b: i32) -> i32 {
    a * b
}

pub mod calculator {
    pub fn subtract(a: i32, b: i32) -> i32 {
        a - b
    }
}
```

### Интеграционный тест

```rust
// tests/integration_test.rs

use my_project::{add, multiply, calculator};

#[test]
fn test_add() {
    assert_eq!(add(2, 3), 5);
}

#[test]
fn test_multiply() {
    assert_eq!(multiply(2, 3), 6);
}

#[test]
fn test_subtract() {
    assert_eq!(calculator::subtract(5, 3), 2);
}
```

Обратите внимание: тест не использует `src/lib.rs` напрямую.

Он импортирует:

```rust
use my_project::...
```

точно так же, как это сделал бы другой крейт, зависящий от `my_project`.

Запускаем:

```bash
cargo test
```

Cargo обнаружит `tests/integration_test.rs`, скомпилирует его как отдельный тестовый крейт и выполнит три теста.

> **Важно:** такой пример нельзя буквально запустить в Rust Playground как интеграционный тест, потому что Playground не создаёт показанную структуру проекта с `src/lib.rs` и `tests/`. Для проверки синтаксиса и самих assertions можно использовать отдельный Playground-пример.

## 49.3. Интеграционные тесты vs модульные тесты

| Характеристика               | Модульные тесты                                    | Интеграционные тесты                                          |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| **Расположение**             | В `src/`, рядом с кодом                            | В `tests/`                                                    |
| **Граница теста**            | Внутри модуля                                      | Снаружи библиотеки                                            |
| **Доступ к приватному коду** | Да                                                 | Нет                                                           |
| **API**                      | Может тестировать внутреннюю реализацию            | Только публичный API                                          |
| **Цель**                     | Проверить отдельную функцию, тип или модуль        | Проверить взаимодействие компонентов через публичный контракт |
| **Компиляция**               | Обычно входит в test build библиотеки              | Каждый `tests/*.rs` — отдельный test crate                    |
| **Скорость**                 | Обычно очень быстрые                               | Обычно медленнее                                              |
| **Количество**               | Обычно много                                       | Обычно меньше                                                 |
| **Типичные сценарии**        | Граничные случаи, алгоритмы, внутренние инварианты | Полные пользовательские сценарии, взаимодействие модулей, API |

Важно не воспринимать это как строгое правило:

> **Unit test** отвечает на вопрос: «Правильно ли работает этот компонент?»

> **Integration test** отвечает на вопрос: «Правильно ли взаимодействуют компоненты через публичный API?»

Например, библиотека может состоять из:

```text
Parser → Model → Validator → Serializer
```

Unit-тесты могут отдельно проверять `Parser`, `Validator` и `Serializer`.

Интеграционный тест может проверить уже полный сценарий:

```text
JSON
 ↓
Parser
 ↓
Model
 ↓
Validator
 ↓
Serializer
 ↓
JSON
```

При этом интеграционному тесту совершенно не нужно знать, какие приватные функции используются внутри этих компонентов.

## 49.4. Общие модули в `tests/`

Если несколько интеграционных тестов используют одинаковые вспомогательные функции, их удобно вынести в общий модуль.

Например:

```text
my_project/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    ├── common/
    │   └── mod.rs
    ├── users.rs
    └── orders.rs
```

Файл:

```text
tests/common/mod.rs
```

содержит только вспомогательный код:

```rust
pub fn setup() {
    println!("Setting up test environment...");
}

pub fn create_test_data() -> i32 {
    42
}
```

Теперь его можно использовать из разных тестовых файлов:

```rust
// tests/users.rs

mod common;

use my_project::add;

#[test]
fn test_user_data() {
    common::setup();

    let data = common::create_test_data();

    assert_eq!(add(data, 10), 52);
}
```

И:

```rust
// tests/orders.rs

mod common;

use my_project::multiply;

#[test]
fn test_order_data() {
    common::setup();

    let data = common::create_test_data();

    assert_eq!(multiply(data, 2), 84);
}
```

### Почему `common` не становится отдельным тестовым набором?

Cargo рассматривает файлы непосредственно в `tests/` как интеграционные test crates:

```text
tests/users.rs
tests/orders.rs
```

Но:

```text
tests/common/mod.rs
```

подключается как обычный Rust-модуль:

```rust
mod common;
```

Поэтому `common` не создаёт отдельный тестовый executable.

Если же поместить в `common` функцию:

```rust
#[test]
fn some_test() {
    // ...
}
```

и подключить:

```rust
mod common;
```

в двух тестовых файлах, этот тест будет включён **в оба test crate** и фактически выполнится дважды — по одному разу в каждом из них.

Поэтому `common` предназначен именно для **вспомогательного кода**, а не для хранения самих тестов.

## 49.5. Тестирование публичного API

Одно из главных преимуществ интеграционных тестов — возможность проверять библиотеку с позиции её пользователя.

Рассмотрим API:

```rust
// src/lib.rs

pub struct User {
    name: String,
    age: u32,
}

impl User {
    pub fn new(name: &str, age: u32) -> Self {
        Self {
            name: name.to_string(),
            age,
        }
    }

    pub fn name(&self) -> &str {
        &self.name
    }

    pub fn age(&self) -> u32 {
        self.age
    }

    pub fn is_adult(&self) -> bool {
        self.age >= 18
    }
}
```

Обратите внимание:

```rust
name: String,
age: u32,
```

не являются `pub`.

Следовательно, внешний пользователь не может сделать:

```rust
let user = User {
    name: "Alice".to_string(),
    age: 30,
};
```

Он должен использовать публичный конструктор:

```rust
User::new(...)
```

Именно это мы и проверяем в интеграционном тесте:

```rust
// tests/user_tests.rs

use my_project::User;

#[test]
fn user_can_be_created_through_public_api() {
    let user = User::new("Alice", 30);

    assert_eq!(user.name(), "Alice");
    assert_eq!(user.age(), 30);
}

#[test]
fn user_can_be_checked_for_adulthood() {
    let adult = User::new("Bob", 25);
    assert!(adult.is_adult());

    let minor = User::new("Charlie", 17);
    assert!(!minor.is_adult());
}
```

Такой тест проверяет именно тот API, который доступен потребителю библиотеки.

Если позднее внутренняя реализация `User` полностью изменится, но публичный API останется прежним, интеграционные тесты продолжат проверять тот же контракт.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=pub%20struct%20User%20%7B%0A%20%20%20%20name%3A%20String%2C%0A%20%20%20%20age%3A%20u32%2C%0A%7D%0A%0Aimpl%20User%20%7B%0A%20%20%20%20pub%20fn%20new%28name%3A%20%26str%2C%20age%3A%20u32%29%20-%3E%20Self%20%7B%0A%20%20%20%20%20%20%20%20Self%20%20%7B%0A%20%20%20%20%20%20%20%20%20%20%20%20name%3A%20name.to_string%28%29%2C%0A%20%20%20%20%20%20%20%20%20%20%20%20age%2C%0A%20%20%20%20%20%20%20%20%7D%0A%20%20%20%20%7D%0A%0A%20%20%20%20pub%20fn%20name%28%26self%29%20-%3E%20%26str%20%7B%0A%20%20%20%20%20%20%20%20%26self.name%0A%20%20%20%20%7D%0A%0A%20%20%20%20pub%20fn%20age%28%26self%29%20-%3E%20u32%20%7B%0A%20%20%20%20%20%20%20%20self.age%0A%20%20%20%20%7D%0A%0A%20%20%20%20pub%20fn%20is_adult%28%26self%29%20-%3E%20bool%20%7B%0A%20%20%20%20%20%20%20%20self.age%20%3E%3D%2018%0A%20%20%20%20%7D%0A%7D%0A%0A%23%5Btest%5D%0Afn%20user_can_be_created%28%29%20%7B%0A%20%20%20%20let%20user%20%3D%20User%3A%3Anew%28%22Alice%22%2C%2030%29%3B%0A%20%20%20%20assert_eq%21%28user.name%28%29%2C%20%22Alice%22%29%3B%0A%20%20%20%20assert_eq%21%28user.age%28%29%2C%2030%29%3B%0A%7D%0A%0A%23%5Btest%5D%0Afn%20user_can_be_checked%28%29%20%7B%0A%20%20%20%20assert%21%28User%3A%3Anew%28%22Bob%22%2C%2025%29.is_adult%28%29%29%3B%0A%20%20%20%20assert%21%28%21User%3A%3Anew%28%22Charlie%22%2C%2017%29.is_adult%28%29%29%3B%0A%7D)

## 49.6. Тестирование ошибок в интеграционных тестах

Интеграционные тесты могут проверять не только успешные сценарии, но и ошибки публичного API.

Если функция действительно использует `panic!`, можно использовать `#[should_panic]`:

```rust
// src/lib.rs

pub fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("Division by zero!");
    }

    a / b
}
```

Интеграционный тест:

```rust
// tests/error_tests.rs

use my_project::divide;

#[test]
fn divide_works() {
    assert_eq!(divide(10, 2), 5);
}

#[test]
#[should_panic(expected = "Division by zero!")]
fn divide_by_zero_panics() {
    divide(10, 0);
}
```

Здесь проверяются два разных контракта:

```text
divide(10, 2) → 5
divide(10, 0) → panic
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=pub%20fn%20divide%28a%3A%20i32%2C%20b%3A%20i32%29%20-%3E%20i32%20%7B%0A%20%20%20%20if%20b%20%3D%3D%200%20%7B%0A%20%20%20%20%20%20%20%20panic%21%28%22Division%20by%20zero%21%22%29%3B%0A%20%20%20%20%7D%0A%0A%20%20%20%20a%20%2F%20b%0A%7D%0A%0A%23%5Btest%5D%0Afn%20divide_works%28%29%20%7B%0A%20%20%20%20assert_eq%21%28divide%2810%2C%202%29%2C%205%29%3B%0A%7D%0A%0A%23%5Btest%5D%0A%23%5Bshould_panic%28expected%20%3D%20%22Division%20by%20zero%21%22%29%5D%0Afn%20divide_by_zero_panics%28%29%20%7B%0A%20%20%20%20divide%2810%2C%200%29%3B%0A%7D)

Однако для ошибок, которые являются **ожидаемой частью API**, обычно лучше возвращать `Result`, а не использовать `panic!`.

## 49.7. Тесты с `Result`

Тестовая функция может возвращать `Result<(), E>`. Если результат — `Ok(())`, тест считается успешным. Если результат — `Err(...)`, тест считается проваленным.

Это особенно удобно при тестировании функций, которые сами возвращают `Result`, поскольку оператор `?` позволяет не писать большое количество ручных проверок.

Например, создадим функцию:

```rust
pub fn parse_number(value: &str) -> Result<i32, std::num::ParseIntError> {
    value.parse()
}
```

Тест:

```rust
#[test]
fn parse_valid_number() -> Result<(), std::num::ParseIntError> {
    let number = parse_number("42")?;

    assert_eq!(number, 42);

    Ok(())
}
```

А ошибочный ввод можно проверить непосредственно:

```rust
#[test]
fn parse_invalid_number() {
    let result = parse_number("hello");

    assert!(result.is_err());
}
```

Можно проверить и конкретный тип результата:

```rust
#[test]
fn parse_negative_number() -> Result<(), std::num::ParseIntError> {
    let number = parse_number("-42")?;

    assert_eq!(number, -42);

    Ok(())
}
```

Такой стиль особенно полезен для интеграционных тестов реальных библиотек, где API часто выглядит так:

```rust
fn load(...) -> Result<T, Error>
```

и тест должен проверить одновременно успешный сценарий и обработку ошибок.

## 49.8. Несколько интеграционных тестов

Для большого проекта интеграционные тесты удобно разделять по сценариям:

```text
tests/
├── common/
│   └── mod.rs
├── basic_tests.rs
├── edge_cases.rs
├── user_tests.rs
└── api_tests.rs
```

Например:

```rust
// tests/basic_tests.rs

use my_project::add;

#[test]
fn add_positive_numbers() {
    assert_eq!(add(2, 3), 5);
}

#[test]
fn add_negative_numbers() {
    assert_eq!(add(-2, -3), -5);
}
```

А отдельный файл можно посвятить граничным значениям:

```rust
// tests/edge_cases.rs

use my_project::add;

#[test]
fn add_zero() {
    assert_eq!(add(5, 0), 5);
    assert_eq!(add(0, 5), 5);
}

#[test]
fn add_max_value_and_zero() {
    assert_eq!(add(i32::MAX, 0), i32::MAX);
}
```

При этом следует осторожно относиться к тестам переполнения.

Например, такой код:

```rust
add(i32::MAX, 1)
```

в debug-сборке приведёт к panic, потому что обычное целочисленное сложение проверяется на переполнение.

Поэтому тестировать переполнение нужно **осознанно**, исходя из контракта функции. Если функция должна возвращать ошибку, лучше реализовать такой контракт явно:

```rust
pub fn checked_add(a: i32, b: i32) -> Option<i32> {
    a.checked_add(b)
}
```

и проверять:

```rust
#[test]
fn addition_overflow_is_reported() {
    assert_eq!(checked_add(i32::MAX, 1), None);
}
```

[▶ Открыть пример с обработкой переполнения в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=pub%20fn%20checked_add%28a%3A%20i32%2C%20b%3A%20i32%29%20-%3E%20Option%3Ci32%3E%20%7B%0A%20%20%20%20a.checked_add%28b%29%0A%7D%0A%0A%23%5Btest%5D%0Afn%20addition_overflow_is_reported%28%29%20%7B%0A%20%20%20%20assert_eq%21%28checked_add%28i32%3A%3AMAX%2C%201%29%2C%20None%29%3B%0A%7D)

## 49.10. Интеграционные тесты для бинарных крейтов

Здесь есть важное ограничение Rust.

Если пакет содержит только:

```text
src/
└── main.rs
```

то это **binary crate**. Его `main.rs` нельзя импортировать из интеграционного теста как библиотеку:

```rust
// tests/integration_test.rs

use my_app::some_function; // ❌ Нельзя импортировать main.rs
```

Причина проста: бинарный крейт предназначен для запуска программы, а не для использования как библиотека.

### Рекомендуемая структура

Если приложению нужна тестируемая бизнес-логика, её обычно выносят в библиотечный target:

```text
my_app/
├── Cargo.toml
├── src/
│   ├── main.rs
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

Например:

```rust
// src/lib.rs

pub fn calculate_total(price: u32, quantity: u32) -> u32 {
    price * quantity
}
```

`main.rs` становится тонким entry point:

```rust
// src/main.rs

fn main() {
    let total = my_app::calculate_total(100, 3);

    println!("Total: {total}");
}
```

А интеграционный тест использует библиотечный API:

```rust
// tests/integration_test.rs

use my_app::calculate_total;

#[test]
fn calculate_total_works() {
    assert_eq!(calculate_total(100, 3), 300);
}
```

Это распространённый и полезный архитектурный приём:

```text
             ┌──────────────┐
             │   main.rs    │
             │ entry point  │
             └──────┬───────┘
                    │
                    ▼
             ┌──────────────┐
             │   lib.rs     │
             │ application  │
             │    logic     │
             └──────┬───────┘
                    ▲
                    │
             ┌──────┴───────┐
             │   tests/     │
             │ integration  │
             └──────────────┘
```

Такой подход позволяет одновременно:

* иметь исполняемое приложение;
* переиспользовать библиотечную логику;
* тестировать эту логику через интеграционные тесты;
* не помещать бизнес-логику непосредственно в `main()`.

## 49.11. Пример: интеграционный тест для веб-сервера

Интеграционные тесты особенно полезны для API и веб-приложений, потому что позволяют проверять сценарий через публичный интерфейс.

Однако конкретная реализация зависит от используемого веб-фреймворка. Поэтому нельзя использовать вымышленные методы вроде:

```rust
server.start();
server.get("/health");
```

и выдавать такой код за готовый Rust-пример.

Правильная идея выглядит так:

```text
HTTP request
     │
     ▼
┌─────────────┐
│ Web server  │
├─────────────┤
│   Router    │
├─────────────┤
│  Handler    │
├─────────────┤
│ Application │
│    logic    │
└─────────────┘
     │
     ▼
HTTP response
```

Интеграционный тест должен проверять именно внешний контракт:

```text
GET /health
      ↓
HTTP 200
      ↓
{"status":"ok"}
```

Например, API может предоставить функцию, создающую приложение:

```rust
pub fn create_app() -> App {
    // настройка маршрутов
}
```

А тест должен использовать её так, как это делает реальный HTTP-клиент или тестовый HTTP harness конкретного фреймворка:

```rust
#[test]
fn health_endpoint_returns_success() {
    // создать приложение;
    // отправить GET /health;
    // проверить HTTP status;
    // проверить тело ответа.
}
```

В реальном проекте такой тест следует писать средствами используемого фреймворка — например, через его встроенный test client или отдельный HTTP-клиент.

**Главная идея интеграционного теста веб-приложения:** тестировать не приватную функцию обработчика, а наблюдаемое поведение API:

```text
request → router → handler → response
```

Именно поэтому веб-API — один из наиболее естественных случаев применения интеграционных тестов.

## 🔨 Эксперименты с компилятором

### Эксперимент 1: Попытка импорта приватного элемента

Предположим, в библиотеке есть:

```rust
fn private_function() -> i32 {
    42
}
```

Попробуем из `tests/integration_test.rs` написать:

```rust
use my_project::private_function;
```

Компилятор сообщит, что функция является приватной.

Это принципиальное отличие от unit-теста внутри `src/lib.rs`: интеграционный тест находится за границей модуля библиотеки.

### Эксперимент 2: Тест внутри `common`

Создадим:

```rust
// tests/common/mod.rs

#[test]
fn test_in_common() {
    println!("common test");
}
```

И подключим:

```rust
// tests/users.rs

mod common;
```

а также:

```rust
// tests/orders.rs

mod common;
```

Теперь `test_in_common` окажется в двух разных test crates и будет выполнен дважды.

Это показывает, почему `tests/common/` следует использовать для **вспомогательных функций**, а сами тесты размещать в `tests/*.rs`.

## Главное из этой главы

После этой главы мы понимаем:

* **Интеграционные тесты** проверяют публичный API и взаимодействие компонентов.
* **`tests/`** содержит интеграционные test crates.
* **Каждый `tests/*.rs`** компилируется как отдельный тестовый крейт.
* **Приватные элементы** библиотеки недоступны интеграционным тестам.
* **`tests/common/`** удобно использовать для общих тестовых утилит.
* **`Result<(), E>`** позволяет писать fallible-тесты и использовать оператор `?`.
* **`#[should_panic]`** позволяет проверять ожидаемые паники.
* **`cargo test --test NAME`** запускает конкретный интеграционный test target.
* **Binary-only crate** нельзя импортировать из интеграционного теста; тестируемую логику следует вынести в library target.
* Интеграционные тесты особенно полезны для проверки **пользовательских сценариев и публичных API**.

**Самая важная идея:**

> Интеграционный тест должен смотреть на программу снаружи. Он не должен знать, как устроена внутренняя реализация; ему важно только, что публичный API выполняет заявленный контракт.
>
> Хорошая архитектура тестов обычно сочетает много быстрых unit-тестов, проверяющих отдельные компоненты и граничные случаи, с меньшим количеством интеграционных тестов, проверяющих важные пользовательские сценарии и взаимодействие компонентов.
