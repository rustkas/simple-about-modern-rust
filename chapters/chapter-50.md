# Глава 50. Documentation Tests

В Rust документация — это не просто текст, описывающий код. Это **исполняемые примеры**, которые автоматически тестируются вместе с вашими тестами. Это одна из самых сильных сторон Rust: документация всегда актуальна, потому что примеры в ней проверяются компилятором.

В этой главе мы научимся писать документацию, создавать примеры, которые тестируются, и использовать документацию как часть публичного API.

Все примеры этой главы используют **Rust Edition 2024**.

---

## 50.1. Комментарии документации: `///`

Для документирования Rust-кода используются специальные **doc-комментарии**:

| Стиль        | Назначение                                     |
| ------------ | ---------------------------------------------- |
| `///`        | Документирует следующий элемент                |
| `//!`        | Документирует содержащий модуль или весь crate |
| `/** ... */` | Многострочная форма `///`                      |
| `/*! ... */` | Многострочная форма `//!`                      |

На практике наиболее часто используются `///` и `//!`.

````rust
/// Складывает два целых числа.
///
/// # Examples
///
/// ```
/// let result = add(2, 3);
/// assert_eq!(result, 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

Здесь блок кода после `# Examples` является не просто иллюстрацией. `rustdoc` воспринимает его как **documentation test**: код компилируется и, если это обычный doctest, выполняется.

Однако есть важный нюанс: документация выше предполагает, что `add` доступна в контексте crate. В реальном crate пользователю обычно нужен импорт:

````rust
/// Складывает два целых числа.
///
/// # Examples
///
/// ```
/// use my_crate::add;
///
/// let result = add(2, 3);
/// assert_eq!(result, 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

Именно такой вариант лучше использовать в публичной документации: пример должен показывать **реальный способ использования API**.

**Открыть пример в Rust Playground** — [пример использования `add`](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=fn%20add%28a%3A%20i32%2C%20b%3A%20i32%29%20-%3E%20i32%20%7B%0A%20%20%20%20a%20%2B%20b%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20result%20%3D%20add%282%2C%203%29%3B%0A%20%20%20%20assert_eq%21%28result%2C%205%29%3B%0A%20%20%20%20println%21%28%22%7Bresult%7D%22%29%3B%0A%7D)

## 50.2. Запуск документационных тестов

Documentation tests запускаются вместе с обычными тестами:

```bash
# Все тесты, включая documentation tests
cargo test

# Только documentation tests
cargo test --doc
```

Например, если crate содержит:

````rust
/// Складывает два числа.
///
/// # Examples
///
/// ```
/// use my_crate::add;
///
/// assert_eq!(add(2, 3), 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

команда:

```bash
cargo test --doc
```

создаст тест из примера, скомпилирует его и выполнит.

Типичный вывод выглядит примерно так:

```text
running 1 test
test src/lib.rs - add (line 5) ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

Номер строки в выводе зависит от расположения документации в исходном файле.

Можно использовать фильтр:

```bash
cargo test --doc add
```

В этом случае `rustdoc` будет запускать documentation tests, соответствующие указанному фильтру.

**Важно:** documentation tests относятся к тестированию документации crate. Поэтому `cargo test` является особенно полезной командой перед публикацией библиотеки: она проверяет не только обычные unit/integration tests, но и примеры, которые увидит пользователь.

## 50.3. Написание документационных тестов

Рассмотрим полноценный пример:

````rust
/// Вычисляет факториал числа.
///
/// # Examples
///
/// ```
/// use my_crate::factorial;
///
/// assert_eq!(factorial(0), 1);
/// assert_eq!(factorial(1), 1);
/// assert_eq!(factorial(5), 120);
/// ```
pub fn factorial(n: u64) -> u64 {
    match n {
        0 | 1 => 1,
        _ => n * factorial(n - 1),
    }
}
````

Здесь происходят две вещи одновременно:

1. пользователь получает пример использования `factorial`;
2. `cargo test` автоматически проверяет, что этот пример продолжает работать.

Если изменить реализацию так, что:

```rust
factorial(5)
```

начнёт возвращать неправильный результат, documentation test также завершится ошибкой.

Это делает документацию **частью тестируемого контракта API**.

### Что происходит с кодом внутри блока?

Обычный блок:

````markdown
```rust
use my_crate::factorial;

assert_eq!(factorial(5), 120);
```
````

не является отдельной программой с собственным `main`. `rustdoc` создаёт тестовую программу и помещает код примера в неё.

Поэтому пользователь документации обычно может писать пример так, как он будет выглядеть при обычном использовании API:

```rust
use my_crate::factorial;

assert_eq!(factorial(5), 120);
```

а не:

```rust
fn main() {
    let result = factorial(5);
    assert_eq!(result, 120);
}
```

Обе формы возможны, но первая обычно лучше читается в документации.

## 50.4. Секции в документации

В `rustdoc` принято использовать стандартные секции, описывающие контракт API:

| Секция        | Назначение                                                       |
| ------------- | ---------------------------------------------------------------- |
| `# Examples`  | Примеры использования                                            |
| `# Panics`    | Условия, при которых функция паникует                            |
| `# Errors`    | Ошибки, возвращаемые через `Result`                              |
| `# Safety`    | Требования безопасности для `unsafe` API                         |
| `# Arguments` | Описание аргументов, если это действительно помогает             |
| `# Returns`   | Описание возвращаемого значения, если это действительно помогает |

Заголовок `# Remarks` также можно использовать, но это **обычный заголовок Markdown**, а не специальная секция `rustdoc`.

Например:

````rust
/// Делит одно число на другое.
///
/// # Panics
///
/// Паникует, если делитель равен нулю.
///
/// # Examples
///
/// ```
/// use my_crate::divide;
///
/// assert_eq!(divide(10, 2), 5);
/// ```
pub fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("Division by zero");
    }

    a / b
}
````

Секция `# Panics` является частью **контракта функции**. Если функция действительно может паниковать при определённом условии, это следует явно документировать.

Для функции, возвращающей `Result`, вместо `# Panics` обычно используется `# Errors`:

````rust
/// Делит одно число на другое.
///
/// # Errors
///
/// Возвращает ошибку, если делитель равен нулю.
///
/// # Examples
///
/// ```
/// use my_crate::divide;
///
/// assert_eq!(divide(10, 2).unwrap(), 5);
/// assert!(divide(10, 0).is_err());
/// ```
pub fn divide(a: i32, b: i32) -> Result<i32, &'static str> {
    if b == 0 {
        Err("division by zero")
    } else {
        Ok(a / b)
    }
}
````

Для `unsafe fn` секция `# Safety` особенно важна:

````rust
/// Возвращает значение по указателю.
///
/// # Safety
///
/// Указатель `ptr` должен быть ненулевым и указывать
/// на корректно инициализированное значение `i32`.
///
/// # Examples
///
/// ```
/// let value = 42;
/// let ptr = &value as *const i32;
///
/// // Требования безопасности здесь выполнены.
/// let result = unsafe { read_value(ptr) };
/// assert_eq!(result, 42);
/// ```
pub unsafe fn read_value(ptr: *const i32) -> i32 {
    unsafe { *ptr }
}
````

## 50.5. Документирование модулей: `//!`

`//!` используется для документации **самого модуля**, а не следующего элемента.

Для документации всего crate обычно `//!` размещают в начале `src/lib.rs`:

````rust
//! # My Crate
//!
//! Библиотека для выполнения базовых математических операций.
//!
//! ## Возможности
//!
//! - сложение;
//! - вычитание;
//! - умножение;
//! - деление.
//!
//! # Examples
//!
//! ```
//! use my_crate::add;
//!
//! assert_eq!(add(2, 3), 5);
//! ```

/// Складывает два числа.
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

/// Вычитает одно число из другого.
pub fn subtract(a: i32, b: i32) -> i32 {
    a - b
}
````

Это особенно полезно для crate-level documentation: пользователь, открыв документацию crate, сразу получает описание назначения библиотеки, её возможностей и базового способа использования.

`//!` можно применять и внутри обычного модуля:

```rust
mod math {
    //! Математические операции.

    pub fn add(a: i32, b: i32) -> i32 {
        a + b
    }
}
```

## 50.6. Ссылки на другие элементы

`rustdoc` умеет создавать ссылки на другие элементы API.

Для этого используется Markdown-синтаксис:

```rust
/// Складывает два числа.
///
/// См. также [`subtract`], [`multiply`] и [`divide`].
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

pub fn subtract(a: i32, b: i32) -> i32 {
    a - b
}

pub fn multiply(a: i32, b: i32) -> i32 {
    a * b
}

pub fn divide(a: i32, b: i32) -> i32 {
    a / b
}
```

В сгенерированной документации `rustdoc` постарается превратить такие ссылки в ссылки на соответствующие элементы API.

Можно использовать и полные пути:

```rust
/// См. [`std::collections::HashMap`].
pub fn create_map() {}
```

Это особенно полезно, когда имя неоднозначно или элемент находится в другом модуле:

```rust
/// Создаёт новый калькулятор.
///
/// См. [`crate::calculator::Calculator`].
pub fn create_calculator() {}
```

### Ссылки с другим отображаемым текстом

Можно отделить текст ссылки от пути:

```rust
/// Используйте [`Calculator`](crate::calculator::Calculator)
/// для выполнения вычислений.
pub fn create_calculator() {}
```

Так документация остаётся естественной для чтения, а `rustdoc` знает, на какой элемент API должна вести ссылка.

**Открыть пример в Rust Playground** — [пример ссылок на элементы API](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=mod%20calculator%20%7B%0A%20%20%20%20pub%20struct%20Calculator%3B%0A%7D%0A%0A%2F%2F%2F%20Creates%20a%20new%20calculator.%0A%2F%2F%2F%0A%2F%2F%2F%20See%20%5B%60Calculator%60%5D%28calculator%3A%3ACalculator%29.%0Afn%20create_calculator%28%29%20-%3E%20calculator%3A%3ACalculator%20%7B%0A%20%20%20%20calculator%3A%3ACalculator%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20_%20%3D%20create_calculator%28%29%3B%0A%7D)

## 50.7. Управление документационными тестами

Не каждый пример в документации должен запускаться. Для этого у блоков кода есть специальные атрибуты.

### `no_run`

`no_run` означает: **код должен успешно скомпилироваться, но запускаться не должен**.

Это полезно, например, когда пример запускает сервер или выполняет другую долгую операцию:

````rust
/// Запускает сервер.
///
/// ```no_run
/// use my_crate::Server;
///
/// let server = Server::new();
/// server.run();
/// ```
pub fn run_server() {}
````

`no_run` всё равно проверяет код компилятором. Поэтому ошибки типов, отсутствующие методы и другие ошибки компиляции будут обнаружены.

### `ignore`

`ignore` полностью исключает пример из обычного запуска documentation tests:

````rust
/// Пример требует внешнего сервиса.
///
/// ```ignore
/// connect_to_production_database();
/// ```
pub fn connect() {}
````

Игнорируемые примеры можно запустить отдельно:

```bash
cargo test --doc -- --ignored
```

### `compile_fail`

`compile_fail` означает, что пример **должен завершиться ошибкой компиляции**:

````rust
/// Нельзя присвоить строку переменной типа `i32`.
///
/// ```compile_fail
/// let value: i32 = "hello";
/// ```
pub fn example() {}
````

Такой тест считается успешным, если приведённый код действительно не компилируется.

Это особенно полезно для документации, объясняющей ограничения системы типов Rust.

### `should_panic`

`should_panic` означает, что пример должен успешно скомпилироваться, а во время выполнения должен завершиться паникой:

````rust
/// Деление на ноль вызывает панику.
///
/// ```should_panic
/// use my_crate::divide;
///
/// divide(10, 0);
/// ```
pub fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        panic!("division by zero");
    }

    a / b
}
````

Можно дополнительно проверить текст паники:

````rust
/// ```should_panic(expected = "division by zero")
/// use my_crate::divide;
///
/// divide(10, 0);
/// ```
````

### Комбинирование атрибутов

Атрибуты можно комбинировать:

````rust
/// ```no_run,ignore
/// start_server();
/// ```
````

При этом `ignore` имеет практический смысл только как способ исключить пример из обычного запуска; `no_run` отдельно уже означает, что пример компилируется, но не выполняется.

## 50.8. Скрытые строки в документационных тестах

Иногда документационный тест требует дополнительного кода, который не хочется показывать пользователю.

Для этого используется специальный префикс `#`:

````rust
/// # Examples
///
/// ```
/// # fn helper() -> i32 {
/// #     42
/// # }
/// assert_eq!(helper(), 42);
/// ```
pub fn example() {}
````

Строки, начинающиеся с `#`, участвуют в тесте, но **не отображаются в итоговой документации как обычный код**.

Это очень полезный механизм. Например, можно скрыть подготовку данных:

````rust
/// # Examples
///
/// ```
/// # use my_crate::User;
/// # let user = User::new("Alice", 30);
/// assert_eq!(user.name(), "Alice");
/// ```
pub fn example() {}
````

Пользователь видит только существенную часть примера:

```rust
assert_eq!(user.name(), "Alice");
```

но documentation test при этом получает все необходимые объявления.

Это позволяет одновременно:

* сделать пример коротким;
* сохранить его полностью компилируемым;
* не перегружать документацию вспомогательным кодом.

### Когда нужен собственный `main`

Если пример сложный или использует `?`, можно написать обычный `main` и скрыть его:

````rust
/// # Examples
///
/// ```
/// # fn main() -> Result<(), Box<dyn std::error::Error>> {
/// let value = "42".parse::<u32>()?;
/// assert_eq!(value, 42);
/// # Ok(())
/// # }
/// ```
pub fn parse_number() {}
````

Здесь строки с `#` являются частью тестируемого кода, но не загромождают документацию.

**Открыть пример в Rust Playground** — [пример с `?` и скрытым `main`](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=fn%20parse_number%28%29%20-%3E%20Result%3Cu32%2C%20std%3A%3Anum%3A%3AParseIntError%3E%20%7B%0A%20%20%20%20%2242%22.parse%28%29%0A%7D%0A%0Afn%20main%28%29%20-%3E%20Result%3C%28%29%2C%20Box%3Cdyn%20std%3A%3Aerror%3A%3AError%3E%3E%20%7B%0A%20%20%20%20let%20value%20%3D%20parse_number%28%29%3F%3B%0A%20%20%20%20assert_eq%21%28value%2C%2042%29%3B%0A%20%20%20%20Ok%28%28%29%29%0A%7D)

## 50.9. Генерация документации

Для генерации HTML-документации используется:

```bash
cargo doc
```

Документация будет создана в:

```text
target/doc/
```

Чтобы после генерации автоматически открыть документацию:

```bash
cargo doc --open
```

Например:

```bash
cargo doc --open
```

сначала создаст документацию, а затем откроет страницу crate в браузере.

### Документация без зависимостей

По умолчанию Cargo может генерировать документацию и для зависимостей crate.

Если документация зависимостей не нужна, используйте:

```bash
cargo doc --no-deps
```

`--no-deps` означает именно **«не генерировать документацию зависимостей»**.

Это особенно удобно для библиотек с большим количеством зависимостей.

### Документация в release-профиле

Можно использовать release-профиль:

```bash
cargo doc --release
```

Это может быть полезно, если проект имеет конфигурацию документации, зависящую от профиля сборки.

## 50.10. Документация как часть API

Для библиотеки документация — это часть публичного API.

Публичный API состоит не только из имён функций и типов. Пользователю также необходимо понимать:

* что делает функция;
* какие аргументы она принимает;
* что возвращает;
* когда может вернуть ошибку;
* когда может запаниковать;
* какие ограничения существуют;
* как выглядит минимальный рабочий пример.

Например:

````rust
/// Конфигурация HTTP-сервера.
///
/// # Examples
///
/// ```
/// use my_crate::Config;
///
/// let config = Config::new("localhost", 8080);
///
/// assert_eq!(config.host(), "localhost");
/// assert_eq!(config.port(), 8080);
/// ```
pub struct Config {
    host: String,
    port: u16,
}

impl Config {
    pub fn new(host: &str, port: u16) -> Self {
        Self {
            host: host.to_string(),
            port,
        }
    }

    pub fn host(&self) -> &str {
        &self.host
    }

    pub fn port(&self) -> u16 {
        self.port
    }
}
````

Здесь documentation test проверяет не внутреннюю реализацию `Config`, а **пользовательский сценарий**:

```rust
let config = Config::new("localhost", 8080);
```

Если API изменится, например `Config::new()` будет принимать другие аргументы, documentation test может сразу обнаружить несовместимость.

Поэтому для публичного crate полезно воспринимать документацию как **исполняемую спецификацию примеров использования API**.

**Открыть пример в Rust Playground** — [пример `Config`](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=pub%20struct%20Config%20%7B%0A%20%20%20%20host%3A%20String%2C%0A%20%20%20%20port%3A%20u16%2C%0A%7D%0A%0Aimpl%20Config%20%7B%0A%20%20%20%20pub%20fn%20new%28host%3A%20%26str%2C%20port%3A%20u16%29%20-%3E%20Self%20%7B%0A%20%20%20%20%20%20%20%20Self%20%7B%0A%20%20%20%20%20%20%20%20%20%20%20%20host%3A%20host.to_string%28%29%2C%0A%20%20%20%20%20%20%20%20%20%20%20%20port%2C%0A%20%20%20%20%20%20%20%20%7D%0A%20%20%20%20%7D%0A%0A%20%20%20%20pub%20fn%20host%28%26self%29%20-%3E%20%26str%20%7B%0A%20%20%20%20%20%20%20%20%26self.host%0A%20%20%20%20%7D%0A%0A%20%20%20%20pub%20fn%20port%28%26self%29%20-%3E%20u16%20%7B%0A%20%20%20%20%20%20%20%20self.port%0A%20%20%20%20%7D%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20config%20%3D%20Config%3A%3Anew%28%22localhost%22%2C%208080%29%3B%0A%20%20%20%20assert_eq%21%28config.host%28%29%2C%20%22localhost%22%29%3B%0A%20%20%20%20assert_eq%21%28config.port%28%29%2C%208080%29%3B%0A%7D)

## 50.11. Интеграционные тесты и documentation tests

Documentation tests занимают особое положение между обычными unit и integration tests.

Рассмотрим библиотеку:

```text
my_project/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

В `src/lib.rs`:

````rust
/// Складывает два числа.
///
/// # Examples
///
/// ```
/// use my_project::add;
///
/// assert_eq!(add(2, 3), 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

В `tests/integration_test.rs`:

```rust
use my_project::add;

#[test]
fn add_works() {
    assert_eq!(add(2, 3), 5);
}
```

Получается два разных уровня проверки одного API:

**Documentation test:**

```rust
use my_project::add;

assert_eq!(add(2, 3), 5);
```

проверяет, что пример из документации работает.

**Integration test:**

```rust
use my_project::add;

assert_eq!(add(2, 3), 5);
```

проверяет API независимо от текста документации.

Это не обязательно означает, что каждый сценарий нужно дублировать. Практический подход:

* documentation tests — для **коротких примеров использования API**;
* unit tests — для детальной проверки внутренней логики;
* integration tests — для **ключевых пользовательских сценариев и взаимодействия компонентов**.

## 50.12. Документационные тесты для бинарных crate

Здесь важно различать **library target** и **binary target**.

Если package содержит только:

```text
src/
└── main.rs
```

то его бинарный target нельзя импортировать в integration test или documentation test как библиотеку:

```rust
use my_app::some_function;
```

не сработает только потому, что существует `src/main.rs`.

Поэтому распространённая архитектура приложения выглядит так:

```text
my_app/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   └── main.rs
└── tests/
    └── integration_test.rs
```

Общую логику помещают в `lib.rs`:

````rust
// src/lib.rs

/// Возвращает приветствие.
///
/// # Examples
///
/// ```
/// use my_app::greeting;
///
/// assert_eq!(greeting("Alice"), "Hello, Alice!");
/// ```
pub fn greeting(name: &str) -> String {
    format!("Hello, {name}!")
}
````

А `main.rs` становится тонким слоем:

```rust
// src/main.rs

fn main() {
    println!("{}", my_app::greeting("World"));
}
```

Так библиотечная логика получает полноценный публичный API, который можно проверять unit tests, integration tests и documentation tests.

Если же необходимо протестировать именно запуск бинарного файла, integration test может запускать собранный binary target через переменную окружения `CARGO_BIN_EXE_<name>`:

```rust
use std::process::Command;

#[test]
fn application_starts() {
    let output = Command::new(env!("CARGO_BIN_EXE_my_app"))
        .output()
        .expect("failed to run application");

    assert!(output.status.success());
}
```

Это уже тестирование **самого исполняемого приложения**, а не импортирование его как библиотеки.

## 🔨 Эксперименты с компилятором

### Эксперимент 1: Documentation test с ошибкой

````rust
/// # Examples
///
/// ```
/// assert_eq!(2 + 2, 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

Запустите:

```bash
cargo test --doc
```

Результат — documentation test будет провален, потому что assertion завершится паникой.

---

### Эксперимент 2: Ошибка компиляции

````rust
/// # Examples
///
/// ```
/// let value: i32 = "hello";
/// ```
pub fn example() {}
````

Здесь проблема возникает ещё до выполнения теста: пример не компилируется.

Попробуйте заменить блок на:

````rust
/// ```compile_fail
/// let value: i32 = "hello";
/// ```
````

Теперь ожидаемая ошибка компиляции становится **условием успешного теста**.

---

### Эксперимент 3: `no_run`

````rust
/// ```no_run
/// let _server = std::net::TcpListener::bind("127.0.0.1:8080").unwrap();
/// ```
pub fn server_example() {}
````

Проверяется компиляция примера, но он не запускается.

Это принципиально отличается от `ignore`: `no_run` продолжает проверять пример компилятором.

---

### Эксперимент 4: Скрытые строки

````rust
/// # Examples
///
/// ```
/// # let value = 42;
/// assert_eq!(value, 42);
/// ```
pub fn example() {}
````

Строка:

```rust
# let value = 42;
```

не показывается как обычная строка примера, но участвует в тесте.

## Главное из этой главы

После этой главы мы понимаем:

* **`///`** — документация следующего элемента.
* **`//!`** — документация модуля или всего crate.
* **Documentation tests** — кодовые примеры, которые `rustdoc` автоматически компилирует и запускает.
* **`cargo test --doc`** — запуск documentation tests.
* **`# Examples`** — стандартная секция для рабочих примеров API.
* **`# Panics`** — описание условий паники.
* **`# Errors`** — описание ошибок, возвращаемых через `Result`.
* **`# Safety`** — описание требований безопасности `unsafe` API.
* **`no_run`** — компилировать, но не запускать пример.
* **`ignore`** — временно исключить пример из обычного запуска.
* **`compile_fail`** — проверить, что пример не компилируется.
* **`should_panic`** — проверить, что пример завершается паникой.
* **`#` в начале строки** — скрыть вспомогательный код из отображаемой документации.
* **rustdoc-ссылки** — связывать документацию с другими элементами API.
* **`cargo doc --open`** — генерировать и открывать HTML-документацию.
* **`cargo doc --no-deps`** — генерировать документацию без документации зависимостей.

**Самая важная идея:**

> Документация в Rust может быть исполняемой частью API. Пример, который пользователь видит в документации, может одновременно быть тестом, проверяемым компилятором и выполняемым автоматически. Поэтому хорошая документация — это не просто описание того, как код *должен* работать. Это проверяемый пример того, как API *действительно* используется.
>
> Для качественного Rust crate полезно рассматривать documentation tests как отдельный уровень тестирования: **unit tests проверяют реализацию, integration tests проверяют взаимодействие и публичный API, а documentation tests проверяют реальные примеры использования API**.
