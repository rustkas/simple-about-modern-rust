# Глава 52. Benchmarks и производительность

Rust славится своей производительностью. Но "быстрый язык" не означает, что любой код на нём будет быстрым. Чтобы писать эффективные программы, нужно понимать, как измерять производительность, где искать узкие места и как Rust компилирует код.

В этой главе мы разберёмся с инструментами и подходами к бенчмаркингу, профилированию и оптимизации в Rust.

Все примеры этой главы используют **Rust Edition 2024**.

---

## 52.1. Debug vs Release

В Rust основными профилями сборки являются **`dev`** и **`release`**. По умолчанию `cargo build` и `cargo run` используют `dev`, а `cargo build --release` и `cargo run --release` — `release`.

| Режим         | Команда                 | Оптимизация | Основное назначение             |
| ------------- | ----------------------- | ----------- | ------------------------------- |
| **`dev`**     | `cargo build`           | Низкая      | Разработка и отладка            |
| **`release`** | `cargo build --release` | Высокая     | Производительность и production |

В `dev` компилятор старается быстрее собирать программу и сохранять удобную для отладки структуру кода. В `release` компилятор тратит больше времени на оптимизацию результирующего машинного кода.

Например:

```rust
use std::hint::black_box;
use std::time::Instant;

fn main() {
    let start = Instant::now();

    let mut sum = 0u64;

    for i in 0..100_000_000 {
        sum = sum.wrapping_add(black_box(i));
    }

    let elapsed = start.elapsed();

    println!("sum = {sum}");
    println!("elapsed = {elapsed:?}");
}
```

Запустить программу можно так:

```bash
cargo run
```

и затем:

```bash
cargo run --release
```

Время выполнения в этих двух режимах может отличаться очень существенно. **Конкретные значения времени нельзя считать частью результата эксперимента**: они зависят от процессора, операционной системы, температуры, фоновых процессов и настроек компилятора.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=release&edition=2024&code=use%20std%3A%3Ahint%3A%3Ablack_box%3B%0Ause%20std%3A%3Atime%3A%3AInstant%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20start%20%3D%20Instant%3A%3Anow%28%29%3B%0A%20%20%20%20let%20mut%20sum%20%3D%200u64%3B%0A%0A%20%20%20%20for%20i%20in%200..100_000_000%20%7B%0A%20%20%20%20%20%20%20%20sum%20%3D%20sum.wrapping_add%28black_box%28i%29%29%3B%0A%20%20%20%20%7D%0A%0A%20%20%20%20let%20elapsed%20%3D%20start.elapsed%28%29%3B%0A%0A%20%20%20%20println%21%28%22sum%20%3D%20%7Bsum%7D%22%29%3B%0A%20%20%20%20println%21%28%22elapsed%20%3D%20%7Belapsed%3A%3F%7D%22%29%3B%0A%7D)

> **Важно:** производительность имеет смысл сравнивать в одинаковых условиях и, как правило, в `release`. Одного запуска недостаточно для серьёзного бенчмаркинга.

## 52.2. Измерение времени с `Instant`

Для простых экспериментов можно использовать `std::time::Instant`.

```rust
use std::hint::black_box;
use std::time::{Duration, Instant};

fn expensive_operation() -> u64 {
    (0..10_000_000)
        .map(black_box)
        .sum()
}

fn main() {
    let mut total = Duration::ZERO;
    let iterations = 10;

    for _ in 0..iterations {
        let start = Instant::now();

        let result = black_box(expensive_operation());

        let elapsed = start.elapsed();
        total += elapsed;

        println!("result = {result}, elapsed = {elapsed:?}");
    }

    println!("average = {:?}", total / iterations);
}
```

Здесь используется `std::hint::black_box`. Он сообщает компилятору, что значение следует рассматривать как неизвестное во время оптимизации. Это помогает избежать некоторых ситуаций, когда компилятор полностью устраняет вычисления, которые не влияют на результат программы.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=release&edition=2024&code=use%20std%3A%3Ahint%3A%3Ablack_box%3B%0Ause%20std%3A%3Atime%3A%3ADuration%3B%0A%0Afn%20expensive_operation%28%29%20-%3E%20u64%20%7B%0A%20%20%20%20%280..10_000_000%29.map%28black_box%29.sum%28%29%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20mut%20total%20%3D%20Duration%3A%3AZERO%3B%0A%20%20%20%20let%20iterations%20%3D%2010%3B%0A%0A%20%20%20%20for%20_%20in%200..iterations%20%7B%0A%20%20%20%20%20%20%20%20let%20start%20%3D%20std%3A%3Atime%3A%3AInstant%3A%3Anow%28%29%3B%0A%20%20%20%20%20%20%20%20let%20result%20%3D%20black_box%28expensive_operation%28%29%29%3B%0A%20%20%20%20%20%20%20%20let%20elapsed%20%3D%20start.elapsed%28%29%3B%0A%20%20%20%20%20%20%20%20total%20%2B%3D%20elapsed%3B%0A%20%20%20%20%20%20%20%20println%21%28%22result%20%3D%20%7Bresult%7D%2C%20elapsed%20%3D%20%7Belapsed%3A%3F%7D%22%29%3B%0A%20%20%20%20%7D%0A%0A%20%20%20%20println%21%28%22average%20%3D%20%7B%3A%3F%7D%22%2C%20total%20%2F%20iterations%29%3B%0A%7D)

Такой подход удобен для **быстрой оценки**, но это ещё не полноценный benchmark. На результат влияют:

* другие процессы операционной системы;
* состояние CPU и частота процессора;
* кэш процессора;
* аллокатор;
* прогрев кода;
* оптимизации компилятора;
* порядок и количество измерений.

Для серьёзного сравнения производительности лучше использовать специализированный benchmark framework.

## 52.3. Встроенный `#[bench]`: nightly-only механизм

В Rust существует встроенный механизм бенчмарков на основе `#[bench]`:

```rust
#![feature(test)]

extern crate test;

#[bench]
fn bench_sum(b: &mut test::Bencher) {
    b.iter(|| {
        (0..10_000).sum::<u64>()
    });
}
```

Он требует **nightly Rust** и нестабильного API `test`.

Поэтому для нового проекта этот механизм обычно **не является рекомендуемым выбором**. Современный практический подход — использовать внешний benchmark framework, например Criterion.

Это важное различие:

* `#[test]` — стабильный механизм тестирования;
* `#[bench]` — nightly-only механизм бенчмаркинга;
* Criterion — внешний framework для полноценного статистического бенчмаркинга.

## 52.4. Criterion — полноценный бенчмаркинг

**Criterion** — популярный framework для статистически более надёжных benchmark-измерений в Rust.

Он выполняет серию измерений, анализирует распределение результатов и позволяет сравнивать производительность между запусками.

Структура проекта:

```text
my_project/
├── Cargo.toml
├── src/
│   └── lib.rs
└── benches/
    └── my_benchmark.rs
```

### `Cargo.toml`

```toml
[package]
name = "my_project"
version = "0.1.0"
edition = "2024"

[lib]
name = "my_project"

[dev-dependencies]
criterion = { version = "0.7", features = ["html_reports"] }

[[bench]]
name = "my_benchmark"
harness = false
```

### `src/lib.rs`

```rust
pub fn fibonacci(n: u64) -> u64 {
    match n {
        0 | 1 => n,
        _ => fibonacci(n - 1) + fibonacci(n - 2),
    }
}
```

### `benches/my_benchmark.rs`

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use my_project::fibonacci;

fn bench_fibonacci(c: &mut Criterion) {
    c.bench_function("fibonacci 20", |b| {
        b.iter(|| fibonacci(black_box(20)));
    });
}

criterion_group!(benches, bench_fibonacci);
criterion_main!(benches);
```

Запуск:

```bash
cargo bench
```

Criterion выполнит множество измерений вместо одного `Instant::now()` и позволит увидеть статистически значимое изменение производительности.

`black_box` здесь нужен для того же общего принципа: benchmark не должен становиться измерением оптимизированного «ничего».

Criterion также создаёт HTML-отчёты, если включена соответствующая возможность.

> **Важно:** benchmark следует измерять на реальной целевой платформе. Результат Rust Playground не является заменой измерения на вашем production hardware.

## 52.5. Профилирование

Бенчмарк отвечает на вопрос:

> **«Насколько быстро работает этот код?»**

Профилирование отвечает на другой вопрос:

> **«Где именно программа проводит время?»**

Одним из популярных инструментов является **flamegraph** — визуализация стека вызовов.

Для Linux/macOS можно использовать `cargo-flamegraph`:

```bash
cargo install flamegraph
```

Затем:

```bash
cargo flamegraph
```

Для запуска бинарного файла с аргументами:

```bash
cargo flamegraph --bin my_app -- arg1 arg2
```

На Linux `cargo-flamegraph` обычно использует `perf` в качестве источника данных.

Можно также работать с `perf` непосредственно:

```bash
cargo build --release

perf record --call-graph dwarf target/release/my_app
perf report
```

На Linux для этого могут потребоваться дополнительные права или настройка системы.

Типичный workflow:

```text
Программа
    │
    ▼
Профилировщик
    │
    ▼
Статистика вызовов
    │
    ▼
Flamegraph
    │
    ▼
Самые дорогие функции
```

Например, если flamegraph показывает, что значительная часть времени уходит на:

```text
parse_request
    ├── decode_headers
    ├── parse_json
    └── allocate_string
```

то оптимизировать весь проект сразу не нужно. Сначала стоит исследовать именно наиболее дорогой участок.

## 52.6. Анализ аллокаций с `dhat`

Производительность — это не только CPU. Большое количество выделений памяти может существенно замедлить программу.

`dhat` позволяет анализировать выделения памяти во время выполнения.

### `Cargo.toml`

```toml
[dependencies]
dhat = "0.3"
```

### `src/main.rs`

```rust
#[global_allocator]
static ALLOC: dhat::Alloc = dhat::Alloc;

fn main() {
    let _profiler = dhat::Profiler::new_heap();

    let mut values = Vec::new();

    for i in 0..10_000 {
        values.push(i);
    }

    println!("values = {}", values.len());
}
```

Запуск:

```bash
cargo run --release
```

`dhat` собирает информацию о выделениях памяти и сообщает, сколько памяти было выделено, сколько блоков было создано и какой был пик использования.

При анализе аллокаций особенно полезно сравнивать варианты:

```rust
let mut values = Vec::new();

for i in 0..10_000 {
    values.push(i);
}
```

и:

```rust
let mut values = Vec::with_capacity(10_000);

for i in 0..10_000 {
    values.push(i);
}
```

Во втором варианте `Vec` заранее получает достаточную ёмкость, поэтому при заполнении ему обычно не требуется выполнять последовательные перевыделения буфера.

> Это не означает, что `with_capacity` всегда быстрее. Если фактический размер данных неизвестен или существенно меньше ожидаемого, предварительное выделение большого буфера может, наоборот, быть невыгодным. Это снова задача для измерения.

## 52.7. Профили сборки и оптимизации компилятора

Компилятор Rust выполняет множество оптимизаций, среди которых:

1. **Инлайнинг** — встраивание вызовов функций.
2. **Удаление мёртвого кода** — удаление вычислений, результаты которых не используются.
3. **Оптимизация циклов**.
4. **Мономорфизация** generic-кода.
5. **LTO** — оптимизация на этапе линковки.
6. **Удаление избыточных промежуточных вычислений**.

Настройки профиля можно изменить в `Cargo.toml`:

```toml
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
panic = "abort"

[profile.dev]
opt-level = 0
debug = true
```

Здесь:

* `opt-level = 3` — высокий уровень оптимизации;
* `lto = "thin"` — Thin LTO, обычно более быстрый вариант LTO;
* `codegen-units = 1` может улучшить возможности оптимизации между частями программы, но обычно увеличивает время компиляции;
* `panic = "abort"` означает завершение процесса при panic без раскрутки стека.

`panic = "abort"` **не следует включать автоматически ради производительности**. Это изменение поведения программы и часть стратегии обработки ошибок.

Аналогично, `lto = true` не является универсальным «ускорителем». Оптимальный профиль зависит от конкретного приложения.

## 52.8. Zero-cost abstractions

Одна из фундаментальных идей Rust — **zero-cost abstractions**.

Идея заключается не в том, что любой высокоуровневый код обязательно превращается в абсолютно идентичный машинный код с ручной реализацией.

Идея в другом:

> Если абстракция не требует дополнительной работы во время выполнения, компилятор может устранить её стоимость.

Например:

```rust
fn sum_doubled(values: &[i32]) -> i32 {
    values
        .iter()
        .map(|x| x * 2)
        .sum()
}
```

может быть очень эффективным кодом после оптимизации.

Эквивалентная ручная реализация:

```rust
fn sum_doubled(values: &[i32]) -> i32 {
    let mut sum = 0;

    for x in values {
        sum += x * 2;
    }

    sum
}
```

Не следует утверждать, что компилятор **гарантированно** генерирует абсолютно одинаковые инструкции для любых таких вариантов. Реальный результат зависит от оптимизатора, target architecture, профиля сборки и конкретного кода.

Но сама модель итераторов Rust устроена так, чтобы композиция адаптеров не требовала обязательного runtime-объекта «итератор» или цепочки виртуальных вызовов.

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=release&edition=2024&code=fn%20sum_doubled%28values%3A%20%26%5Bi32%5D%29%20-%3E%20i32%20%7B%0A%20%20%20%20values.iter%28%29.map%28%7Cx%7C%20x%20%2A%202%29.sum%28%29%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20values%20%3D%20%5B1%2C%202%2C%203%2C%204%5D%3B%0A%20%20%20%20println%21%28%22%7B%7D%22%2C%20sum_doubled%28%26values%29%29%3B%0A%7D)

## 52.9. Поиск узких мест

Нельзя эффективно оптимизировать программу, не зная, **что именно является узким местом**.

Утверждение «80% времени выполняется в 20% кода» часто используется как практическая эвристика, но это **не универсальный закон**. В конкретной программе распределение времени может быть совершенно другим.

Надёжный процесс выглядит так:

1. **Измерьте** производительность.
2. **Профилируйте** программу.
3. **Найдите** горячий участок.
4. **Сформулируйте гипотезу**, почему он дорогой.
5. **Измените** код.
6. **Измерьте снова**.
7. Оставьте изменение только в том случае, если оно действительно улучшает нужную характеристику.

Например, рассмотрим построение строки:

```rust
fn build_message(name: &str, count: usize) -> String {
    let mut result = String::new();

    for _ in 0..count {
        result.push_str(name);
        result.push(' ');
    }

    result
}
```

Если заранее известен приблизительный размер результата, можно попробовать:

```rust
fn build_message(name: &str, count: usize) -> String {
    let mut result = String::with_capacity(
        name.len() * count + count
    );

    for _ in 0..count {
        result.push_str(name);
        result.push(' ');
    }

    result
}
```

Вторая версия может уменьшить количество перевыделений памяти.

Но это **гипотеза**, а не доказательство улучшения.

Нужно измерить обе версии:

```text
baseline
    │
    ▼
benchmark
    │
    ▼
optimization
    │
    ▼
benchmark again
    │
    ├── faster → keep
    │
    └── same/slower → reconsider
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=release&edition=2024&code=fn%20build_message%28name%3A%20%26str%2C%20count%3A%20usize%29%20-%3E%20String%20%7B%0A%20%20%20%20let%20mut%20result%20%3D%20String%3A%3Awith_capacity%28name.len%28%29%20%2A%20count%20%2B%20count%29%3B%0A%0A%20%20%20%20for%20_%20in%200..count%20%7B%0A%20%20%20%20%20%20%20%20result.push_str%28name%29%3B%0A%20%20%20%20%20%20%20%20result.push%28%27%20%27%29%3B%0A%20%20%20%20%7D%0A%0A%20%20%20%20result%0A%7D%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20println%21%28%22%7B%7D%22%2C%20build_message%28%22Rust%22%2C%203%29%29%3B%0A%7D)

## 52.10. Регрессии производительности

**Регрессия производительности** возникает, когда новая версия программы становится медленнее или начинает использовать больше памяти, CPU или других ресурсов.

Например:

```text
Commit A → 100 ms
Commit B → 102 ms
Commit C → 150 ms  ← регрессия
Commit D → 148 ms
```

Для обнаружения регрессий используются:

1. **Benchmark suites** — регулярно измеряют важные операции.
2. **Сравнение результатов** — с baseline или предыдущими измерениями.
3. **Профилирование** — помогает понять причину ухудшения.
4. **`git bisect`** — помогает найти коммит, после которого появилась проблема.

Criterion умеет сравнивать результаты benchmark-запусков и показывать статистически значимые изменения.

Однако:

> **`cargo bench` сам по себе не является системой CI-контроля регрессий.**

Простой шаг:

```yaml
- name: Run benchmarks
  run: cargo bench
```

запускает benchmark, но не означает автоматически:

> «Если программа стала на 5% медленнее — CI обязательно завершится ошибкой».

Для production CI необходимо отдельно определить, **какие изменения считаются регрессией**, с каким baseline сравнивать результаты и насколько результаты стабильны на CI-машине.

Практический процесс может выглядеть так:

```text
Pull Request
     │
     ▼
Build + Tests
     │
     ▼
Benchmark
     │
     ▼
Compare with baseline
     │
     ├── acceptable → merge
     │
     └── regression → investigate
```

Для критичных участков приложения benchmarks следует хранить как часть исходного кода проекта и запускать регулярно.

## 🔨 Эксперименты с компилятором

### Эксперимент 1: Debug vs Release

Создайте программу:

```rust
use std::hint::black_box;
use std::time::Instant;

fn main() {
    let start = Instant::now();

    let mut sum = 0u64;

    for i in 0..50_000_000 {
        sum = sum.wrapping_add(black_box(i));
    }

    println!("sum = {sum}");
    println!("time = {:?}", start.elapsed());
}
```

Запустите:

```bash
cargo run
```

затем:

```bash
cargo run --release
```

Сравните результаты.

**Вопрос:** почему разница между режимами может быть огромной?

---

### Эксперимент 2: Что произойдёт без `black_box`?

Сравните:

```rust
let mut sum = 0u64;

for i in 0..50_000_000 {
    sum = sum.wrapping_add(i);
}
```

с:

```rust
use std::hint::black_box;

let mut sum = 0u64;

for i in 0..50_000_000 {
    sum = sum.wrapping_add(black_box(i));
}
```

Попробуйте измерить обе версии в `release`.

Компилятор может обнаружить, что вычисление имеет свойства, позволяющие сильно его упростить или даже устранить.

`black_box` делает benchmark более устойчивым к таким оптимизациям, хотя **не превращает измерение в абсолютно изолированный эксперимент**.

---

### Эксперимент 3: `Vec::new()` vs `Vec::with_capacity()`

Сравните:

```rust
fn build() -> Vec<u64> {
    let mut values = Vec::new();

    for i in 0..100_000 {
        values.push(i);
    }

    values
}
```

и:

```rust
fn build() -> Vec<u64> {
    let mut values = Vec::with_capacity(100_000);

    for i in 0..100_000 {
        values.push(i);
    }

    values
}
```

Затем измерьте:

* время выполнения;
* количество аллокаций;
* пиковое использование памяти.

Важно не делать вывод только по одному запуску: иногда разница будет небольшой или вообще окажется статистически незначимой.

## Главное из этой главы

После этой главы мы понимаем:

* **`dev` и `release`** — разные профили сборки с существенно разными характеристиками производительности.
* **`Instant`** — простой инструмент для грубого измерения времени.
* **`std::hint::black_box`** — помогает защитить benchmark от некоторых нежелательных оптимизаций.
* **Criterion** — полноценный framework для статистического бенчмаркинга.
* **Профилирование** — позволяет найти реальные горячие участки программы.
* **Flamegraph** — удобный способ визуализировать распределение времени.
* **`dhat`** — инструмент для анализа выделений памяти.
* **Профили сборки** — позволяют управлять оптимизацией компилятора.
* **Zero-cost abstractions** — позволяют использовать высокоуровневые абстракции без обязательной дополнительной runtime-стоимости.
* **Оптимизация** начинается с измерения, а не с догадок.
* **Регрессии производительности** необходимо обнаруживать сравнением с baseline, а не субъективными ощущениями.

**Самая важная идея:**

> **Не оптимизируйте то, что вы не измерили.**
>
> Правильный процесс выглядит так:
>
> **измерить → найти узкое место → сформулировать гипотезу → изменить код → снова измерить.**
>
> Rust предоставляет мощные инструменты для каждого этапа: `cargo build --release`, `Instant`, `black_box`, Criterion, профилировщики и инструменты анализа памяти.
>
> Производительность — это не свойство языка, которое автоматически получает любая программа на Rust. Это свойство конкретной реализации, которое необходимо **измерять, понимать и подтверждать экспериментом**.
