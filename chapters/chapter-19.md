## 19.1. Типы выражают ограничения

В Rust типы — это не просто способ хранить данные. Это **способ описать, какие значения допустимы, а какие — нет**.

**Пример:** `Option<T>`

```rust
fn divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 {
        None
    } else {
        Some(a / b)
    }
}
```

Тип `Option<f64>` говорит: «результат может быть, а может и не быть». Компилятор заставляет нас обрабатывать оба случая. Мы не можем просто использовать результат, как будто он всегда существует.

**Пример:** `Result<T, E>`

```rust
fn parse_number(s: &str) -> Result<i32, std::num::ParseIntError> {
    s.parse()
}
```

Тип `Result<i32, ParseIntError>` говорит: «результат либо успешен со значением, либо содержит ошибку». Компилятор заставляет нас обрабатывать оба случая.

**Главная идея:** типы делают недопустимые состояния **непредставимыми** в программе. Если тип не позволяет ошибку, ошибка не может произойти.

## 19.2. Типы выражают состояние

Перечисления позволяют описать **все возможные состояния** системы:

```rust
enum ConnectionState {
    Disconnected,
    Connecting,
    Connected { session_id: u32 },
    Failed { error: String },
}
```

**Что это даёт?**

1. **Ясность.** Любой, кто видит этот тип, знает все возможные состояния соединения.
2. **Безопасность.** Компилятор проверяет, что мы обрабатываем все состояния в `match`.
3. **Эволюционность.** Если мы добавим новое состояние, компилятор укажет все места, где его нужно обработать.

**Главная идея:** Типы описывают не только данные, но и **жизненный цикл** этих данных. Состояния, которые не описаны в типе, не могут существовать в программе.

## 19.3. Ownership выражает ответственность

Владение — это не просто технический механизм управления памятью. Это способ выразить **ответственность** за ресурс.

```rust
fn read_file() -> std::io::Result<()> {
    let file = std::fs::File::open("data.txt")?;
    // file владеет файлом
    // Когда file выходит из области видимости, файл закрывается
    Ok(())
}
```

*(Здесь и далее в этой главе фрагменты кода иллюстративны и приводятся без ссылок на Rust Playground — эта глава не вводит новых технических конструкций, а обобщает уже изученное. `File` и работу с файловой системой мы подробно рассмотрим позже, во второй части книги.)*

**Кто отвечает за ресурс?**
- Владелец отвечает за **освобождение** ресурса.
- Владелец отвечает за **валидность** данных.
- Владелец определяет **время жизни** ресурса.

**Главная идея:** Ownership делает ответственность явной. Вы всегда знаете, кто отвечает за каждый ресурс в программе.

---

## 19.4. Borrowing выражает доступ

Если владение выражает ответственность, то заимствование выражает **доступ**.

```rust
fn process_data(data: &Data) {
    // У меня есть доступ к данным, но я не отвечаю за них
    // Я не могу их уничтожить или изменить (если это &mut)
}
```

**Типы доступа:**
- `&T` — доступ на чтение.
- `&mut T` — доступ на чтение и запись.
- Нет доступа — владелец может делать всё, что хочет.

**Главная идея:** Borrowing разделяет ответственность и доступ. Многие части программы могут читать данные, но только одна может их изменять (или владеть ими).

## 19.5. Traits выражают возможности

Трейты описывают, **что умеет делать** тип.

```rust
trait Summary {
    fn summarize(&self) -> String;
}

impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{} by {}", self.headline, self.author)
    }
}
```

**Трейты как контракты:**
- Если тип реализует трейт, он гарантирует определённое поведение.
- Обобщённый код может полагаться на это поведение.

```rust
fn print_summary<T: Summary>(item: &T) {
    println!("{}", item.summarize());
}
```

**Главная идея:** Трейты отделяют **что** делает тип от **как** он это делает. Это позволяет писать универсальный код, который работает с любым типом, обладающим нужным поведением.

---

## 19.6. Generics выражают универсальность

Обобщения позволяют писать код, который работает с **множеством типов**.

```rust
fn identity<T>(value: T) -> T {
    value
}
```

**Что это даёт?**
- Один алгоритм — много типов.
- Статическая типизация — типы проверяются во время компиляции.
- Безопасность — код работает одинаково для всех типов.

**Главная идея:** Обобщения позволяют абстрагироваться от конкретного типа, сохраняя при этом полную безопасность типов.

---

## 19.7. Compiler проверяет инварианты

Компилятор Rust — это не просто программа, которая превращает код в исполняемый файл. Это **инструмент проверки корректности**.

```text
Типы           → проверяют, что операции допустимы
Ownership      → проверяет, что ресурсы освобождаются
Borrowing      → проверяет, что нет гонок данных
Lifetimes      → проверяет, что ссылки действительны
Traits         → проверяет, что типы реализуют нужное поведение
```

**Компилятор проверяет инварианты:**
- Нет висячих ссылок.
- Нет двойного освобождения.
- Нет гонок данных.
- Все возможные состояния обработаны.
- Все типы согласованы.

**Главная идея:** Компилятор — ваш партнёр. Он не враг, который мешает писать код. Он помощник, который гарантирует, что код корректен.

## 19.8. Zero-cost abstractions

Одна из самых мощных идей Rust: **выразительный код не обязан быть медленным**.

```rust
// Итераторная версия
let sum: i32 = numbers.iter().map(|x| x * 2).filter(|x| x % 2 == 0).sum();

// Ручной цикл
let mut sum = 0;
for x in &numbers {
    let doubled = x * 2;
    if doubled % 2 == 0 {
        sum += doubled;
    }
}
```

**Что такое zero-cost abstraction?**
- Абстракция не добавляет накладных расходов во время выполнения.
- Компилятор оптимизирует код так же хорошо, как и ручной цикл.
- Вы получаете выразительность без потери производительности.

**Главная идея:** В Rust вы можете использовать мощные абстракции (итераторы, трейты, замыкания) без страха, что это замедлит программу.

## 19.9. Type-driven design

Теперь мы можем сформулировать главный принцип проектирования на Rust:

> **Начинайте проектирование не с функций, а с типов.**

**Вместо того чтобы спрашивать:**
> «Какие функции мне нужны?»

**Спросите:**
> «Какие данные и состояния существуют в моей предметной области?»

**Пример: онлайн-заказ**

1. **Какие состояния?**
```rust
enum OrderStatus {
    Pending,
    Paid,
    Shipped,
    Delivered,
    Cancelled,
}
```

2. **Какие данные?**
```rust
struct Order {
    id: u32,
    status: OrderStatus,
    items: Vec<OrderItem>,
    total: f64,
}
```

3. **Какие операции допустимы для каждого состояния?**
- Только заказ в статусе `Pending` можно отменить.
- Только заказ в статусе `Paid` можно отправить.

4. **Как типы могут гарантировать эти ограничения?**
- Используем `enum` для состояний.
- Используем `Option` для необязательных данных.
- Используем методы, которые принимают только допустимые состояния.

**Главная идея:** когда типы правильно отражают предметную область, многие ошибки становятся **невозможными** по определению типа.

## 19.10. Что теперь мы понимаем

После 19 глав мы понимаем не просто синтаксис Rust. Мы понимаем **модель мышления**, которая стоит за ним.

| Концепция | Что выражает |
|---|---|
| **Типы** | Ограничения и состояния |
| **Ownership** | Ответственность за ресурсы |
| **Borrowing** | Доступ к ресурсам |
| **Lifetimes** | Действительность ссылок |
| **Traits** | Возможности и поведение |
| **Generics** | Универсальность алгоритмов |
| **Compiler** | Проверку инвариантов |
| **Zero-cost** | Выразительность без потери производительности |
| **Type-driven design** | Проектирование через типы |

## 19.11. Главная мысль главы

До этой главы мы изучали отдельные возможности Rust.

Теперь мы можем увидеть, что они не являются независимым набором конструкций.

```text
Types
  ↓
Ownership
  ↓
Borrowing
  ↓
Lifetimes
  ↓
Traits
  ↓
Generics
  ↓
Compiler
  ↓
Zero-cost abstractions
  ↓

```

**Всё это — единая система.**

Именно эта система определяет то, как Rust позволяет нам описывать программы и одновременно проверять их корректность ещё до запуска.

Это не просто язык программирования. Это способ мышления о программах.
