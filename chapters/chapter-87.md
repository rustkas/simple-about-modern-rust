# Глава 87. Что пока не стало stable

Rust развивается быстро, но не всё, что есть в nightly, становится stable сразу. Некоторые функции остаются экспериментальными годами, другие меняются или отбрасываются.

В этой главе мы разберёмся, как работает процесс стабилизации в Rust, какие функции пока остаются на nightly, как оценивать экспериментальные возможности и почему не стоит использовать их без необходимости.

## 87.2. Что такое nightly?

**Nightly** — это ежедневная сборка Rust, которая содержит все последние изменения.

```bash
# Установка nightly
rustup install nightly

# Использование nightly
rustup default nightly

```

**Что доступно в nightly:**

- Экспериментальные функции (`feature gates`).
- Нестабильные API.
- Изменения, которые ещё не прошли полное тестирование.

---

## 87.3. Feature gates

**Feature gates** — это флаги, которые включают экспериментальные функции:

```rust
#![feature(async_closure)]
#![feature(generic_associated_types)]
#![feature(const_generics)]
#![feature(negative_impls)]

fn main() {
    // Использование экспериментальной функции
}

```

**Популярные feature gates:**

| Feature                    | Описание                  | Статус         |
| -------------------------- | ------------------------- | -------------- |
| `async_closure`            | Асинхронные замыкания     | В разработке   |
| `generic_associated_types` | GAT                       | Стабилизирован |
| `const_generics`           | Const generics            | Стабилизирован |
| `async_fn_in_trait`        | Async функции в трейтах   | Стабилизирован |
| `negative_impls`           | Отрицательные реализации  | В разработке   |
| `specialization`           | Специализация трейтов     | В разработке   |
| `async_drop`               | Асинхронный `Drop`        | В разработке   |
| `fmt_internals`            | Внутреннее форматирование | Нестабильно    |

## 87.5. Почему не следует использовать nightly без причины

**Проблемы nightly:**

1. **Нестабильность API** — функции могут измениться без предупреждения.
2. **Ошибки компилятора** — nightly может содержать баги.
3. **Зависимости** — библиотеки могут не работать с nightly.
4. **Продуктовые проблемы** — нельзя выпустить production-приложение на nightly.
5. **Сложность отладки** — ошибки в nightly сложнее понять.

**Когда стоит использовать nightly:**

1. **Изучение** — чтобы попробовать новые функции.
2. **Тестирование** — чтобы проверить совместимость.
3. **Разработка библиотек** — чтобы подготовиться к новым возможностям.
4. **Эксперименты** — для исследования будущего языка.

## 87.6. Как оценить, когда использовать unstable feature

**Критерии:**

1. **Статус RFC** — принят ли RFC? Если нет, функция может исчезнуть.
2. **Tracking issue** — есть ли открытый issue для стабилизации? Чем активнее, тем ближе к стабилизации.
3. **Использование в экосистеме** — используют ли популярные библиотеки эту функцию?
4. **Альтернативы** — есть ли стабильный обходной путь?

**Пример: оценка `async_drop**`

| Критерий                      | Оценка                       |
| ----------------------------- | ---------------------------- |
| **RFC принят**                | ✅ Да                        |
| **Tracking issue активен**    | ✅ Да                        |
| **Используется в экосистеме** | ⚠️ Ограниченно               |
| **Альтернативы**              | ✅ Есть (явный `close()`)    |
| **Решение**                   | Не использовать в production |

## 87.9. Как переключиться на nightly

```bash
# Установка
rustup install nightly

# Переключение
rustup default nightly

# Проверка версии
rustc --version

# Сборка с nightly
cargo +nightly build

# Запуск тестов на nightly
cargo +nightly test

# Возврат на stable
rustup default stable

```

**`rust-toolchain.toml` для проекта:**

```toml
[toolchain]
channel = "nightly-2026-08-01"
components = ["rustfmt", "clippy"]
targets = ["wasm32-unknown-unknown"]

```

## 87.10. Пример: использование nightly функции

> _Примечание:_ Для запуска кода с нестабильными фичами обязательно требуется компилятор версии Nightly и явно активированный макрос фичи на уровне крейта.

```rust
// Требуется nightly компилятор и активная фича
#![feature(async_drop)]

struct AsyncResource {
    name: String,
}

impl AsyncDrop for AsyncResource {
    async fn drop(&mut self) {
        // Асинхронное освобождение ресурса (например, закрытие сетевого сокета)
        println!("Releasing async resource: {}", self.name);
    }
}

#[tokio::main]
async fn main() {
    let _resource = AsyncResource {
        name: "DatabaseConnection".to_string(),
    };

    // При выходе из области видимости срабатывает async drop (в рамках экспериментальной семантики)
    println!("Working with resource...");
}

```

## 87.11. Будущее стабилизации

**Ожидаемые в ближайшее время:**

1. **Async drop** — `async fn drop(&mut self)`
2. **Specialization** — частичная стабилизация
3. **Negative traits** — `impl !Send for MyType`
4. **Const traits** — трейты в const контексте

**Далеко:**

1. **Async closures** — синтаксис и семантика
2. **Full specialization** — сложный механизм
3. **Reflection** — низкоуровневая рефлексия

## Главное из этой главы

После этой главы мы понимаем:

- **Nightly** — экспериментальная версия Rust.
- **Feature gates** — включение экспериментальных функций.
- **Статусы** — stable, beta, nightly.
- **Почему не использовать nightly** — нестабильность, риски.
- **Как оценивать** — RFC, tracking issue, экосистема.
- **Ресурсы** — Rust Blog, This Week in Rust, tracking issues.

**Самая важная идея:**

> Nightly — это окно в будущее Rust, но не место для production-кода. Используйте его для экспериментов и изучения, но не для приложений, которые должны работать надёжно. Следите за tracking issues и RFC, чтобы понимать, когда функция станет stable. Большинство разработчиков могут использовать только stable — этого достаточно для 99% задач.
