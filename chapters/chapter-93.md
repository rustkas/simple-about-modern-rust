# Глава 93. Как поддерживать Rust-проект годами

Создать проект легко. Поддерживать его годами — сложно. Rust-проекты, особенно библиотеки, живут долго. За это время меняется язык, экосистема, появляются новые уязвимости, и требования к проекту эволюционируют.

В этой главе мы разберёмся, как поддерживать Rust-проект в здоровом состоянии на протяжении многих лет: обновлять зависимости, управлять изменениями, обеспечивать безопасность и сохранять совместимость.

### 93.1. Жизненный цикл Rust-проекта

```text
┌────────────────────────────────────────────────────────────────┐
│                   Жизненный цикл проекта                       │
├────────────────────────────────────────────────────────────────┤
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌──────────┐  │
│  │  Создание  │─▶│  Развитие  │─▶│  Зрелость  │─▶│ Поддер- │ │
│  │            │  │            │  │            │  │  жка     │  │

│        │               │               │               │       │
│        ▼               ▼               ▼               ▼       │
│    прототип        добавление      стабильный    долгосрочная  │
│    MVP             фич             API           поддержка     │
└────────────────────────────────────────────────────────────────┘

```

**Фазы:**

1. **Создание** — прототип, MVP.
2. **Развитие** — добавление функций, улучшение.
3. **Зрелость** — стабильный API, широкая аудитория.
4. **Поддержка** — долгосрочная стабильность, безопасность.

### 93.2. Обновление зависимостей

**Почему нужно обновлять:**

1. **Безопасность** — исправления уязвимостей.
2. **Стабильность** — исправления багов.
3. **Новые возможности** — новые функции.
4. **Совместимость** — с новой версией Rust.

**Инструменты для обновления:**

```bash
# Проверка устаревших зависимостей
cargo outdated

# Обновление всех зависимостей до последних совместимых версий
cargo update

# Обновление конкретной зависимости
cargo update serde

# Обновление до новых мажорных версий (с осторожностью)
cargo upgrade

```

**Стратегия обновления:**

1. **Регулярно** — раз в месяц/квартал.
2. **Постепенно** — обновляйте по одной зависимости.
3. **Тестируйте** — после каждого обновления.
4. **Фиксируйте** — обновляйте changelog.

---

### 93.3. Безопасность (Security)

**Уязвимости в зависимостях — главная угроза.**

```bash
# Проверка уязвимостей
cargo audit

# Еженедельный запуск в CI
cargo audit --ignore RUSTSEC-2024-0001

```

**Рекомендации:**

1. **Используйте `cargo audit**` регулярно.
2. **Подписывайтесь на уведомления** о уязвимостях.
3. **Обновляйте зависимости** с уязвимостями в первую очередь.
4. **Используйте `cargo deny**` для проверки лицензий и уязвимостей.

**`cargo deny`:**

```toml
# deny.toml
[advisories]
vulnerability = "deny"
unmaintained = "deny"
yanked = "deny"

[licenses]
unlicensed = "deny"
allow = ["MIT", "Apache-2.0", "BSD-3-Clause"]

```

### 93.4. Rust Editions

**Editions — это эволюция языка.**

```bash
# Проверка текущей Edition
cargo pkgid | grep edition

# Обновление до новой Edition
cargo fix --edition
cargo fix --edition-idioms

```

**Стратегия обновления Editions:**

1. **Дождитесь стабилизации** — не переходите на beta/nightly.
2. **Обновляйте постепенно** — сначала зависимости, потом код.
3. **Используйте `cargo fix**` — автоматическое исправление.
4. **Тестируйте** — после обновления.
5. **Обновляйте MSRV** — если требуется.

---

### 93.5. MSRV — Minimum Supported Rust Version

**MSRV — минимальная версия Rust, которую поддерживает ваш проект.**

```toml
[package]
rust-version = "1.85.0"

```

**Политика MSRV:**

1. **Укажите MSRV** в `Cargo.toml`.
2. **Документируйте MSRV** в README.
3. **Тестируйте MSRV** в CI.
4. **Обновляйте MSRV** только в минорных или мажорных релизах.

**Пример CI для MSRV:**

```yaml
jobs:
  test-msrv:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions-rs/toolchain@v1
        with:
          toolchain: 1.85.0
      - run: cargo test

```

### 93.6. Breaking Changes

**Breaking changes — несовместимые изменения API.**

**Как управлять:**

1. **Используйте SemVer** — мажорная версия для breaking changes.
2. **Документируйте** — в changelog и README.
3. **Предупреждайте** — используйте `#[deprecated]`.
4. **Предоставляйте миграционные пути** — как обновиться.

**`#[deprecated]`:**

```rust
#[deprecated(
    since = "2.0.0",
    note = "Use `new_method` instead"
)]
pub fn old_method() {
    // старая логика
}

#[deprecated(
    since = "2.0.0",
    note = "Use `Config::with_timeout` instead"
)]
pub fn set_timeout(_value: u64) {
    // установка таймаута
}

fn main() {
    println!("Демонстрация атрибута deprecated");
}

```

### 93.7. Deprecations

**Устаревание функций перед удалением.**

```rust
// v1.5.0 — объявление об устаревании старой функции
#[deprecated(since = "1.5.0", note = "Use `new_method` instead")]
pub fn legacy_operation() {
    new_method();
}

pub fn new_method() {
    println!("Выполнена новая операция");
}

fn main() {
    #[allow(deprecated)]
    legacy_operation();
}

```

**Процесс:**

1. **Объявите устаревшим** — с `#[deprecated]`.
2. **Подождите** — минимум один минорный релиз.
3. **Удалите** — в мажорном релизе.
4. **Документируйте** — в changelog.

### 93.8. Миграционные гайды

**Миграционные гайды — как пользователям перейти на новую версию.**

```markdown
# Migration Guide: v1.0.0 → v2.0.0

## Breaking Changes

### 1. `old_method()` removed

Use `new_method()` instead.

**Before:**
```rust
old_method();

```

**After:**

```rust
new_method();

```

### 2. `Config` fields renamed

`Config::host` → `Config::hostname`

**Before:**

```rust
let config = Config { host: "localhost" };

```

**After:**

```rust
let config = Config { hostname: "localhost" };

```

```

**Рекомендации:**

1. **Объясните каждое breaking change.**

2. **Покажите код до и после.**

3. **Дайте альтернативные пути.**

4. **Укажите, как исправить ошибки.**

### 93.9. Воспроизводимые сборки (Reproducible Builds)

**Воспроизводимость — возможность собрать один и тот же бинарник на разных машинах.**

**Инструменты:**

```bash
# Фиксация версий зависимостей
cargo update --verbose

# Использование Cargo.lock
cargo build --locked

# Проверка воспроизводимости
cargo build --release
diff <(sha256sum target/release/my_app) expected.sha256

```

**Рекомендации:**

1. **Храните `Cargo.lock**` в репозитории для приложений.
2. **Используйте `--locked**` в CI.
3. **Фиксируйте версии** всех инструментов.
4. **Используйте Docker** для воспроизводимых сборок.

### 93.10. Безопасность цепочки поставок (Supply-Chain Security)

**Угрозы:**

* Компрометация зависимостей.
* Вредоносные крейты.
* Несанкционированные изменения.

**Защита:**

1. **Аудит зависимостей** — `cargo audit`.
2. **Проверка лицензий** — `cargo deny`.
3. **Проверка источников** — проверяйте, откуда берутся крейты.
4. **Следите за обновлениями** — подписывайтесь на уведомления.
5. **Используйте `cargo vet**` — проверка безопасности зависимостей.

**`cargo vet`:**

```bash
cargo vet init
cargo vet check
cargo vet certify --all

```

**Инструменты для автоматизации:**

### Главное из этой главы

После этой главы мы понимаем:

* **Обновление зависимостей** — регулярно, с тестированием.
* **Безопасность** — `cargo audit`, `cargo deny`.
* **Rust Editions** — обновляйте с осторожностью.
* **MSRV** — минимальная версия, тестируйте в CI.
* **Breaking changes** — мажорные версии, миграционные гайды.
* **Deprecations** — предупреждайте до удаления.
* **Миграционные гайды** — помогают пользователям.
* **Воспроизводимые сборки** — `Cargo.lock`, `--locked`.
* **Supply-chain security** — `cargo vet`.

**Самая важная идея:**

> Поддержка проекта годами — это не рутина, а стратегия. Регулярные обновления, проверка безопасности, обновление Editions и чёткая политика версионирования делают проект надёжным и долгоживущим. Автоматизация (CI, Renovate, cargo-audit) помогает не упускать важные изменения. И главное — всегда думайте о пользователях: как им будет легко обновляться и использовать ваш проект в будущем.
