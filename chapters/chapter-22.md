# Глава 22. Interior Mutability

В предыдущих главах мы узнали, что Rust имеет строгие правила заимствования: либо несколько неизменяемых ссылок, либо одна изменяемая. Эти правила проверяются на этапе компиляции и гарантируют безопасность памяти.

Но что, если нам нужно изменить данные через **неизменяемую ссылку**? Это кажется невозможным — и в большинстве случаев так и есть. Однако Rust предоставляет механизм, который называется **внутренняя изменяемость (interior mutability)**.

Внутренняя изменяемость позволяет изменять данные даже при наличии неизменяемых ссылок, перекладывая проверку правил заимствования с **времени компиляции** на **время выполнения**.

В этой главе мы разберёмся, что такое внутренняя изменяемость, какие типы её реализуют, и когда это хороший дизайн, а когда — сигнал архитектурной проблемы.

Все примеры этой главы используют **Rust Edition 2024** и подготовлены для запуска непосредственно в [Rust Playground](https://play.rust-lang.org/).

---

## 22.1. Ограничение: неизменяемая ссылка означает неизменяемость

Во всех предыдущих главах мы последовательно опирались на одно и то же правило: если у значения нет `&mut`-доступа, изменить его нельзя.

```rust
fn main() {
    let data = 42;

    // data = 100; // ошибка: data не объявлена как mut
}
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=fn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%2042%3B%0A%0A%20%20%20%20%2F%2F%20data%20%3D%20100%3B%0A%7D)

Это же правило распространяется и на ссылки: `&T` даёт только чтение, а изменить значение через неё нельзя, даже если сама исходная переменная объявлена как `mut`:

```rust
fn main() {
    let mut data = 42;
    let r: &i32 = &data;

    // *r = 100; // ошибка: r — неизменяемая ссылка
    println!("{r}");
}
```

[▶ Открыть пример с ошибкой в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=fn%20main%28%29%20%7B%0A%20%20%20%20let%20mut%20data%20%3D%2042%3B%0A%20%20%20%20let%20r%3A%20%26i32%20%3D%20%26data%3B%0A%0A%20%20%20%20%2F%2F%20%2Ar%20%3D%20100%3B%0A%20%20%20%20println%21%28%22%7Br%7D%22%29%3B%0A%7D)

Раскомментируйте строку `*r = 100;` — компилятор откажется собирать программу: `cannot assign to *r, which is behind a & reference`.

Это разумное и полезное правило: оно, например, лежит в основе всей модели заимствования из глав 12–13 — компилятор может гарантировать отсутствие гонок данных именно потому, что неизменяемая ссылка действительно неизменяема.

Но на практике время от времени возникает задача, которая, казалось бы, требует нарушить именно это правило. Например:

* нескольким частям программы нужно совместно владеть значением (через `Rc<T>` из главы 21), но при этом хотя бы одной из них иногда требуется его изменить;
* структура должна выглядеть неизменяемой снаружи (например, реализовывать кеш за read-only методом), но внутри ей нужно обновлять служебное состояние;
* сам `Rc<T>` устроен так, что его счётчик ссылок увеличивается при каждом `Rc::clone(&self)` — а `clone` принимает `&self`, то есть неизменяемую ссылку, и тем не менее должен изменить внутренний счётчик.

Ни один из этих сценариев не решается обычными `&T`/`&mut T` — по определению, `&self` не даёт права ничего менять. Означает ли это, что такие задачи в Rust невыполнимы?

Нет — но для их решения понадобится механизм, который работает не по тем же правилам, что обычные ссылки. Именно этот механизм называется **внутренней изменяемостью (interior mutability)**, и именно ему посвящена оставшаяся часть главы.

## 22.2. Что такое внутренняя изменяемость?

**Внутренняя изменяемость (interior mutability)** — это механизм, позволяющий изменять данные через неизменяемое снаружи значение.

Обычные правила Rust выглядят так:

```rust
let data = 42;
```

После этого нельзя получить изменяемую ссылку:

```rust
let data = 42;

// &mut data
```

Но некоторые типы стандартной библиотеки предоставляют специальный API, позволяющий изменять их внутреннее состояние даже через `&self`.

Простейший пример — `Cell<T>`:

```rust
use std::cell::Cell;

fn main() {
    let value = Cell::new(42);

    value.set(100);

    println!("{}", value.get());
}

```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ACell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20value%20%3D%20Cell%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20value.set%28100%29%3B%0A%0A%20%20%20%20println%21%28%22%7B%7D%22%2C%20value.get%28%29%29%3B%0A%7D)

Здесь переменная `value` сама не объявлена как `mut`:

```rust
let value = Cell::new(42);
```

Тем не менее вызов:

```rust
value.set(100);
```

изменяет значение, находящееся внутри `Cell`.

Это и есть interior mutability.

Однако важно понимать: **interior mutability — это не один конкретный механизм**.

Например:

* `Cell<T>` предоставляет изменение без получения ссылок на внутреннее значение;
* `RefCell<T>` позволяет получать ссылки, проверяя правила заимствования во время выполнения;
* `Mutex<T>` и `RwLock<T>` предоставляют изменяемый доступ с синхронизацией между потоками;
* `UnsafeCell<T>` является фундаментальным примитивом, на котором строятся многие механизмы внутренней изменяемости.

Поэтому фраза «interior mutability переносит borrow checking на runtime» подходит прежде всего к `RefCell<T>`, но **не ко всей категории interior mutability**.

## 22.3. `Cell<T>` — простая внутренняя изменяемость

`Cell<T>` предназначен для простых случаев, когда необходимо заменить или получить значение, но не требуется выдавать ссылки на содержимое.

```rust
use std::cell::Cell;

fn main() {
    let data = Cell::new(42);

    println!("data: {}", data.get());

    data.set(100);

    println!("data: {}", data.get());

    let value = data.take();

    println!("value: {}, data: {}", value, data.get());
}

```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ACell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20Cell%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20println%21%28%22data%3A%20%7B%7D%22%2C%20data.get%28%29%29%3B%0A%0A%20%20%20%20data.set%28100%29%3B%0A%0A%20%20%20%20println%21%28%22data%3A%20%7B%7D%22%2C%20data.get%28%29%29%3B%0A%0A%20%20%20%20let%20value%20%3D%20data.take%28%29%3B%0A%0A%20%20%20%20println%21%28%22value%3A%20%7B%7D%2C%20data%3A%20%7B%7D%22%2C%20value%2C%20data.get%28%29%29%3B%0A%7D)

У `Cell<T>` нет методов `borrow()` и `borrow_mut()`. Вместо этого используются операции над самим значением.

Например:

```rust
data.set(100);
```

заменяет значение.

Метод:

```rust
data.get();
```

возвращает копию значения.

Именно поэтому `get()` требует:

```rust
T: Copy
```

Но это **не означает, что весь `Cell<T>` работает только с `Copy`-типами**.

Например, `Cell<String>` также допустим:

```rust
use std::cell::Cell;

fn main() {
    let data = Cell::new(String::from("hello"));

    data.set(String::from("world"));

    println!("{}", data.take());
}

```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ACell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20Cell%3A%3Anew%28String%3A%3Afrom%28%22hello%22%29%29%3B%0A%0A%20%20%20%20data.set%28String%3A%3Afrom%28%22world%22%29%29%3B%0A%0A%20%20%20%20println%21%28%22%7B%7D%22%2C%20data.take%28%29%29%3B%0A%7D)

Главное ограничение `Cell<T>` другое:

> `Cell<T>` не позволяет получать обычную ссылку на своё внутреннее значение.

Это принципиальное отличие от `RefCell<T>`.

## 22.4. `RefCell<T>` — изменяемость с проверкой во время выполнения

`RefCell<T>` используется тогда, когда обычные правила заимствования невозможно удобно выразить на этапе компиляции.

Он позволяет получать:

```rust
borrow()
```

для неизменяемого заимствования и:

```rust
borrow_mut()
```

для изменяемого.

Проверка выполняется **во время выполнения программы**.

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(42);

    let r1 = data.borrow();
    let r2 = data.borrow();

    println!("r1: {}, r2: {}", r1, r2);

    drop(r1);
    drop(r2);

    let mut r3 = data.borrow_mut();
    *r3 = 100;

    println!("r3: {}", r3);

    drop(r3);

    println!("final: {}", data.borrow());
}

```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ARefCell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20RefCell%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20let%20r1%20%3D%20data.borrow%28%29%3B%0A%20%20%20%20let%20r2%20%3D%20data.borrow%28%29%3B%0A%0A%20%20%20%20println%21%28%22r1%3A%20%7B%7D%2C%20r2%3A%20%7B%7D%22%2C%20r1%2C%20r2%29%3B%0A%0A%20%20%20%20drop%28r1%29%3B%0A%20%20%20%20drop%28r2%29%3B%0A%0A%20%20%20%20let%20mut%20r3%20%3D%20data.borrow_mut%28%29%3B%0A%20%20%20%20%2Ar3%20%3D%20100%3B%0A%0A%20%20%20%20println%21%28%22r3%3A%20%7B%7D%22%2C%20r3%29%3B%0A%0A%20%20%20%20drop%28r3%29%3B%0A%0A%20%20%20%20println%21%28%22final%3A%20%7B%7D%22%2C%20data.borrow%28%29%29%3B%0A%7D)

Важный момент:

```rust
let r1 = data.borrow();
let r2 = data.borrow();
```

разрешён, потому что несколько читателей могут существовать одновременно.

Но:

```rust
let r1 = data.borrow();
let r2 = data.borrow_mut();
```

нарушает правила заимствования.

Разница состоит в том, **когда обнаруживается нарушение**:

```text
обычная ссылка
      ↓
компилятор
      ↓
ошибка компиляции


RefCell
      ↓
runtime borrow checking
      ↓
panic при нарушении
```

`RefCell<T>` не делает неправильное заимствование безопасным. Он позволяет обнаружить его во время выполнения и остановить выполнение через `panic`.

## 22.5. 🔨 Эксперимент: паника при нарушении правил

Попробуем одновременно создать неизменяемое и изменяемое заимствование:

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(42);

    let r1 = data.borrow();
    let r2 = data.borrow_mut();

    println!("{} {}", r1, r2);
}

```

[▶ Открыть пример с паникой в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ARefCell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20RefCell%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20let%20r1%20%3D%20data.borrow%28%29%3B%0A%20%20%20%20let%20r2%20%3D%20data.borrow_mut%28%29%3B%0A%0A%20%20%20%20println%21%28%22%7B%7D%20%7B%7D%22%2C%20r1%2C%20r2%29%3B%0A%7D)

Программа завершится паникой.

Причина — в момент вызова:

```rust
data.borrow_mut()
```

у `RefCell` уже существует активное неизменяемое заимствование.

В отличие от обычного `&T` / `&mut T`, это нарушение не обнаруживается компилятором.

`RefCell<T>` обнаруживает его во время выполнения.

## 22.6. `Cell<T>` vs `RefCell<T>`

| Характеристика                               | `Cell<T>`                      | `RefCell<T>`            |
| -------------------------------------------- | ------------------------------ | ----------------------- |
| Внутренняя изменяемость                      | Да                             | Да                      |
| Получение значения                           | `get()` для `Copy`             | `borrow()`              |
| Изменение                                    | `set()`, `replace()`, `take()` | `borrow_mut()`          |
| Получение ссылки на значение                 | Нет                            | Да                      |
| Runtime borrow checking                      | Нет                            | Да                      |
| Возможна паника из-за нарушения borrow rules | Нет                            | Да                      |
| Работа с `Copy` типами                       | Да                             | Да                      |
| Работа с произвольными типами                | Да, но API ограничен           | Да                      |
| Основное применение                          | Простое состояние              | Более сложные структуры |

Практическое правило можно сформулировать так:

> Если достаточно заменить значение целиком и не нужно получать ссылку на него — сначала посмотрите на `Cell<T>`.

> Если необходимо временно получить `&T` или `&mut T` через неизменяемый объект — подходит `RefCell<T>`.

При этом не стоит автоматически считать `Cell<T>` «быстрее», а `RefCell<T>` «медленнее» в любой программе. Реальная стоимость зависит от конкретного кода, оптимизаций компилятора и того, какие операции выполняются.

## 22.7. `RefCell<T>` и `Rc<T>` — мощное сочетание

Сочетание `Rc<T>` и `RefCell<T>` позволяет иметь несколько владельцев и изменять данные:

```rust
use std::rc::Rc;
use std::cell::RefCell;

fn main() {
    let data = Rc::new(RefCell::new(42));

    let a = Rc::clone(&data);
    let b = Rc::clone(&data);

    *a.borrow_mut() = 100;

    println!("a: {}, b: {}", a.borrow(), b.borrow());
}
```

**Вывод:** `a: 100, b: 100`

## 22.8. `Mutex<T>` и `RwLock<T>` — потокобезопасная изменяемость

Для многопоточных программ используются `Mutex<T>` и `RwLock<T>`:

```rust
use std::sync::Mutex;

fn main() {
    let data = Mutex::new(42);

    {
        let mut guard = data.lock().unwrap();
        *guard = 100;
    } // guard освобождается

    let value = data.lock().unwrap();
    println!("{}", value);
}
```

| Тип | Для чего | Блокировка |
|---|---|---|
| `Mutex<T>` | Одновременный доступ из нескольких потоков | Взаимное исключение |
| `RwLock<T>` | Разделение на читателей и писателей | Много читателей, один писатель |

## 22.9. `UnsafeCell<T>` — фундамент внутренней изменяемости

В основе модели внутренней изменяемости Rust находится специальный тип:

```rust
UnsafeCell<T>
```

`UnsafeCell<T>` сообщает компилятору, что значение внутри может изменяться даже тогда, когда сам `UnsafeCell` доступен через `&`.

Это фундаментальный механизм, необходимый для реализации низкоуровневых абстракций с изменяемым состоянием.

Однако `UnsafeCell<T>` **сам по себе не предоставляет безопасного API для произвольного изменения данных**.

Например, его можно использовать следующим образом:

```rust
use std::cell::UnsafeCell;

struct MyCell<T> {
    value: UnsafeCell<T>,
}

impl<T> MyCell<T> {
    fn new(value: T) -> Self {
        Self {
            value: UnsafeCell::new(value),
        }
    }

    fn set(&self, value: T) {
        unsafe {
            *self.value.get() = value;
        }
    }
}

fn main() {
    let cell = MyCell::new(42);

    cell.set(100);

    println!("done");
}

```

Здесь появляется `unsafe`, потому что компилятор больше не может самостоятельно проверить все необходимые инварианты.

Именно поэтому `UnsafeCell<T>` следует рассматривать не как обычный smart pointer и не как готовый способ «обойти borrow checker», а как **низкоуровневый строительный блок** для создания безопасных абстракций.

`Cell<T>`, `RefCell<T>` и многие другие типы стандартной библиотеки используют эту возможность внутри своей реализации.

Главная ответственность при непосредственной работе с `UnsafeCell<T>` ложится уже на разработчика: он должен доказать, что созданная им абстракция не нарушает требования Rust к безопасности памяти.

## 22.10. Compile-time vs Runtime borrow checking

У Rust существует несколько разных способов обеспечить корректный доступ к данным.

| Механизм        | Когда проверяется | Что происходит при нарушении            |
| --------------- | ----------------- | --------------------------------------- |
| `&T` / `&mut T` | Compile time      | Ошибка компиляции                       |
| `RefCell<T>`    | Runtime           | `panic`                                 |
| `Mutex<T>`      | Runtime           | Блокировка или ошибка блокировки        |
| `RwLock<T>`     | Runtime           | Блокировка или ошибка блокировки        |
| `Cell<T>`       | Через API типа    | Конфликтующие ссылки наружу не выдаются |

Здесь важно не смешивать две разные задачи.

`RefCell<T>` решает задачу **внутренней изменяемости в пределах одного потока выполнения**.

`Mutex<T>` и `RwLock<T>` решают другую задачу — **синхронизацию доступа к общим данным между потоками**.

Поэтому `Mutex<T>` нельзя рассматривать просто как «потокобезопасный `RefCell<T>`». У этих типов разные модели использования и разные гарантии.

---

## 22.11. Почему interior mutability не нарушает модель Rust

На первый взгляд может показаться, что:

```rust
let value = Cell::new(42);
value.set(100);
```

нарушает правило:

> неизменяемый объект нельзя изменять.

Но правило Rust относится не к любой внутренней детали объекта, а к **гарантиям, которые предоставляет его тип и его API**.

`Cell<T>` специально устроен так, чтобы не выдавать конфликтующие обычные ссылки на своё внутреннее значение.

`RefCell<T>` следит за правилами заимствования во время выполнения.

`Mutex<T>` и `RwLock<T>` обеспечивают синхронизацию доступа между потоками.

Таким образом, interior mutability не является лазейкой, позволяющей произвольно нарушать правила Rust.

Напротив, это **формализованный механизм изменения способа проверки инвариантов**.

При использовании безопасных типов стандартной библиотеки разработчику не требуется самостоятельно писать `unsafe`.

А при создании собственной абстракции на основе `UnsafeCell<T>` именно разработчик отвечает за соблюдение необходимых инвариантов.

## 22.12. Когда внутренняя изменяемость — хороший дизайн

1. **Структуры с кешем** — когда данные редко меняются, но могут обновляться.

   ```rust
   struct Cache {
       data: RefCell<HashMap<String, String>>,
   }
   ```

2. **Счётчики ссылок** — `Rc<T>` использует внутреннюю изменяемость для счётчика.

3. **Ленивая инициализация** — `LazyCell` и `OnceCell`.

4. **Моки для тестирования** — когда нужно подменять поведение.

---

## 22.13. Когда это сигнал архитектурной проблемы

1. **Слишком частое использование `RefCell`** — возможно, стоит пересмотреть дизайн.

2. **Циклические ссылки** — `RefCell` + `Rc` могут создавать циклы.

3. **Сложность отладки** — паники `RefCell` могут быть трудны для отладки.

4. **Производительность** — `RefCell` добавляет накладные расходы.

## 🔨 Эксперименты с компилятором

### Эксперимент 1: `RefCell` не требует `mut` снаружи

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(42);
    let mut r = data.borrow_mut();
    *r = 100;
    println!("{}", r);
}
```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ARefCell%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20RefCell%3A%3Anew%2842%29%3B%0A%20%20%20%20let%20mut%20r%20%3D%20data.borrow_mut%28%29%3B%0A%20%20%20%20%2Ar%20%3D%20100%3B%0A%20%20%20%20println%21%28%22%7B%7D%22%2C%20r%29%3B%0A%7D)

Обратите внимание: переменная `data` объявлена **без** `mut`:

```rust
let data = RefCell::new(42);
```

и тем не менее вызов `data.borrow_mut()` компилируется и позволяет изменить значение внутри. Это не ошибка и не поблажка компилятора — это и есть суть interior mutability, о которой шла речь в начале главы: тип `RefCell<T>` спроектирован так, что его метод `borrow_mut(&self)` принимает `&self`, а не `&mut self`, и сам решает, можно ли выдать изменяемый доступ, проверяя это во время выполнения, а не полагаясь на то, объявлен ли сам `data` как `mut`.

Единственное место, где `mut` всё же нужен — это сама переменная `r`:

```rust
let mut r = data.borrow_mut();
```

`r` имеет тип `RefMut<i32>` — это временная обёртка-«охранник» (guard), которая реализует `DerefMut`. Чтобы записать через неё значение (`*r = 100`), компилятору нужно вызвать `DerefMut::deref_mut(&mut r)`, а для этого сама переменная `r` обязана быть изменяемым биндингом — точно так же, как в главе о заимствовании обычная `&mut T`-ссылка требует `let mut` для переменной, хранящей саму ссылку. Это `mut` относится к промежуточной переменной-обёртке, а не к исходным данным `data`.

### Эксперимент 2: Паника при нарушении правил

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(42);
    let r1 = data.borrow();
    let r2 = data.borrow_mut(); // Паника!
}
```

### Эксперимент 3: `RefCell<T>` и многопоточность

Здесь важно не допустить распространённой ошибки.

`RefCell<T>` не является `Sync`, но это **не означает, что любой `RefCell<T>` нельзя передать в другой поток**.

Например, если владение `RefCell<T>` целиком передаётся новому потоку, это может быть допустимо:

```rust
use std::cell::RefCell;
use std::thread;

fn main() {
    let data = RefCell::new(42);

    let handle = thread::spawn(move || {
        *data.borrow_mut() = 100;

        println!("{}", data.borrow());
    });

    handle.join().unwrap();
}

```

[▶ Открыть пример в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ARefCell%3B%0Ause%20std%3A%3Athread%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20RefCell%3A%3Anew%2842%29%3B%0A%0A%20%20%20%20let%20handle%20%3D%20thread%3A%3Aspawn%28move%20%7C%7C%20%7B%0A%20%20%20%20%20%20%20%20%2Adata.borrow_mut%28%29%20%3D%20100%3B%0A%0A%20%20%20%20%20%20%20%20println%21%28%22%7B%7D%22%2C%20data.borrow%28%29%29%3B%0A%20%20%20%20%7D%29%3B%0A%0A%20%20%20%20handle.join%28%29.unwrap%28%29%3B%0A%7D)

Это возможно потому, что значение целиком принадлежит новому потоку.

Проблема возникает, если несколько потоков должны **одновременно обращаться к одним и тем же данным**.

Например, попытка использовать `Arc<RefCell<T>>` для общего состояния не работает:

```rust
use std::cell::RefCell;
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(RefCell::new(42));

    let shared = Arc::clone(&data);

    thread::spawn(move || {
        *shared.borrow_mut() = 100;
    });
}

```

[▶ Открыть пример с ошибкой в Rust Playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&code=use%20std%3A%3Acell%3A%3ARefCell%3B%0Ause%20std%3A%3Async%3A%3AArc%3B%0Ause%20std%3A%3Athread%3B%0A%0Afn%20main%28%29%20%7B%0A%20%20%20%20let%20data%20%3D%20Arc%3A%3Anew%28RefCell%3A%3Anew%2842%29%29%3B%0A%0A%20%20%20%20let%20shared%20%3D%20Arc%3A%3Aclone%28%26data%29%3B%0A%0A%20%20%20%20thread%3A%3Aspawn%28move%20%7C%7C%20%7B%0A%20%20%20%20%20%20%20%20%2Ashared.borrow_mut%28%29%20%3D%20100%3B%0A%20%20%20%20%7D%29%3B%0A%7D)

Причина — `RefCell<T>` не является `Sync`.

Для общего изменяемого состояния между потоками обычно используется:

```rust
Arc<Mutex<T>>
```

или:

```rust
Arc<RwLock<T>>
```

Это важное различие:

```text
RefCell<T>
    ↓
runtime borrow checking
    ↓
один поток


Mutex<T> / RwLock<T>
    ↓
синхронизация
    ↓
несколько потоков
```

## Главное из этой главы

После этой главы мы понимаем:

- **Внутренняя изменяемость** позволяет изменять данные через неизменяемую ссылку.
- **`Cell<T>`** — для `Copy` типов, без ссылок и паники.
- **`RefCell<T>`** — для любых типов, с проверкой во время выполнения.
- **`Mutex<T>` и `RwLock<T>`** — для многопоточных программ.
- **`UnsafeCell<T>`** — основа всех типов для внутренней изменяемости.
- **Компилятор vs Runtime** — проверка правил заимствования может быть на этапе компиляции или выполнения.
- **Хороший дизайн** — внутренняя изменяемость полезна для кешей, счётчиков, ленивой инициализации.
- **Сигнал проблемы** — слишком частое использование может указывать на архитектурные проблемы.

**Самая важная идея:**

> Внутренняя изменяемость — это мощный инструмент, который расширяет модель владения Rust. Она позволяет писать гибкий код, но требует осторожности. Правильный выбор между проверкой на этапе компиляции и проверкой во время выполнения — ключ к безопасному и эффективному коду.
